# C1.4 · Mô hình bộ nhớ — `Ad → Ex`

> **Mục tiêu của tài liệu.** Đưa người đọc từ "biết có stack và heap" lên "mở được `/proc/PID/maps` và giải thích từng dòng, đọc được core dump, và **chứng minh** được một firmware không tràn stack".
>
> Đây là tài liệu **hội tụ** của cụm C1. Ba tài liệu trước tiếp cận bộ nhớ từ ba phía:
> * **C1.1** cho bạn con trỏ, padding, `malloc`/`free`, UB.
> * **C1.2** cho bạn refcount, GC, và 20 MB runtime.
> * **C1.3** cho bạn ownership được compiler kiểm chứng.
>
> C1.4 nhìn xuống **tầng dưới cả ba**: cùng một tiến trình Linux, cùng một bộ nhớ ảo, cùng một allocator. Hiểu tầng này là điều kiện để giải thích được vì sao ba mô hình kia hành xử như vậy.
>
> **Điều kiện tiên quyết:** C1.1 §3, §5, §7, §13; C1.2 §9, §11; C1.3 §2 (đọc qua là đủ).
> **Điều kiện hoàn thành:** vượt Checkpoint §9 — đọc một core dump và chỉ ra nguyên nhân segfault bằng bằng chứng, **và** tính được cận trên stack của một firmware rồi chứng minh nó không tràn.

## 0. Cách dùng tài liệu và bộ công cụ

### 0.1 Nguyên tắc

Bộ nhớ là chủ đề dễ nói sai nhất vì ai cũng có một mô hình mơ hồ "đúng đủ để không sai ngay". Quy tắc của tài liệu này:

> **Mọi khẳng định về bố cục, kích thước và hành vi bộ nhớ phải kiểm chứng được bằng một lệnh cụ thể.** Nếu bạn không chỉ ra được lệnh đó, bạn đang đoán.

### 0.2 Bộ công cụ

| Công cụ | Trả lời câu hỏi |
|---|---|
| `/proc/PID/maps` | tiến trình đang có những vùng nhớ nào, quyền gì |
| `/proc/PID/smaps`, `smaps_rollup` | mỗi vùng tốn bao nhiêu RSS/PSS/swap thật |
| `/proc/PID/status` | `VmRSS`, `VmHWM`, `VmSize`, `VmStk`, `Threads` |
| `pmap -X PID` | bản đồ dễ đọc |
| `size`, `size -A` | `.text`/`.data`/`.bss` của một file ELF |
| `readelf -lSW` | segment và section, địa chỉ nạp |
| `nm -S --size-sort` | symbol nào chiếm bao nhiêu byte |
| `objdump -dr` | mã máy, prologue/epilogue, đồ thị gọi |
| `gcc -fstack-usage` | kích thước frame từng hàm (`.su`) |
| `gdb` + core dump | vì sao nó chết |
| ASan / UBSan / valgrind | lỗi bộ nhớ lúc chạy |
| `mallinfo2`, `malloc_stats`, `malloc_usable_size` | allocator đang giữ gì |
| `strace -e trace=memory` | `brk`/`mmap`/`munmap` thực tế |

## 1. Bố cục tiến trình

### 1.1 Bản đồ tổng quát

```
địa chỉ CAO   0x7fff_ffff_ffff
  ┌──────────────────────────┐
  │ [vsyscall] / [vdso]      │  kernel ánh xạ vào, gọi hàm nhanh không syscall
  ├──────────────────────────┤
  │ [stack]                  │  MỌC XUỐNG ↓   biến cục bộ, đối số, địa chỉ trả về
  ├──────────────────────────┤
  │ ↓ guard page ↓           │  trang không quyền — chạm vào = SIGSEGV
  │                          │
  │      (khoảng trống)      │
  │                          │
  ├──────────────────────────┤
  │ vùng mmap                │  MỌC XUỐNG ↓   thư viện .so, malloc lớn, file map
  │  libc.so, ld.so, ...     │
  ├──────────────────────────┤
  │                          │
  ├──────────────────────────┤
  │ [heap]                   │  MỌC LÊN ↑     brk / sbrk, malloc nhỏ
  ├──────────────────────────┤
  │ .bss                     │  biến toàn cục = 0, KHÔNG chiếm chỗ trong file
  ├──────────────────────────┤
  │ .data                    │  biến toàn cục có giá trị khởi tạo ≠ 0
  ├──────────────────────────┤
  │ .rodata                  │  hằng số, string literal — CHỈ ĐỌC
  ├──────────────────────────┤
  │ .text                    │  mã máy — CHỈ ĐỌC + THỰC THI
  └──────────────────────────┘
địa chỉ THẤP  0x0000_0000_0000   ← trang 0 không bao giờ được ánh xạ (bắt deref NULL)
```

### 1.2 Kiểm chứng: in địa chỉ từng loại object

✅ Chương trình sau in địa chỉ thật của mỗi loại (biên dịch `-no-pie`, chạy với ASLR tắt để địa chỉ ổn định):

```c
int   g_init      = 42;        /* .data   */
int   g_zero;                  /* .bss    */
const int g_ro    = 7;         /* .rodata */
char  g_big[1 << 20];          /* .bss 1 MiB */
const char *g_str = "chuoi hang";

int main(void) {
    int  local       = 1;
    void *heap_small = malloc(64);
    void *heap_big   = malloc(8u << 20);     /* 8 MiB -> mmap */
    void *anon = mmap(NULL, 4096, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
    /* ... in ra ... */
}
```
✅ Output thật:
```text
&f           (.text)             0x401276
&g_ro        (.rodata)           0x402004
g_str        (.rodata)           0x402008
&g_init      (.data)             0x404068
&g_zero      (.bss)              0x4040a0
&g_big       (.bss)              0x4040c0
malloc(64)   (heap)              0x5052a0
sbrk(0)      (brk)               0x526000
malloc(8MiB) (mmap)        0x7ffff73ff010
mmap(4K)     (mmap)        0x7ffff7fba000
&local       (stack)       0x7fffffffe73c
```
Thứ tự địa chỉ khớp chính xác sơ đồ §1.1: `.text < .rodata < .data < .bss < heap ≪ mmap ≪ stack`.

⚠️ Chú ý `malloc(8MiB)` trả `0x7ffff73ff010` — kết thúc bằng **`010`**, không phải `000`. 16 byte đầu của vùng mmap là **header chunk của glibc** (§3.3). Đây là chi tiết bạn sẽ dùng khi đọc core dump.

### 1.3 `.bss` không chiếm chỗ trong file

Đây là điều bị hiểu sai nhiều nhất về bố cục ELF.

✅
```text
$ size layout
   text     data      bss      dec      hex   filename
   3341      640  1048648  1052629   100fd5  layout

$ ls -la layout
20224 byte
```
`.bss` là **1.048.648 byte** nhưng file chỉ **20.224 byte**. Lý do: `.bss` chỉ được ghi trong header ELF dưới dạng *"cần N byte, toàn số 0"*. Kernel ánh xạ trang zero khi nạp.

Hệ quả thực tế:
* `static char buf[1<<20];` **không** làm binary to thêm; `static char buf[1<<20] = {1};` **có** (nó vào `.data`).
* Trong firmware, `.bss` chiếm **RAM** nhưng không chiếm **flash**; `.data` chiếm **cả hai** (bản gốc nằm trong flash, được copy sang RAM lúc khởi động). Xem §7.2.

| Section | Trong file? | Trong RAM? | Quyền |
|---|---|---|---|
| `.text` | ✔ | ✔ | r-x |
| `.rodata` | ✔ | ✔ | r-- |
| `.data` | ✔ | ✔ | rw- |
| `.bss` | ✘ | ✔ | rw- |
| heap / stack | ✘ | ✔ | rw- |

### 1.4 Đọc `/proc/PID/maps`

✅ Trích từ tiến trình thật ở trên:
```text
00400000-00401000 r--p 00000000 fe:00 647231   /home/claude/mem/layout
00401000-00402000 r-xp 00001000 fe:00 647231   /home/claude/mem/layout
00402000-00403000 r--p 00002000 fe:00 647231   /home/claude/mem/layout
00404000-00405000 rw-p 00003000 fe:00 647231   /home/claude/mem/layout
00405000-00505000 rw-p 00000000 00:00 0
00505000-00526000 rw-p 00000000 00:00 0        [heap]
7ffff73ff000-7ffff7c00000 rw-p 00000000 00:00 0
7ffff7c00000-7ffff7c28000 r--p 00000000 fe:00 2826273  /usr/lib/.../libc.so.6
7ffff7c28000-7ffff7db1000 r-xp 00028000 fe:00 2826273  /usr/lib/.../libc.so.6
7ffff7fc3000-7ffff7fc5000 r-xp 00000000 00:00 0        [vdso]
7ffffffde000-7ffffffff000 rw-p 00000000 00:00 0        [stack]
```

**Cách đọc từng cột:**
```
00401000-00402000  r-xp  00001000  fe:00  647231  /path
└──── khoảng ────┘ └──┘ └offset─┘ └dev┘ └inode┘ └file┘
                    │││└ p = private (COW) / s = shared
                    ││└─ x = thực thi
                    │└── w = ghi
                    └─── r = đọc
```

Bốn điều đáng để ý ngay:
1. **Một file được map nhiều lần với quyền khác nhau.** `layout` xuất hiện 4 lần: `r--` (ELF header + `.rodata` phần đầu), `r-x` (`.text`), `r--` (`.rodata`, RELRO), `rw-` (`.data`). Đây là bảo vệ **W^X**: không vùng nào vừa ghi được vừa thực thi được.
2. **Vùng `00405000-00505000` (1 MiB) không có tên file** — đó chính là `g_big[1<<20]` trong `.bss`, được ánh xạ ẩn danh.
3. **`[heap]` bắt đầu ngay sau `.bss`** và mở rộng bằng `brk`.
4. **`[stack]` chỉ 132 KiB** (`0x7ffffffde000`–`0x7ffffffff000`), dù `ulimit -s` là 8 MiB. Kernel chỉ ánh xạ phần đã dùng; vùng này **tự mở rộng xuống** khi cần, cho đến giới hạn.

### 1.5 VSZ, RSS, PSS — ba con số khác nhau

| Chỉ số | Nghĩa | Ở đâu |
|---|---|---|
| **VSZ** (`VmSize`) | tổng địa chỉ ảo đã đặt chỗ, kể cả chưa dùng | `status` |
| **RSS** (`VmRSS`) | trang vật lý đang thường trú | `status` |
| **VmHWM** | **đỉnh** RSS từ đầu tiến trình | `status` |
| **PSS** | RSS nhưng trang chia sẻ được chia đều cho các tiến trình | `smaps_rollup` |
| **VmStk** | kích thước vùng stack | `status` |

⚠️ VSZ gần như vô dụng để đo "tốn bao nhiêu RAM": `malloc(1 GiB)` mà không ghi gì làm VSZ tăng 1 GiB nhưng RSS tăng ~0, vì Linux **overcommit** và chỉ cấp trang vật lý khi ghi lần đầu (page fault).

Khi so sánh nhiều tiến trình dùng chung thư viện, **PSS** mới công bằng:
```sh
grep -E '^(Rss|Pss|Private_Dirty)' /proc/PID/smaps_rollup
```

### 1.6 ASLR và PIE

Mặc định Linux bật **ASLR**: mỗi lần chạy, stack, heap, mmap và (với PIE) cả `.text` nằm ở địa chỉ khác nhau.

```sh
setarch -R ./prog        # tắt ASLR cho lần chạy này (dễ debug)
cat /proc/sys/kernel/randomize_va_space   # 0=tắt 1=một phần 2=đầy đủ
gcc -no-pie ...          # địa chỉ nạp cố định 0x400000
gcc -fPIE -pie ...       # mặc định hiện nay: nạp ngẫu nhiên
```
⚠️ Khi đọc core dump của binary PIE, địa chỉ tuyệt đối trong log **không so sánh trực tiếp** với `objdump` được. Dùng `gdb` (nó tự tính offset), hoặc `addr2line -e prog -f -C $((addr - base))`.

## 2. Stack frame, calling convention, stack overflow, đo stack usage

### 2.1 Stack frame trên x86-64

Nhắc lại C1.1 §13.7, giờ nhìn từ phía bộ nhớ:

```
địa chỉ CAO
  ┌────────────────────────┐
  │ đối số thứ 7, 8, …     │  caller đẩy (6 đối số đầu đi bằng thanh ghi)
  ├────────────────────────┤
  │ địa chỉ trả về         │  ← lệnh `call` đẩy
  ├────────────────────────┤
  │ saved rbp              │  ← `push rbp`
  ├────────────────────────┤ ← rbp
  │ canary (nếu bật)       │
  │ biến cục bộ, mảng      │
  │ vùng spill thanh ghi   │
  ├────────────────────────┤ ← rsp
  │ red zone 128 byte      │  hàm lá dùng được mà không đổi rsp
  └────────────────────────┘
địa chỉ THẤP  (stack mọc xuống)
```

### 2.2 Prologue/epilogue thật

✅ `gcc -O2 -S -masm=intel`, ba hàm có đặc điểm khác nhau:

```asm
leaf:                       ; int leaf(int a, int b) { return a*b + 1; }
        endbr64
        imul    edi, esi
        lea     eax, 1[rdi]
        ret                 ; KHÔNG chạm rsp: hàm lá, dùng thanh ghi + red zone
```
```asm
big:                        ; int big(int n) { int arr[1024]; ... }
        endbr64
        sub     rsp, 4096
        or      QWORD PTR [rsp], 0     ; <- STACK PROBE: chạm từng trang
        sub     rsp, 24
        mov     rax, QWORD PTR fs:40   ; <- CANARY: lấy từ TLS
        mov     QWORD PTR 4104[rsp], rax
        ...
        mov     rdx, QWORD PTR 4104[rsp]
        sub     rdx, QWORD PTR fs:40   ; <- kiểm tra canary
        jne     .L9                    ;    khác -> __stack_chk_fail
        add     rsp, 4120
        ret
```

Ba cơ chế bảo vệ nhìn thấy được trong mã sinh ra:

| Cơ chế | Cờ | Làm gì |
|---|---|---|
| **Stack canary** | `-fstack-protector-strong` (mặc định Ubuntu) | giá trị bí mật từ `fs:40` đặt trước địa chỉ trả về; sai → `__stack_chk_fail` |
| **Stack probe** | `-fstack-clash-protection` (mặc định) | chạm từng trang khi frame > 1 trang, để **không nhảy qua guard page** |
| **`endbr64`** | `-fcf-protection` (mặc định) | điểm đích hợp lệ cho indirect branch (Intel CET) |

⚠️ Stack probe quan trọng hơn vẻ ngoài: không có nó, một hàm có `char buf[16384]` sẽ dời `rsp` xuống **vượt qua** guard page và ghi thẳng vào vùng khác mà không sinh fault — đó là lớp lỗ hổng *stack clash*.

### 2.3 Stack overflow xảy ra thế nào

Kernel đặt một **guard page** (trang không quyền) ngay dưới vùng stack. Khi stack mọc chạm tới:
* nếu là truy cập hợp lệ ngay dưới đáy → kernel **tự mở rộng** vùng stack;
* nếu đã chạm giới hạn `RLIMIT_STACK` → **SIGSEGV**.

✅ Thí nghiệm: đệ quy vô hạn, mỗi frame chứa `char scratch[1024]`.
```text
$ ulimit -s
8192
$ ./crash2
Segmentation fault (core dumped)     exit=139   (128 + SIGSEGV(11))
```
✅ Phân tích core:
```text
#0  0x...1b9 in walk (n=<error reading variable: Cannot access memory at 0x7ffdca13cf68>)
#7701 ... in walk (n=4)
#7702 ... in walk (n=3)
#7703 ... in walk (n=2)
#7704 ... in walk (n=1)
#7705 ... in main ()

$1 = 7704                                     (biến depth)
$2 = (void *) 0x7ffdca13cf68                  (si_addr — địa chỉ gây fault)
$3 = (void *) 0x7ffdca13cf60                  (rsp)
Stack level 0, frame at 0x7ffdca13d3a0:
 called by frame at 0x7ffdca13d7e0
```
Ba bằng chứng khớp nhau:
1. `si_addr` (`0x…cf68`) chỉ cách `rsp` (`0x…cf60`) đúng **8 byte** — đó là lần `push` địa chỉ trả về chạm vào guard page.
2. Kích thước một frame = `0x7ffdca13d7e0 − 0x7ffdca13d3a0` = **1088 byte**.
3. ✅ `-fstack-usage` cho cùng con số: `crash2.c:7:13:walk  1088  static`.

**Kiểm tra bằng số học:**
```
8.388.608 byte / 1088 byte = 7710 frame lý thuyết
đo được: 7705 frame
chênh: 5 frame  (frame của main + phần khởi động libc)
```
Sai số 0,06%. Đây là cách bạn **tin** một mô hình: nó dự đoán được con số trước khi bạn đo.

⚠️ Stack overflow **trên thread** nguy hiểm hơn: thread dùng stack cấp phát bằng `mmap` với kích thước cố định (mặc định 8 MiB), và tràn có thể ghi đè vùng của thread khác nếu guard page bị vô hiệu.

### 2.4 Bốn cách đo stack usage

| Cách | Cho biết | Giới hạn |
|---|---|---|
| **`gcc -fstack-usage`** | kích thước frame **từng hàm** (file `.su`) | không tự cộng theo đường gọi; `dynamic` với VLA/alloca |
| **Phân tích tĩnh** (`.su` + đồ thị gọi) | **cận trên** cho toàn chương trình | hỏng khi có đệ quy / con trỏ hàm |
| **Stack painting** | high-water mark **thực tế** | chỉ đo được đường đã chạy |
| **`ulimit -s` + crash** | giới hạn | phá huỷ |

```text
$ cat frames.su
frames.c:4:5:leaf         8     static
frames.c:6:5:medium       8     static
frames.c:12:5:big      4128     static
frames.c:18:5:vla        32     dynamic     ← ⚠️ KHÔNG dùng để chứng minh được
frames.c:20:5:main       16     static
```

> ⚠️ Chữ **`dynamic`** trong `.su` là dấu hiệu bạn **không thể** chứng minh cận trên tĩnh. Đây chính là lý do C1.1 §4.5 và MISRA cấm VLA/`alloca` trong code quan trọng.

**Stack painting** — kỹ thuật chuẩn của công nghiệp nhúng:
```c
/* Lúc khởi động: tô toàn bộ stack chưa dùng bằng một mẫu nhận ra được */
memset(stack_base, 0xA5, paintable);
/* ... chạy hệ thống ...  */
/* Sau đó: quét từ đáy lên, đếm byte còn nguyên mẫu */
size_t untouched = 0;
while (untouched < paintable && stack_base[untouched] == 0xA5) untouched++;
size_t high_water = paintable - untouched;
```
Nó cho **giới hạn dưới** của mức dùng thật; phân tích tĩnh cho **giới hạn trên**. Hai cái kẹp lấy sự thật. Checkpoint §9.2 làm đúng điều đó.

### 2.5 Ảnh hưởng của tối ưu hoá

⚠️ Inline làm **thay đổi hoàn toàn** bố cục stack. ✅ Cùng một firmware:

```text
-O2                        -O2 -fno-inline
app_step    176 byte       app_step     48 byte
                           on_byte      16
                           deliver      16
                           log_frame   112
                           hexdump       8
```
Ở `-O2`, năm hàm gộp thành một frame 176 byte. Ở `-fno-inline`, chuỗi gọi cho tổng 200 byte.

> **Hệ quả cho việc chứng minh:** phân tích stack **phải chạy trên đúng binary sẽ được nạp**, với đúng cờ biên dịch. Phân tích ở `-O0` rồi ship `-O2` là phân tích một chương trình khác.

## 3. Heap: allocator hoạt động thế nào

### 3.1 Hai đường xin bộ nhớ từ kernel

```
malloc(n)
   │
   ├─ n < M_MMAP_THRESHOLD (mặc định 128 KiB)
   │     └─→ lấy từ arena; nếu hết, mở rộng bằng brk()      → vùng [heap]
   │
   └─ n ≥ M_MMAP_THRESHOLD
         └─→ mmap() riêng một vùng                           → vùng mmap
               free() sẽ munmap() trả thẳng về OS
```

✅ Kiểm chứng bằng `mallinfo2()`:
```text
                            brk                arena   hblks    hblkhd  uordblks  fordblks
khởi đầu            0x55924c3c8000                  0       0         0         0         0
sau malloc(64)      0x55924c3e9000             135168       0         0      4848    130320
sau malloc(100 KiB) 0x55924c3e9000             135168       0         0    107264     27904
sau malloc(200 KiB) 0x55924c3e9000             135168       1    208896    107264     27904

địa chỉ: a=0x55924c3c92b0  b=0x55924c3c9300  c=0x7f9972d71010
```
Đọc ra ba sự thật:
1. `malloc(64)` đầu tiên làm `brk` nhảy **135.168 byte** (132 KiB) — glibc xin dư rất nhiều để lần sau khỏi syscall.
2. `malloc(100 KiB)` **không** gọi syscall nào: lấy từ arena đã có (`fordblks` giảm).
3. `malloc(200 KiB)` làm `hblks` = 1 và `hblkhd` = 208.896 → đi bằng **mmap**, và địa chỉ `c` nhảy sang vùng `0x7f99…` cách xa heap.

⚠️ `M_MMAP_THRESHOLD` là **động**: khi bạn `free` một khối mmap, glibc nâng ngưỡng lên bằng kích thước đó (tối đa 32 MiB) để tránh lặp lại `mmap`/`munmap`. Đặt cố định bằng `mallopt(M_MMAP_THRESHOLD, n)` nếu cần hành vi tiên đoán được.

### 3.2 Chunk: header và làm tròn

Mỗi khối glibc cấp phát có một **header 8 byte** ngay trước con trỏ bạn nhận, chứa kích thước và cờ.

✅ Đo bằng `malloc_usable_size` và khoảng cách hai khối liên tiếp:
```text
 yêu cầu   usable    chunk  lãng phí
       1       24       32     3100%
       8       24       32      300%
      16       24       32      100%
      24       24       32       33%
      25       40       48       92%
      32       40       48       50%
      40       40       48       20%
      48       56       64       33%
      64       72       80       25%
     100      104      112       12%
    1000     1000     1008        1%
```
**Quy luật rút ra:** `usable = max(24, round_up(N + 8, 16) − 8)`, `chunk = usable + 8`.

✅ Và alignment luôn là 16:
```text
alignment của malloc: 16 byte (_Alignof(max_align_t))
  malloc(1) -> 0x563e03ab3050  (mod 16 = 0)
  malloc(1) -> 0x563e03ab3070  (mod 16 = 0)
```

> **Hệ quả thiết kế:** cấp phát nhiều object nhỏ là cách tốn bộ nhớ nhất. 1 triệu `malloc(8)` tốn **32 MB** thay vì 8 MB. Đây chính là lý do C1.1 §7.4–7.5 đề nghị arena và pool, và là một phần của 20 MB runtime Python ở C1.2 §9.1.

### 3.3 Các bin của glibc

```
tcache      64 bin, mỗi bin 7 khối, KHÔNG khoá — đường nhanh nhất (glibc ≥ 2.26)
fastbin     khối nhỏ (≤ 128B), LIFO, không hợp nhất ngay
unsorted    nơi tạm sau free, cho lần malloc sau thử trước
smallbin    < 1024B, mỗi bin một kích thước, FIFO
largebin    ≥ 1024B, mỗi bin một dải kích thước, có sắp xếp
top chunk   phần còn lại của arena; mở rộng bằng brk khi thiếu
```
Biết tên các bin có giá trị thực tế khi đọc thông điệp lỗi — ví dụ `free(): double free detected in tcache 2` nói ngay rằng khối nằm trong tcache bin số 2.

### 3.4 Fragmentation — đo thật

Đây là hiện tượng bị nói nhiều nhưng ít khi được chỉ ra bằng số.

✅ Thí nghiệm: cấp phát 200.000 khối 128 byte, giải phóng **xen kẽ** một nửa, rồi xin một khối lớn.
```text
bắt đầu                                    RSS=  1416 kB
sau 200k x malloc(128)                     RSS= 31484 kB
sau free 100k khối xen kẽ                  RSS= 31484 kB   ← KHÔNG giảm
malloc(4 MiB) sau đó:                      thành công (phải xin OS thêm)
sau malloc(4 MiB)                          RSS= 31488 kB   ← không tái dùng được 12,8 MB đã free
sau free TẤT CẢ                            RSS=  3496 kB
sau malloc_trim(0)                         RSS=  3368 kB
```

Bốn kết luận:
1. **`free` không trả bộ nhớ cho OS.** Nó trả cho *allocator*. RSS đứng nguyên 31.484 kB sau khi giải phóng 12,8 MB.
2. **Bộ nhớ đã free bị phân mảnh không dùng được cho khối lớn.** 12,8 MB trống nằm rải rác thành 100.000 lỗ 144 byte; `malloc(4 MiB)` buộc phải xin OS thêm.
3. **Chỉ khi các khối liền kề được hợp nhất** (free hết) glibc mới rút `top chunk` và giảm brk → RSS tụt còn 3.496 kB.
4. `malloc_trim(0)` ép trả thêm, nhưng chỉ lấy lại được 128 kB nữa.

> Đây là lý do một dịch vụ chạy lâu có thể "rò rỉ" theo quan sát của `top` mà valgrind báo **không leak**: bộ nhớ không mất, chỉ là bị phân mảnh và không trả về OS. Cách chữa thường không phải "tìm leak" mà là **đổi chiến lược cấp phát** (arena theo request, pool cho object cùng cỡ) hoặc đổi allocator.

### 3.5 Allocator thay thế

| Allocator | Điểm mạnh | Khi nào |
|---|---|---|
| **glibc malloc** (ptmalloc2) | mặc định, ổn | đa số |
| **jemalloc** | phân mảnh thấp, arena theo thread, thống kê tốt | dịch vụ chạy lâu, nhiều thread |
| **tcmalloc** | rất nhanh cho object nhỏ | ứng dụng cấp phát dày |
| **mimalloc** | nhanh, gọn, free-list sharded | thay thế hiện đại |
| **arena/pool tự viết** | tiên đoán được, O(1) | game loop, parser, firmware (C1.1 §7.4) |

```sh
LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2 ./myapp   # đổi không cần build lại
```

### 3.6 Điều chỉnh glibc

```c
mallopt(M_MMAP_THRESHOLD, 64 * 1024);   /* ép mmap sớm hơn -> trả OS nhiều hơn */
mallopt(M_TRIM_THRESHOLD, 128 * 1024);  /* ngưỡng rút top chunk */
mallopt(M_ARENA_MAX, 2);                /* giới hạn số arena (giảm RSS đa luồng) */
malloc_trim(0);                          /* ép trả bộ nhớ ngay */
```
```sh
MALLOC_ARENA_MAX=2 ./myapp              # cùng tác dụng, không sửa code
```
⚠️ Mặc định glibc tạo tới `8 × số lõi` arena cho chương trình đa luồng. Trên máy 64 lõi, đó là 512 arena × 64 MiB địa chỉ ảo — nguyên nhân phổ biến của "RSS cao bất thường" trong container.

## 4. Alignment

### 4.1 Vì sao nó tồn tại

CPU đọc bộ nhớ theo **đơn vị word** qua bus có độ rộng cố định. Một `uint32_t` ở địa chỉ `0x1003` nằm vắt qua hai word 8 byte → phần cứng phải làm hai lần truy cập rồi ghép lại. Các kiến trúc khác nhau chọn cách khác nhau:

| Kiến trúc | Truy cập lệch |
|---|---|
| x86-64 | cho phép, phần cứng tự xử lý |
| ARMv7-A trở lên (Linux) | cho phép cho load/store thường, **fault** cho một số lệnh |
| ARMv5, SPARC, MIPS cũ | **SIGBUS** |
| RISC-V | tuỳ cài đặt: cho phép, bẫy, hoặc mô phỏng bằng phần mềm (rất chậm) |
| Mọi kiến trúc: lệnh SIMD "aligned", lệnh nguyên tử | **fault** nếu lệch |

### 4.2 Chi phí thật trên x86-64 — đo chứ không đoán

🔬 Đọc 512K giá trị `uint64_t`, mỗi lần ở một offset cố định trong cache line 64 byte, lặp 10 vòng:

```text
off 0 (aligned)  13,3 ms | off 4 (lệch, trong line) 12,9 ms
off 60 (cắt line) 13,3 ms | off 63 (cắt line)       13,4 ms
```

**Kết luận trung thực: trên CPU x86-64 hiện đại, chênh lệch nằm trong nhiễu đo (~3%)** — kể cả khi *mọi* lần đọc đều cắt qua ranh giới cache line. Các con số "unaligned chậm 2 lần" thường trích từ CPU đời cũ hoặc từ trường hợp cắt qua **ranh giới trang**, không phải cache line.

> Vậy tại sao vẫn phải quan tâm? Ba lý do **không liên quan tới tốc độ trên x86**:
> 1. **Nó là UB theo chuẩn C** (C1.1 §11.4) — compiler được phép giả định con trỏ đúng alignment và sinh lệnh SIMD aligned.
> 2. **Nó crash trên kiến trúc khác** — code chạy trên máy dev x86 và chết trên ARM nhúng.
> 3. **Nguyên tử và SIMD bắt buộc** — `lock cmpxchg` trên địa chỉ lệch qua ranh giới cache line gây khoá bus (cực chậm) hoặc `#AC`; `movaps` fault.

### 4.3 UBSan bắt được

✅ Output thật:
```text
mis.c:7:8: runtime error: store to misaligned address 0x55f2247a40e1 for type
           'uint32_t', which requires 4 byte alignment
0x55f2247a40e1: note: pointer points here
 00 00 00  00 00 00 00 00 ...
              ^
mis.c:8:5: runtime error: load of misaligned address 0x55f2247a40e1 for type 'uint32_t'
```
Chương trình vẫn in ra kết quả **đúng** (`11223344`) — nó "chạy được" trên x86. Đó chính là điều nguy hiểm: **bạn chỉ phát hiện được bằng công cụ, không bằng test.**

Cách viết đúng (C1.1 §3.9), và nó **miễn phí** ở `-O2`:
```c
uint32_t v;
memcpy(&v, buf + 1, sizeof v);      /* luôn hợp lệ; GCC sinh đúng 1 lệnh mov */
```

### 4.4 Alignment trong thiết kế cấu trúc

Nhắc lại C1.1 §5 và C1.3 §2.8, đặt cạnh nhau:

| | C (`repr(C)`) | Rust (`repr(Rust)`) |
|---|---|---|
| `struct { u8; u32; u8 }` | 🔬 **12 byte** | 🔬 **8 byte** (tự sắp xếp lại) |
| Có sắp xếp lại trường? | ✘ | ✔ |
| Buộc giống C | mặc định | `#[repr(C)]` |

```c
_Alignas(64) static uint8_t dma_buf[2048];   /* căn cache line / yêu cầu DMA */
_Static_assert(_Alignof(struct hdr) == 4, "");
```

### 4.5 Cache line và false sharing

Alignment còn quyết định hiệu năng đa luồng:

```c
struct counters {           /* ❌ hai bộ đếm chung một cache line 64B */
    _Atomic long a;         /* thread 1 ghi */
    _Atomic long b;         /* thread 2 ghi -> làm invalid cache line của thread 1 */
};
struct counters_ok {        /* ✔ tách ra hai cache line */
    _Alignas(64) _Atomic long a;
    _Alignas(64) _Atomic long b;
};
```
**False sharing**: hai biến độc lập nằm cùng cache line khiến mỗi lần ghi phải đồng bộ cache giữa các lõi. Có thể làm chậm 5–10 lần mà không có dấu hiệu nào trong code.

## 5. Lifetime: ai sở hữu, ai giải phóng

### 5.1 Ba câu hỏi phải trả lời được cho mọi con trỏ

```
1. AI SỞ HỮU nó?           (ai có trách nhiệm giải phóng)
2. NÓ SỐNG ĐẾN BAO GIỜ?    (trước hay sau người đang giữ tham chiếu)
3. AI CÒN TRỎ VÀO NÓ?      (còn tham chiếu nào sau khi giải phóng không)
```
Mọi lỗi trong mục này là hệ quả của việc không trả lời được một trong ba câu.

### 5.2 Use-after-free — thường **không** crash

Đây là điểm khiến UAF nguy hiểm hơn segfault.

✅ Thí nghiệm: `malloc(32)`, ghi dữ liệu, `free`, rồi đọc và ghi lại.
```text
đọc sau free: Y                                     ← rác, không crash
q=0x55916fcf22a0 p=0x55916fcf22a0 (tcache trả lại CÙNG khối)
exit=0                                              ← chương trình "chạy bình thường"
```
Ba điều xảy ra:
1. Khối đã free **vẫn được ánh xạ**, nên đọc/ghi không sinh SIGSEGV.
2. glibc ghi **metadata tcache** (con trỏ `next` + key) đè lên 16 byte đầu của vùng dữ liệu — đó là ký tự rác bạn đọc được.
3. `malloc` tiếp theo trả lại **chính khối đó**. Nếu code cũ vẫn ghi qua `p`, nó đang phá dữ liệu của chủ mới.

> Đây là cơ chế của cả một lớp khai thác: giải phóng một object, ép chương trình cấp phát object khác vào đúng chỗ, rồi dùng con trỏ cũ để ghi vào object mới.

### 5.3 Thông điệp lỗi thật của glibc

✅ Bốn kịch bản, output nguyên văn:

| Kịch bản | Thông điệp | Tín hiệu |
|---|---|---|
| `free(p); free(p);` | `free(): double free detected in tcache 2` | SIGABRT (exit 134) |
| ghi 64 byte vào khối 32 byte rồi `free` + `malloc` | `malloc(): corrupted top size` | SIGABRT (exit 134) |
| `free(p + 8)` | *(không có thông điệp)* | SIGSEGV (exit 139) |
| đọc/ghi sau `free` | *(không có gì)* | exit 0 ⚠️ |

**Cách đọc các thông điệp glibc hay gặp:**

| Thông điệp | Nghĩa |
|---|---|
| `free(): double free detected in tcache 2` | khối đã nằm trong tcache bin 2 |
| `free(): invalid pointer` | con trỏ không trỏ tới đầu một chunk hợp lệ |
| `free(): invalid size` / `invalid next size` | header chunk bị ghi đè → **heap overflow ở đâu đó trước đó** |
| `malloc(): corrupted top size` | ghi tràn đè lên top chunk |
| `malloc(): memory corruption` | danh sách bin bị hỏng |
| `munmap_chunk(): invalid pointer` | `free` một con trỏ mmap sai |
| `*** stack smashing detected ***` | canary sai → **tràn buffer trên stack** |

⚠️ **Thông điệp chỉ ra nơi lỗi bị *phát hiện*, không phải nơi lỗi *xảy ra*.** `malloc(): corrupted top size` báo ở lời gọi `malloc` sau, trong khi hỏng hóc do một `memcpy` từ trước đó rất lâu. Đây là lý do bạn cần ASan.

### 5.4 Đọc báo cáo ASan

✅ Cùng chương trình UAF ở trên, biên dịch với `-fsanitize=address`:
```text
==310==ERROR: AddressSanitizer: heap-use-after-free on address 0x503000000040
WRITE of size 20 at 0x503000000040 thread T0
    #1 ... in strcpy
    #2 0x... in main /home/claude/c14/t_uaf.c:9          ← NƠI TRUY CẬP SAI

0x503000000040 is located 0 bytes inside of 32-byte region [0x503000000040,0x503000000060)
freed by thread T0 here:
    #1 0x... in main /home/claude/c14/t_uaf.c:7          ← NƠI ĐÃ FREE

previously allocated by thread T0 here:
    #1 0x... in main /home/claude/c14/t_uaf.c:5          ← NƠI CẤP PHÁT
```
**Ba stack trace là toàn bộ giá trị của ASan:** nó nói bạn *truy cập ở đâu*, *đã free ở đâu*, và *đã cấp phát ở đâu*. Không công cụ nào khác cho đủ ba.

Đọc thêm phần "Shadow bytes" khi cần biết truy cập rơi vào loại vùng nào:
```
fa = heap left redzone   fd = freed heap region   f1 = stack left redzone
f5 = stack after return  f8 = stack use after scope   00 = addressable
```

### 5.5 Kỷ luật ownership trong C

Nhắc lại và mở rộng C1.1 §7.2:

```c
/* 1. Tài liệu hoá quyền sở hữu NGAY TRONG TÊN và chữ ký */
Doc  *doc_create(void);           /* CHUYỂN quyền cho người gọi   */
void  doc_destroy(Doc *d);        /* NHẬN lại quyền                */
const char *doc_title(const Doc *d);  /* MƯỢN — không được free     */

/* 2. Gán NULL sau free nếu con trỏ còn sống tiếp */
free(p); p = NULL;

/* 3. Một điểm thoát, dọn ngược thứ tự cấp phát */
cleanup:
    free(d); free(buf); if (f) fclose(f);
    return rc;

/* 4. Sở hữu trong container: lưu CHỈ SỐ, không lưu con trỏ,
      nếu container có thể realloc */
uint32_t node_index;      /* thay vì Node *node */
```

**Bảng ánh xạ lỗi ↔ câu hỏi chưa trả lời:**

| Lỗi | Câu hỏi §5.1 bị bỏ qua |
|---|---|
| leak | (1) ai sở hữu — không ai |
| double free | (1) ai sở hữu — hai nơi cùng nghĩ mình sở hữu |
| use-after-free | (3) ai còn trỏ vào |
| dangling sau `realloc` | (2) + (3) |
| trả địa chỉ biến cục bộ | (2) sống đến bao giờ |
| free con trỏ không phải đầu khối | (1) sai đối tượng |

## 6. Ownership model ở ba ngôn ngữ

### 6.1 Ba lời giải cho cùng một bài toán

Bài toán: **khi nào một vùng nhớ được giải phóng, và ai quyết định?**

```
C:      LẬP TRÌNH VIÊN quyết định, tại thời điểm chạy, không ai kiểm tra.
Python: RUNTIME quyết định, tại thời điểm chạy, bằng refcount + GC.
Go:     RUNTIME quyết định, tại thời điểm chạy, bằng tracing GC đồng thời.
Rust:   COMPILER quyết định, tại thời điểm biên dịch, và chèn lệnh free.
```

### 6.2 C — thủ công

```c
char *buf = malloc(n);
if (!buf) return -1;
/* ... */
free(buf);
```
| | |
|---|---|
| Chi phí runtime | chỉ chi phí allocator |
| Độ trễ | tiên đoán được (trừ khi allocator phải xin OS) |
| Bộ nhớ dư | header chunk + làm tròn (🔬 `malloc(8)` tốn 32 byte) |
| Lỗi có thể xảy ra | leak, UAF, double free, wild free, overflow |
| Ai bắt lỗi | ASan, valgrind, review — **lúc chạy, trên đường đã chạy** |

### 6.3 Python và Go — GC

**Python (CPython):** refcount là chính, GC theo thế hệ chỉ để dọn chu trình.
```
refcount = 0  →  giải phóng NGAY, tiên đoán được
chu trình     →  chờ GC thế hệ
```
🔬 Đo ở C1.2 §9.1: mỗi object có header refcount; `int` 28 byte, `dict` rỗng 64 byte, instance có `__dict__` 344 byte. Và C1.4 §3.2 giải thích vì sao: mỗi object nhỏ còn phải chịu header chunk + làm tròn 16 byte của allocator bên dưới.

⚠️ Kết quả trái trực giác đã đo ở C1.3 §10.8: với một handler không tạo chu trình, **GC gần như không đóng góp vào tail latency** (chênh 2% giữa `gc.enable()` và `gc.disable()`). Tail đến từ biến thiên của allocator, không từ GC. Đừng đổ lỗi cho GC trước khi đo.

**Go:** tracing GC đồng thời, mục tiêu pause < 1 ms, có escape analysis để nhiều object ở lại stack.
```
+ Không có UAF/double free
+ Pause rất ngắn (concurrent mark & sweep)
− Cần headroom bộ nhớ (GOGC mặc định 100% -> heap gấp đôi live set)
− Throughput giảm vì write barrier
```

### 6.4 Rust — compile-time

```rust
{
    let buf = vec![0u8; n];   // cấp phát
}                              // compiler CHÈN lệnh drop -> free, tại đúng đây
```
Không có runtime, không có refcount (trừ khi bạn chọn `Rc`/`Arc`), không có GC. Chi phí bằng C, an toàn bằng GC. Cái giá nằm ở **thời gian của lập trình viên và compiler** (C1.3 §8.4).

### 6.5 Bảng so sánh

| | **C** | **Python** | **Go** | **Rust** |
|---|---|---|---|---|
| Ai quyết định giải phóng | người viết | runtime | runtime | compiler |
| Khi nào | lúc chạy | lúc chạy | lúc chạy | **lúc biên dịch** |
| Chi phí CPU thường trực | 0 | refcount mọi thao tác | write barrier + mark | **0** |
| Bộ nhớ dư | header chunk | header object + chunk | headroom GC (~2×) | header chunk |
| Độ trễ tiên đoán được | ✔ (allocator) | phần lớn ✔ | pause ngắn nhưng có | ✔ |
| UAF / double free | **có thể** | không | không | không (ngoài `unsafe`) |
| Leak | **có thể** | chu trình + cache | hiếm | **có thể** (`Rc` vòng, `mem::forget`) |
| Data race | **có thể** | GIL che một phần | **có thể** | không biên dịch được |
| Dùng được không có OS | ✔ | ✘ | ✘ (cần runtime) | ✔ (`no_std`) |
| 🔬 RSS một service nhỏ | ~1 MB | **20 MB** | ~5–10 MB | **3 MB** |
| Ai bắt lỗi | ASan/valgrind (runtime) | — | — | **compiler** |

> **Điểm cần nhớ:** không mô hình nào loại bỏ được việc **suy nghĩ về vòng đời**. Rust bắt bạn nói ra; GC cho phép bạn hoãn lại (và trả bằng bộ nhớ + độ trễ); C cho phép bạn bỏ qua (và trả bằng CVE). Ba câu hỏi ở §5.1 vẫn phải trả lời trong cả bốn ngôn ngữ.

## 7. Cấp phát tĩnh cho hệ nhúng

### 7.1 Vì sao production firmware tránh heap

Không phải vì heap "chậm". Sáu lý do kỹ thuật, theo thứ tự quan trọng:

| # | Lý do | Hệ quả nếu bỏ qua |
|---|---|---|
| 1 | **Không chứng minh được sẽ không hết bộ nhớ.** Dung lượng đỉnh phụ thuộc thứ tự cấp phát/giải phóng lúc chạy | thiết bị chết ở giờ thứ 5.000, không tái lập được |
| 2 | **Phân mảnh không giới hạn.** Hệ thống chạy liên tục hàng năm, không restart | §3.4 đã đo: 12,8 MB trống mà `malloc(4 MiB)` vẫn thất bại |
| 3 | **`malloc` không xác định về thời gian.** Có thể phải duyệt bin, hợp nhất, xin OS | vi phạm deadline trong hệ thời gian thực cứng |
| 4 | **Xử lý `NULL` bị bỏ sót.** Nhánh hết bộ nhớ hầu như không bao giờ được test | crash ở đúng lúc tệ nhất |
| 5 | **Không có OS để xin thêm.** Trên bare metal, hết là hết | — |
| 6 | **Chuẩn ngành cấm.** MISRA C:2012 Rule 21.3; JPL Rule 3; DO-178C; IEC 61508 | không chứng nhận được |

> Nguyên tắc gói gọn: **mọi thứ được biết tại thời điểm link**. Nếu firmware link thành công và cận trên stack đã được chứng minh, nó **không thể** hết bộ nhớ.

### 7.2 Ngân sách bộ nhớ

```c
/* Mọi giới hạn là hằng số biên dịch, đặt MỘT chỗ */
#define RX_CAP   64u
#define MAX_PAY  32u
#define N_SLOTS   8u

static ring_t  g_rx;                       /* .bss */
static frame_t g_frame;                    /* .bss */
static uint8_t g_slots[N_SLOTS][MAX_PAY];  /* .bss */
static char    g_logbuf[96];               /* .bss */

/* Chứng minh ngân sách TẠI THỜI ĐIỂM BIÊN DỊCH */
_Static_assert(sizeof(g_rx) + sizeof(g_slots) + sizeof(g_logbuf) <= 1024,
               "vuot ngan sach RAM cho module RX");
```

✅ Firmware mẫu ở Checkpoint §9.2 đo được:
```text
$ size -A fw.o
.text      1020
.data         0          ← 0: không có biến khởi tạo khác 0 -> không tốn flash để copy
.bss        456
.rodata      17
```
```
Ngân sách RAM = .data + .bss + stack
              = 0 + 456 + 328  =  784 byte

MCU  2 KiB RAM :  38,3% đã dùng, còn 1264 byte
MCU  8 KiB RAM :   9,6% đã dùng, còn 7408 byte
MCU 20 KiB RAM :   3,8% đã dùng, còn 19696 byte
```
Con số này **biết trước khi nạp firmware lên thiết bị**. Đó là toàn bộ mục đích.

⚠️ Phân biệt hai loại bộ nhớ trên MCU:
```
FLASH cần = .text + .rodata + .data   (bản gốc của .data nằm trong flash)
RAM   cần = .data + .bss + stack (+ heap nếu có)
```
`.bss` tốn RAM nhưng **không** tốn flash (§1.3). Đây là lý do mảng lớn nên để không khởi tạo, hoặc khởi tạo bằng code lúc chạy.

### 7.3 Linker script và section

```c
__attribute__((section(".dma_buffer"), aligned(32)))
static uint8_t g_dma[512];          /* đặt vào vùng RAM mà DMA truy cập được */

__attribute__((section(".noinit")))
static uint32_t g_boot_count;       /* KHÔNG bị xoá bởi startup -> sống qua reset mềm */
```
```ld
/* trích linker script */
MEMORY {
  FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 256K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 20K
}
_stack_top = ORIGIN(RAM) + LENGTH(RAM);

/* Chứng minh ngân sách ở tầng LINKER, không chỉ ở tầng C */
ASSERT(_end_bss - _start_data + STACK_SIZE <= LENGTH(RAM), "RAM overflow");
```
```sh
arm-none-eabi-size fw.elf                # tổng quan
arm-none-eabi-nm --size-sort -S fw.elf   # object nào to nhất
# đọc file .map để biết chính xác symbol nào ở đâu
```

### 7.4 Thay thế heap

| Nhu cầu | Thay bằng |
|---|---|
| Object cùng kích thước, số lượng có giới hạn | **pool tĩnh** + freelist (C1.1 §7.5) |
| Bộ nhớ tạm trong một chu kỳ xử lý | **arena tĩnh**, reset ở cuối chu kỳ (C1.1 §7.4) |
| Chuỗi / buffer độ dài thay đổi | buffer cố định + `(ptr, len)` (C1.1 §8.7) |
| Container động | `heapless::Vec<T, N>` (Rust, C1.3 §6.4) — dung lượng nằm trong **kiểu** |
| Cấp phát lúc khởi động rồi thôi | `malloc` **chỉ trong `init()`**, không bao giờ `free` |

Mẫu cuối cùng đáng chú ý: nhiều dự án cho phép cấp phát động **chỉ trong giai đoạn khởi tạo**, sau đó khoá lại. Nó giữ được sự linh hoạt khi cấu hình mà vẫn có dung lượng đỉnh xác định.

## 8. Memory-mapped I/O và `volatile`

### 8.1 MMIO là gì

Thiết bị ngoại vi (UART, GPIO, timer, DMA) được ánh xạ vào **không gian địa chỉ** như bộ nhớ thường. Ghi vào một địa chỉ = gửi lệnh cho phần cứng; đọc = lấy trạng thái.

```c
#define UART_BASE 0x40004000u
#define UART_SR  (*(volatile uint32_t *)(UART_BASE + 0x00))   /* status */
#define UART_DR  (*(volatile uint32_t *)(UART_BASE + 0x04))   /* data   */
#define TXRDY    (1u << 7)
```
Ba tính chất phá vỡ giả định của compiler:
1. **Đọc có tác dụng phụ** — đọc thanh ghi data thường xoá cờ ngắt.
2. **Giá trị đổi mà không ai ghi** — phần cứng tự cập nhật.
3. **Số lần và thứ tự truy cập là quan trọng** — không được gộp, không được bỏ.

### 8.2 `volatile` — bằng chứng assembly

Đây là chứng minh trực tiếp nhất mà tôi có thể đưa ra. ✅ Cùng một hàm, khác duy nhất ở `volatile`, `gcc -O2 -S -masm=intel`:

**Vòng chờ cờ trạng thái:**
```c
void send(uint32_t c) {
    while ((*UART_SR & 0x80) == 0) { }    /* chờ TXRDY */
    *UART_DR = c;
}
```
```asm
send_no_volatile:                       ; ❌ KHÔNG có volatile
        endbr64
        test    BYTE PTR ds:1073758208, -128
        jne     .L2
.L3:
        jmp     .L3                     ; ← VÒNG LẶP VÔ HẠN!
.L2:
        mov     DWORD PTR ds:1073758212, edi
        ret

send_volatile:                          ; ✔ CÓ volatile
        endbr64
.L6:
        mov     eax, DWORD PTR ds:1073758208
        test    al, -128
        je      .L6                     ; ← đọc lại mỗi vòng
        mov     DWORD PTR ds:1073758212, edi
        ret
```
Không có `volatile`, compiler đọc thanh ghi **một lần**; nếu cờ chưa sẵn sàng thì `jmp .L3` — treo máy vĩnh viễn. Lập luận của nó hoàn toàn đúng theo chuẩn C: không ai ghi vào biến đó, nên giá trị không thể đổi.

**Ba lần đọc liên tiếp:**
```c
uint32_t read3(void) { return *UART_DR + *UART_DR + *UART_DR; }
```
```asm
read3_no_volatile:                      ; ❌
        mov     eax, DWORD PTR ds:1073758212
        lea     eax, [rax+rax*2]        ; ← đọc 1 lần rồi NHÂN 3
        ret

read3_volatile:                         ; ✔
        mov     eax, DWORD PTR ds:1073758212
        mov     ecx, DWORD PTR ds:1073758212
        mov     edx, DWORD PTR ds:1073758212   ; ← đúng 3 lần đọc
        add     eax, ecx
        add     eax, edx
        ret
```
Với một FIFO nhận, ba lần đọc lấy ba byte khác nhau. Bản không `volatile` lấy một byte rồi nhân ba.

### 8.3 `volatile` KHÔNG làm gì — nhắc lại C1.1 §10.2

| `volatile` không… | Phải dùng |
|---|---|
| tạo tính nguyên tử (`x++` vẫn là read-modify-write) | `_Atomic`, hoặc tắt ngắt |
| tạo hàng rào bộ nhớ ở mức **CPU** | `__DMB()`/`__DSB()` (ARM), `atomic_thread_fence` |
| ngăn CPU sắp xếp lại truy cập | hàng rào |
| bảo đảm hiển thị giữa các lõi | atomic với memory order |
| thay thế mutex | mutex, hoặc vùng găng |

Compiler **không** sắp xếp lại hai truy cập `volatile` với nhau, nhưng **được phép** sắp xếp lại truy cập thường quanh chúng, và **CPU** vẫn có thể sắp xếp lại ở mức phần cứng. Với MMIO trên ARM, sau khi cấu hình một thanh ghi điều khiển thường cần `__DSB()` trước khi bật thiết bị.

### 8.4 Mẫu truy cập thanh ghi đúng

```c
/* 1. Kiểu mô tả thanh ghi: repr rõ ràng + static assert */
typedef struct {
    volatile uint32_t SR;      /* 0x00 status  — chỉ đọc         */
    volatile uint32_t DR;      /* 0x04 data                       */
    volatile uint32_t CR1;     /* 0x08 control                    */
    uint32_t          RESERVED;/* 0x0C — giữ chỗ tường minh       */
    volatile uint32_t BRR;     /* 0x10 baud rate                  */
} uart_t;
_Static_assert(sizeof(uart_t) == 0x14, "layout thanh ghi sai");
_Static_assert(offsetof(uart_t, BRR) == 0x10, "");

#define UART1 ((uart_t *)0x40004000u)

/* 2. Đọc-sửa-ghi phải TƯỜNG MINH, không viết |= trực tiếp lên thanh ghi
      nếu thanh ghi có bit write-1-to-clear */
uint32_t cr = UART1->CR1;
cr &= ~MASK_MODE;
cr |=  (2u << SHIFT_MODE);
UART1->CR1 = cr;

/* 3. Thanh ghi chỉ đọc: const volatile */
static const volatile uint32_t *const STATUS = (const volatile uint32_t *)0x40000000u;
```
⚠️ Không dùng bit field cho thanh ghi phần cứng (C1.1 §5.7): thứ tự bit là **implementation-defined**. Dùng mask + shift tường minh.

## 9. Checkpoint

### 9.1 Phần A — Đọc core dump và giải thích segfault

#### A.1 Chuẩn bị môi trường

```sh
ulimit -c unlimited                    # cho phép sinh core (mặc định nhiều hệ là 0)
cat /proc/sys/kernel/core_pattern      # "core" -> ghi ./core
                                       # "|/usr/share/apport/..." -> dùng coredumpctl
gcc -O0 -g -fno-omit-frame-pointer -o prog prog.c     # -g là BẮT BUỘC
```
Trên hệ dùng systemd:
```sh
coredumpctl list
coredumpctl gdb <PID>
coredumpctl dump <PID> > core
```

#### A.2 Chương trình có lỗi

```c
struct record { int id; char *name; double score; };

static struct record *find(struct record *db, int n, int id) {
    for (int i = 0; i < n; i++) if (db[i].id == id) return &db[i];
    return NULL;                              /* không tìm thấy */
}
static void print_record(struct record *r) {
    printf("id=%d name=%s score=%.1f\n", r->id, r->name, r->score);
}
static void lookup_and_print(struct record *db, int n, int id) {
    struct record *r = find(db, n, id);
    print_record(r);                          /* QUÊN kiểm tra NULL */
}
int main(void) {
    struct record db[3] = { {1,"alice",9.5}, {2,"bob",8.0}, {3,"carol",7.25} };
    lookup_and_print(db, 3, 2);
    lookup_and_print(db, 3, 99);              /* id không tồn tại */
}
```
✅
```text
$ ./crash1
Segmentation fault (core dumped)
$ echo $?
139                       # 128 + 11 (SIGSEGV)
```

#### A.3 Quy trình phân tích sáu bước

**Bước 1 — Backtrace: chết ở đâu, ai gọi tới đó**
```sh
gdb -q -batch -ex bt ./crash1 core
```
✅
```text
Program terminated with signal SIGSEGV, Segmentation fault.
#0  0x000055eab551e1ee in print_record (r=0x0) at crash1.c:12
#1  0x000055eab551e258 in lookup_and_print (db=0x7ffc02a48940, n=3, id=99) at crash1.c:17
#2  0x000055eab551e2ff in main () at crash1.c:23
```
Đã thấy ngay: `r = 0x0`, và frame 1 cho biết `id = 99`.

**Bước 2 — Địa chỉ gây fault và loại fault**
```sh
gdb -q -batch -ex 'p $_siginfo._sifields._sigfault.si_addr' -ex 'p (int)$_siginfo.si_code' ./crash1 core
```
✅
```text
$1 = (void *) 0x10
$2 = 1
```
| `si_code` | Nghĩa |
|---|---|
| 1 = `SEGV_MAPERR` | địa chỉ **không được ánh xạ** |
| 2 = `SEGV_ACCERR` | có ánh xạ nhưng **sai quyền** (ví dụ ghi vào `.rodata`) |

Địa chỉ `0x10` nằm trong trang 0 → trang này không bao giờ được ánh xạ (§1.1) → đây là **null pointer dereference với offset 0x10**.

**Bước 3 — Lệnh máy gây lỗi**
```sh
gdb -q -batch -ex 'x/3i $pc' -ex 'info registers rip rsp rdi rax' ./crash1 core
```
✅
```text
=> 0x55eab551e1ee <print_record+20>:   mov    0x10(%rax),%rcx
rip  0x55eab551e1ee   rsp  0x7ffc02a488f0   rdi  0x0   rax  0x0
```
`rax = 0`, lệnh đọc `[rax + 0x10]` → đọc địa chỉ `0x10`. Khớp chính xác `si_addr`.

**Bước 4 — Offset `0x10` là trường nào?**
```sh
gdb -q -batch -ex 'ptype struct record' -ex 'p sizeof(struct record)' \
    -ex 'p &((struct record*)0)->score' ./crash1
```
✅
```text
type = struct record { int id; char *name; double score; }
$1 = 24
$4 = (double *) 0x10
```
Offset 16 = `score`. Áp dụng thuật toán padding C1.1 §5.2: `id`@0 (4 byte), padding 4 byte, `name`@8, `score`@16, tổng 24. **Bốn nguồn độc lập cùng chỉ về một chỗ.**

**Bước 5 — Xác nhận nguyên nhân gốc**
```sh
gdb -q -batch -ex 'frame 1' -ex 'info locals' -ex 'p id' ./crash1 core
```
✅
```text
#1  lookup_and_print (db=..., n=3, id=99) at crash1.c:17
r = 0x0
$2 = 99
```

**Bước 6 — Kết luận (đây là thứ được chấm)**

> **Nguyên nhân:** `find()` trả `NULL` khi `id = 99` không có trong `db`. `lookup_and_print()` truyền thẳng giá trị đó cho `print_record()` mà không kiểm tra. `print_record()` giải tham chiếu `r->score`, tức đọc địa chỉ `0 + 0x10 = 0x10`, nằm trong trang 0 chưa bao giờ được ánh xạ → `SIGSEGV` / `SEGV_MAPERR`.
>
> **Bằng chứng:** `r = 0x0` ở frame 0; `si_addr = 0x10` khớp với `offsetof(struct record, score) = 16`; lệnh `mov 0x10(%rax),%rcx` với `rax = 0`; `id = 99` ở frame 1 giải thích vì sao `find` trả `NULL`.
>
> **Sửa:** kiểm tra `NULL` trong `lookup_and_print`, hoặc đổi chữ ký `find` thành trả mã lỗi để compiler không cho bỏ qua.

#### A.4 Một cái bẫy: stdout biến mất

✅ Lời gọi `lookup_and_print(db, 3, 2)` **thành công** và đã `printf`, nhưng:
```text
$ ./crash1 2>/dev/null | cat
(không có dòng nào)

$ stdbuf -o0 ./crash1 2>/dev/null
id=2 name=bob score=8.0
```
`stdout` khi không phải terminal thì được đệm theo khối. Nội dung đệm **mất khi SIGSEGV** vì `exit` handler không chạy.

> **Bài học vận hành:** nếu log của bạn "dừng ở giữa chừng" trước một crash, đừng kết luận rằng chương trình chết ở đó. Dùng `setvbuf(stdout, NULL, _IOLBF, 0)`, ghi log ra `stderr` (không đệm), hoặc `fflush` ở các mốc quan trọng.

#### A.5 Bảng tra: triệu chứng core dump → nguyên nhân

| Quan sát | Nguyên nhân thường gặp |
|---|---|
| `si_addr` nhỏ (`0` … `0xfff`) | NULL deref; offset = trường nào trong struct |
| `si_addr` ≈ `0xffffffffffffffff` hoặc giá trị lạ lặp lại (`0xA5A5…`, `0xDEADBEEF`) | con trỏ chưa khởi tạo, hoặc đọc vùng đã bị tô mẫu |
| `si_addr` cách `rsp` đúng 8 byte, backtrace hàng nghìn frame | **stack overflow** (§2.3) |
| `si_code = 2` (`SEGV_ACCERR`) | ghi vào `.rodata` (string literal), hoặc vào trang chỉ đọc |
| Backtrace toàn `??` | stack bị phá hỏng (buffer overflow đè địa chỉ trả về) |
| `*** stack smashing detected ***` | canary sai → tràn buffer trên stack |
| SIGABRT + `free(): …` / `malloc(): …` | hỏng heap; chạy lại với ASan |
| Chết trong `malloc`/`free` nhưng code bạn không sai ở đó | heap overflow **từ trước**; chỉ ASan tìm ra |
| `si_addr` trỏ vào vùng đã `munmap` | use-after-free trên khối lớn (mmap-ed) |

#### A.6 Tự chấm phần A

| Tiêu chí | Đạt khi |
|---|---|
| Có core dump và mở được | `gdb prog core` cho backtrace có tên hàm và số dòng |
| Xác định được **tín hiệu và loại** | nêu được `si_addr` và `si_code` |
| Xác định được **lệnh** gây lỗi | `x/i $pc` và giải thích thanh ghi nào sai |
| Nối được địa chỉ với **cấu trúc dữ liệu** | offset ↔ trường; hoặc `si_addr` ↔ vùng trong `maps` |
| Truy ra **nguyên nhân gốc**, không dừng ở nơi crash | chỉ ra hàm nào tạo ra giá trị sai |
| Đề xuất sửa **ở đúng tầng** | sửa hợp đồng API, không chỉ thêm một `if` |

### 9.2 Phần B — Chứng minh firmware không tràn stack

#### B.1 Bài toán

Cho một firmware chỉ dùng cấp phát tĩnh, gồm: ISR nhận byte → ring buffer → state machine phân tích frame → giao cho tầng ứng dụng → ghi log. Cần **chứng minh** nó không tràn stack với dung lượng cho trước.

Chứng minh phải dựa trên **cận trên tính được**, không dựa trên "chạy thử thấy ổn".

#### B.2 Chiến lược: kẹp từ hai phía

```
        phân tích tĩnh (.su + đồ thị gọi)   →  CẬN TRÊN
                                                  ↕
                                            sự thật
                                                  ↕
        stack painting khi chạy             →  CẬN DƯỚI (đường đã chạy)
```
Cận trên dùng để **chứng minh**; cận dưới dùng để **kiểm tra rằng cận trên không vô lý** (nếu đo được 5 KB mà cận trên nói 300 byte thì phân tích sai).

#### B.3 Bước 1 — Lấy kích thước frame từng hàm

```sh

```
✅

⚠️ Ba điều phải kiểm ngay:
1. Không có dòng nào ghi **`dynamic`** → không có VLA/`alloca` → cận trên tồn tại.
2. Tên có hậu tố `.constprop` / `.isra` là hàm đã bị GCC biến đổi; phải chuẩn hoá tên khi ghép với đồ thị gọi.
3. `.su` phản ánh mã **sau khi inline**, nên phải sinh từ đúng cờ biên dịch dùng để ship.

* Lời gọi **chưa resolve** in ra dạng `call <ten_ham+offset>` trỏ vào chính lệnh kế tiếp; đích thật nằm ở dòng **relocation ngay sau**. Nếu nhận cả hai, bạn tạo ra cạnh tự-gọi giả và bị báo "đệ quy".
* Relocation cũng xuất hiện cho **dữ liệu** (`.bss`, `.rodata`); chỉ nhận relocation đứng ngay sau một lệnh `call`.

#### B.5 Bước 3 — Công cụ `stackscan.py`

```python
#!/usr/bin/env python3
"""stackscan.py -- tính worst-case stack usage từ .su + đồ thị gọi của objdump."""
import argparse, re, subprocess, sys
from collections import defaultdict

CALL_RE     = re.compile(r"call\s+[0-9a-f]+\s+<([^>+]+)>")   # có `+` => chỗ trống
RELOC_RE    = re.compile(r"R_X86_64_(?:PLT32|PC32)\s+([^\s-]+)")
INDIRECT_RE = re.compile(r"call\s+\*")
SYM_RE      = re.compile(r"^[0-9a-f]+\s+<([^>]+)>:")

def base(name):
    """Bỏ hậu tố .constprop/.isra/.part GCC thêm vào; lặp vì có thể chồng nhau."""
    prev = None
    while prev != name:
        prev = name
        name = re.sub(r"\.(constprop|isra|part|cold|lto_priv)(\.\d+)*$", "", name)
    return name

def parse_su(paths):
    frames, dynamic = {}, set()
    for p in paths:
        for line in open(p, encoding="utf-8"):
            parts = line.rstrip("\n").split("\t")
            if len(parts) < 3: continue
            fn = base(parts[0].split(":")[-1])
            frames[fn] = max(frames.get(fn, 0), int(parts[1]))
            if "dynamic" in parts[2]: dynamic.add(fn)
    return frames, dynamic

def parse_calls(objs):
    graph, indirect = defaultdict(set), set()
    for o in objs:
        out = subprocess.run(["objdump", "-dr", o], capture_output=True, text=True).stdout
        cur, prev_was_call = None, False
        for line in out.splitlines():
            m = SYM_RE.match(line)
            if m: cur = base(m.group(1)); graph.setdefault(cur, set()); continue
            if cur is None: continue
            if INDIRECT_RE.search(line): indirect.add(cur)
            m = CALL_RE.search(line)
            if m:
                graph[cur].add(base(m.group(1))); prev_was_call = True; continue
            m = RELOC_RE.search(line)                 # chỉ nhận ngay sau một `call`
            if m and prev_was_call:
                n = base(m.group(1))
                if not n.startswith("."): graph[cur].add(n)
            prev_was_call = "call" in line
    return graph, indirect

def worst(fn, frames, graph, memo, stack, cycles, unknown):
    if fn in stack:  cycles.add(fn); return 0, [fn + " <ĐỆ-QUY>"]
    if fn in memo:   return memo[fn]
    own = frames.get(fn)
    if own is None:  unknown.add(fn); own = 0
    best, path = 0, []
    stack.add(fn)
    for callee in sorted(graph.get(fn, ())):
        d, p = worst(callee, frames, graph, memo, stack, cycles, unknown)
        if d > best: best, path = d, p
    stack.discard(fn)
    memo[fn] = (own + best, [f"{fn}({own})"] + path)
    return memo[fn]
```
(Phần `main()` đọc tham số, cộng thêm ISR × số tầng lồng, so với `--limit` và in cảnh báo.)

**Điểm then chốt của thiết kế:** công cụ **không im lặng khi không chắc chắn**. Nó in ra bốn loại cảnh báo, và mỗi loại làm vô hiệu tính đúng đắn của chứng minh:

| Cảnh báo | Vì sao nó phá chứng minh |
|---|---|
| **ĐỆ QUY** | không có cận trên hữu hạn theo đồ thị |
| **FRAME ĐỘNG** (VLA/`alloca`) | `.su` ghi `dynamic` — kích thước phụ thuộc dữ liệu |
| **GỌI GIÁN TIẾP** (`call *rax`) | đồ thị gọi không đầy đủ |
| **KHÔNG CÓ `.su`** | hàm ngoài (libc, asm) — phải tra thủ công |

#### B.7 Bước 5 — Kiểm chứng bằng stack painting

Chạy firmware trên một stack đã tô mẫu `0xA5`, quét lại sau khi chạy. Quan trọng: **tô từ bên trong**, từ đáy vùng lên tới ngay dưới SP hiện tại, đúng cách runtime firmware làm lúc khởi động.

```c
static void *painted_body(void *arg) {
    uint8_t marker;
    uint8_t *sp = &marker;
    size_t paintable = (size_t)(sp - g_stack) - 64;   /* chừa 64 byte an toàn */
    memset(g_stack, 0xA5, paintable);                 /* SƠN phần chưa dùng */

    body(NULL);                                       /* chạy firmware */

    size_t untouched = 0;
    while (untouched < paintable && g_stack[untouched] == 0xA5) untouched++;
    g_used = paintable - untouched;                   /* HIGH-WATER MARK */
    return NULL;
}
```
Tải thử phải **quét mọi nhánh** để cận dưới có ý nghĩa: mọi độ dài payload từ 0 đến `MAX_PAY`, frame `LEN` không hợp lệ, và trường hợp ring buffer đầy.

✅ Kết quả thật:
```text

stack cấp phát                     :  65536 byte
watermark thread rỗng (pthread/TLS):   6312 byte   <- không tồn tại trên MCU
=> firmware dùng THỰC TẾ (đo được) :    223 byte
```

⚠️ Phép đo nền (`thread rỗng`) là bắt buộc: `pthread` tự tiêu 6.312 byte cho TLS và khởi động thread, hoàn toàn không liên quan tới firmware. Không trừ nền đi thì con số vô nghĩa. Trên MCU thật, phần này không tồn tại.

```

```

> **Phát biểu chứng minh:** với binary được build bằng đúng cờ đã phân tích, không có đệ quy, không có frame động, không có lời gọi gián tiếp, và mọi hàm ngoài đã được tính, stack tối đa mà firmware này dùng là **328 byte** kể cả một tầng ngắt. Với 2 KiB stack được cấp, nó **không thể** tràn.
>
> Chứng minh này mất hiệu lực nếu: đổi cờ biên dịch, đổi phiên bản compiler, thêm hàm gọi qua con trỏ, cho phép ngắt lồng nhiều tầng, hoặc thêm VLA. Vì vậy `stackscan.py` phải chạy **trong CI**, trên đúng binary sẽ ship, và fail build khi vượt ngưỡng.

#### B.9 Những điều làm chứng minh sai — kiểm tra hết trước khi tin

| Rủi ro | Cách xử lý |
|---|---|
| **Ngắt lồng nhau** | tính `max(ISR) × số tầng cho phép`; tốt hơn: cấm lồng, hoặc dùng stack riêng cho ISR |
| **Chi phí phần cứng khi vào ngắt** | Cortex-M tự đẩy 8 thanh ghi (32 byte), hoặc 26 từ (104 byte) nếu có FPU → cộng vào mỗi tầng ISR (`--isr-overhead`) |
| **Con trỏ hàm** | liệt kê tường minh tập đích có thể, lấy `max`; hoặc cấm trong code quan trọng |
| **Đệ quy** | cấm (MISRA Rule 17.2), hoặc chứng minh cận độ sâu bằng cách khác |
| **VLA / `alloca`** | cấm |
| **Hàm libc** | dùng bản đã đo, hoặc tự cài |
| **LTO** | phân tích **sau** LTO, trên binary cuối |
| **Compiler đổi phiên bản** | chạy lại phân tích; pin phiên bản toolchain |
| **Frame do trình gỡ lỗi / RTOS** | cộng chi phí context switch của RTOS |

#### B.10 Tự chấm phần B

| Tiêu chí | Đạt khi |
|---|---|
| Có **cận trên** tính được | không chỉ là số đo; có đường gọi sâu nhất kèm số từng frame |
| Phân tích trên **đúng binary** | cùng cờ, cùng compiler với bản ship |
| **Liệt kê được giả định** | đệ quy, con trỏ hàm, VLA, hàm ngoài, ngắt lồng |
| Công cụ **báo động khi không chắc** | không im lặng trả một con số |
| Có **kiểm chứng thực nghiệm** | painting, và cận dưới ≤ cận trên |
| Trừ **chi phí nền** khi đo | không lẫn chi phí của môi trường test |
| Có **biên an toàn** | ≥ 20–30%, nêu rõ lý do chọn |
| Chạy trong **CI** | build fail khi vượt ngưỡng |
| Ngân sách **toàn bộ RAM** | `.data + .bss + stack + heap` so với dung lượng thật |

### 9.3 Mở rộng

1. **Bốn kịch bản crash khác:** buffer overflow đè địa chỉ trả về (backtrace toàn `??`), ghi vào string literal (`SEGV_ACCERR`), heap overflow phát hiện muộn ở `malloc`, use-after-free trên vùng mmap-ed. Phân tích từng cái bằng đúng quy trình §9.1.
2. **Đọc core của tiến trình đa luồng:** `thread apply all bt`, tìm thread gây lỗi.
3. **Core của binary PIE:** tự tính offset `si_addr − base` và tra bằng `addr2line`.
4. **Thêm phát hiện đệ quy có cận:** cho phép khai báo `// @max-depth 4` trong nguồn và để `stackscan.py` đọc.
5. **Port sang ARM:** đổi regex sang `bl`/`blx`, thêm `--isr-overhead 32` (hoặc 104 với FPU).
6. **So sánh với công cụ thương mại:** GCC `-Wstack-usage=N`, `puncover`, hoặc bộ phân tích của IAR/Keil — đối chiếu con số.

## Phụ lục B — Triệu chứng → nguyên nhân

| Triệu chứng quan sát được | Nguyên nhân thường gặp | Kiểm chứng bằng |
|---|---|---|
| RSS tăng đều, valgrind báo **không leak** | phân mảnh heap; allocator không trả về OS | §3.4; `malloc_stats()`; thử jemalloc |
| RSS cao bất thường trong container đa luồng | nhiều arena của glibc | `MALLOC_ARENA_MAX=2` |
| VSZ khổng lồ nhưng máy vẫn chạy tốt | overcommit; địa chỉ ảo đặt chỗ, chưa dùng | so `VmSize` với `VmRSS` |
| SIGSEGV với `si_addr` nhỏ | NULL deref; offset = trường trong struct | §9.1 bước 2–4 |
| SIGSEGV, backtrace hàng nghìn frame | stack overflow | §2.3 |
| SIGSEGV, backtrace toàn `??` | địa chỉ trả về bị đè | ASan; `-fstack-protector-strong` |
| `*** stack smashing detected ***` | tràn buffer trên stack | ASan |
| SIGABRT + `free(): invalid size` | heap overflow **trước đó** | ASan |
| `malloc(): corrupted top size` | ghi tràn đè top chunk | ASan |
| Chương trình "chạy đúng" nhưng ASan báo UAF | khối đã free vẫn được ánh xạ | §5.2 |
| Đúng trên x86, crash trên ARM | truy cập lệch alignment | UBSan `-fsanitize=alignment` |
| Kết quả thay đổi theo mức tối ưu | UB (aliasing, tràn có dấu, chưa khởi tạo) | UBSan, MSan, `-fno-strict-aliasing` để khoanh vùng |
| Vòng chờ cờ phần cứng treo vĩnh viễn | thiếu `volatile` | §8.2 — đọc asm sinh ra |
| Đa luồng chậm bất thường, không thấy khoá | false sharing | `_Alignas(64)`; `perf stat` cache-misses |
| Log dừng giữa chừng trước crash | đệm stdout bị mất | §9.1 A.4 |
| Firmware chết sau vài ngày | phân mảnh heap, hoặc tràn stack ở nhánh hiếm | §7.1; §9.2 |

## Phụ lục C — Checklist

### C.1 Bố cục và ngân sách
- [ ] Biết `.text` / `.data` / `.bss` / stack / heap của binary (`size -A`).
- [ ] Mảng lớn nằm trong `.bss`, không khởi tạo thừa vào `.data`.
- [ ] Với firmware: có `_Static_assert` hoặc `ASSERT` trong linker script cho ngân sách RAM.
- [ ] Đo bằng RSS/PSS, không bằng VSZ.

### C.2 Stack
- [ ] Không có VLA, không có `alloca` (`grep -c dynamic *.su` = 0).
- [ ] Không có đệ quy trong code quan trọng; nếu có thì chứng minh được cận độ sâu.
- [ ] `-Wstack-usage=N` bật, N phù hợp với nền tảng.
- [ ] Buffer trên stack dùng hằng số đặt tên, không phải số ma thuật.
- [ ] Đã tính cận trên bao gồm ISR và số tầng lồng.
- [ ] Phân tích chạy trên đúng binary sẽ ship (cùng cờ, sau LTO).
- [ ] Có biên an toàn ≥ 20–30%.

### C.3 Heap
- [ ] Mọi `malloc` có kiểm tra `NULL`.
- [ ] Tính kích thước có kiểm tra tràn (`SIZE_MAX / sizeof`, hoặc `calloc`).
- [ ] `realloc` gán vào biến tạm trước khi ghi đè con trỏ cũ.
- [ ] Con trỏ gán `NULL` sau `free` nếu còn sống tiếp.
- [ ] Không lưu con trỏ vào container có thể `realloc` — lưu chỉ số.
- [ ] Đã cân nhắc arena/pool cho object cùng vòng đời hoặc cùng kích thước.
- [ ] Dịch vụ chạy lâu: đã đo phân mảnh, đã thử allocator khác.

### C.4 Alignment
- [ ] Không ép kiểu con trỏ làm tăng yêu cầu alignment (`-Wcast-align`).
- [ ] Đọc/ghi số từ mảng byte dùng `memcpy`, không ép kiểu.
- [ ] Struct layout nhị phân có `_Static_assert` cho `sizeof` và `offsetof`.
- [ ] Buffer DMA / SIMD có `_Alignas` đúng yêu cầu.
- [ ] Biến atomic dùng chung bị tranh chấp được tách cache line.

### C.5 Vòng đời
- [ ] Mỗi API nêu rõ ai sở hữu giá trị trả về (`*_create`/`*_destroy` vs `*_get`).
- [ ] Một điểm thoát, dọn ngược thứ tự cấp phát.
- [ ] Không trả địa chỉ biến cục bộ hoặc compound literal block-scope.
- [ ] ASan + UBSan sạch trên toàn bộ test suite.
- [ ] Đường lỗi được test, không chỉ đường thành công.

### C.6 MMIO
- [ ] Mọi thanh ghi phần cứng khai báo `volatile`.
- [ ] Thanh ghi chỉ đọc khai báo `const volatile`.
- [ ] Không dùng bit field cho thanh ghi.
- [ ] Struct thanh ghi có trường `RESERVED` tường minh và `_Static_assert` offset.
- [ ] Có hàng rào bộ nhớ (`DSB`/`DMB`) nơi thứ tự ở mức CPU quan trọng.
- [ ] `volatile` **không** được dùng làm cơ chế đồng bộ đa luồng.

## Tổng kết: mười điều phải mang theo

1. **Bố cục tiến trình kiểm chứng được**, không phải sơ đồ trong sách. `/proc/PID/maps` là nguồn sự thật, và mỗi dòng giải thích được.
2. **`.bss` tốn RAM, không tốn file.** 🔬 1 MiB `.bss` trong một binary 20 KB. Trên MCU: `.bss` tốn RAM, `.data` tốn cả RAM lẫn flash.
3. **VSZ không phải mức dùng bộ nhớ.** Dùng RSS, và PSS khi so nhiều tiến trình.
4. **Stack overflow đo được và tính được.** 🔬 8 MiB / frame 1088 byte = 7710; thực tế 7705. Mô hình đúng thì dự đoán được con số.
5. **`free` trả bộ nhớ cho allocator, không cho OS.** 🔬 Giải phóng 12,8 MB mà RSS không đổi, và `malloc(4 MiB)` vẫn phải xin thêm. "Rò rỉ" theo `top` thường là phân mảnh.
6. **Object nhỏ rất đắt.** 🔬 `malloc(8)` chiếm 32 byte. Đây là cầu nối giải thích 20 MB runtime của Python và giá trị của arena/pool.
7. **Unaligned trên x86 gần như miễn phí** (🔬 chênh 3%), nhưng vẫn là UB, vẫn crash trên ARM, và vẫn hỏng với atomic/SIMD. Dùng `memcpy` — nó cũng miễn phí.
8. **Use-after-free thường không crash.** Khối vẫn được ánh xạ, `malloc` sau trả lại đúng nó. Chỉ ASan cho bạn ba stack trace cần thiết.
9. **`volatile` là bắt buộc cho MMIO, và bằng chứng nằm trong assembly.** 🔬 Thiếu nó, vòng chờ cờ trở thành `jmp .L3` — treo vĩnh viễn.
10. **"Chạy thử thấy ổn" không phải chứng minh.** Cận trên tĩnh 328 byte + đo thực tế 223 byte + danh sách giả định được kiểm tra = chứng minh. Thiếu một trong ba thì chưa.
