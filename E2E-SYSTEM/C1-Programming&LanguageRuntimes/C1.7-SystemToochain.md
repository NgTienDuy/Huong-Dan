# C1.7 · Build system & toolchain

**Câu hỏi trung tâm của file:** *Từ file nguồn đến binary chạy trên thiết bị đích: chính xác cái gì xảy ra ở mỗi bước, và tôi kiểm soát nó bằng gì?*

---

## 1. Chuỗi dịch

### 1.1 Bốn pha
- Tiền xử lý: kết quả là gì, cách xem (`-E`), vì sao lỗi macro khó đọc
- Biên dịch: nguồn → assembly (`-S`); nơi hầu hết tối ưu hóa xảy ra
- Hợp dịch: assembly → object (`-c`); cái gì đã cố định ở bước này
- Liên kết: nhiều object + thư viện → thực thi; cái gì chỉ linker biết
- Đơn vị dịch như đơn vị của ba pha đầu; vì sao ranh giới này quyết định nhiều thứ

### 1.2 Định dạng object và thực thi
- ELF: header, section, segment, sự khác nhau giữa section và segment
- Section chính: `.text`, `.rodata`, `.data`, `.bss`, `.symtab`, `.strtab`, `.debug_*`, `.init_array`
- Bảng ký hiệu: định nghĩa, tham chiếu chưa giải, cục bộ/toàn cục/yếu, `UND`
- Định vị lại (relocation): là gì, ai thực hiện, lúc liên kết vs lúc nạp
- Công cụ khảo sát: `nm`, `objdump`, `readelf`, `size`, `strings`, `addr2line`
- Định dạng khác ở mức biết tồn tại: PE/COFF, Mach-O, hex/bin cho nhúng

**Tự kiểm mục 1:** với một object file, liệt kê ký hiệu chưa giải và nói cái nào sẽ đến từ đâu.

## 2. Linker

### 2.1 Giải ký hiệu
- Thuật toán duyệt: object trước, thư viện sau; vì sao thứ tự trên dòng lệnh quan trọng
- Thư viện tĩnh được kéo theo từng thành viên; `--whole-archive`
- Ký hiệu trùng, ký hiệu yếu (weak), ký hiệu chung (common); `--allow-multiple-definition` và vì sao nó nguy hiểm
- Tầm nhìn ký hiệu (visibility): default/hidden/protected; version script
- Chèn ký hiệu (interposition) và `LD_PRELOAD`

### 2.2 Bố trí và linker script
- Ánh xạ section đầu vào → section đầu ra
- Vùng nhớ (`MEMORY`) và bố trí (`SECTIONS`) cho hệ nhúng
- Ký hiệu do linker định nghĩa và cách code khởi động dùng chúng
- Địa chỉ nạp vs địa chỉ chạy (LMA vs VMA); sao chép `.data` lúc khởi động
- Điểm vào, vector ngắt, căn chỉnh section, lấp đầy
- Bản đồ liên kết (map file): đọc để biết cái gì chiếm chỗ ở đâu
- Loại bỏ section không dùng: `-ffunction-sections -fdata-sections --gc-sections`

### 2.3 Liên kết tĩnh và động
- Thư viện tĩnh `.a` vs thư viện chia sẻ `.so`: đánh đổi về kích thước, cập nhật, khởi động
- PIC/PIE, GOT, PLT: cơ chế và chi phí gián tiếp
- Tra cứu lúc chạy: `ld.so`, `DT_NEEDED`, `rpath` vs `runpath` vs `LD_LIBRARY_PATH`, thứ tự tìm kiếm
- `soname`, phiên bản hóa thư viện, tương thích ABI
- `dlopen`/`dlsym`: nạp động có chủ đích, plugin
- Công cụ: `ldd`, `patchelf`, `objdump -p`
- Liên kết tĩnh toàn phần: libc tĩnh, musl vs glibc, hệ quả

**Tự kiểm mục 2:** giải thích được từng dòng trong một linker script nhúng đang dùng.

## 3. Công cụ build

### 3.1 Mô hình đồ thị phụ thuộc
- Build là đồ thị có hướng không chu trình; đầu vào, đầu ra, quy tắc
- Build tăng dần đúng đắn: điều kiện cần và những cách nó bị phá
- Phụ thuộc thiếu → build sai âm thầm; phụ thuộc thừa → build chậm
- Phụ thuộc header sinh tự động (`-MMD -MP`)
- Vì sao "làm sạch rồi build lại" là dấu hiệu build system sai

### 3.2 make
- Quy tắc, điều kiện tiên quyết, công thức; biến và mở rộng (đệ quy vs đơn giản)
- Quy tắc mẫu, hàm dựng sẵn, `.PHONY`, mục tiêu mặc định
- Build song song và điều kiện để nó an toàn
- Vấn đề recursive make; giải pháp non-recursive
- Giới hạn của make và khi nào nên rời bỏ

### 3.3 CMake và các hệ khác
- Mô hình mục tiêu hiện đại: target, thuộc tính, `PUBLIC`/`PRIVATE`/`INTERFACE`
- Phụ thuộc bắc cầu và lan truyền cờ; vì sao biến toàn cục là phản mẫu
- Generator (Makefiles, Ninja), thư mục build ngoài nguồn
- `find_package`, config package, `FetchContent`, tích hợp với package manager
- Toolchain file và cấu hình cross-compile
- `compile_commands.json` và tích hợp với LSP/clang-tidy
- Hệ khác ở mức so sánh: Meson, Bazel, Ninja trực tiếp, cargo/go build

**Tự kiểm mục 3:** viết từ đầu một file build cho dự án nhiều thư mục, không copy mẫu.

## 4. Cross-compilation

### 4.1 Khái niệm
- Ba máy: build, host, target — định nghĩa chính xác và ví dụ khi cả ba khác nhau
- Bộ ba đích (target triple): kiến trúc, nhà cung cấp, hệ điều hành, môi trường ABI
- Toolchain: compiler, binutils, libc, thư viện chạy của compiler
- Sysroot: là gì, chứa gì, vì sao cần tách khỏi hệ thống của máy build
- Lựa chọn libc cho target: glibc, musl, newlib, không libc (freestanding)

### 4.2 Thực hành
- Nguồn toolchain: nhà sản xuất cung cấp, crosstool-NG, distro, container
- Cờ kiến trúc: `-march`, `-mcpu`, `-mfpu`, `-mfloat-abi` và hậu quả khi sai
- Build thư viện phụ thuộc cho target; pkg-config trong môi trường cross
- Kiểm thử: chạy trên phần cứng thật, qemu-user, giả lập
- Nạp firmware: `objcopy` sang hex/bin, công cụ flash, kiểm tra checksum
- Bẫy kinh điển: lẫn header của host, chạy công cụ của target trên host, phát hiện kiến trúc sai

**Tự kiểm mục 4:** cross-compile một binary cho ARM từ x86, chạy được trên board, giải thích mọi cờ.

## 5. Cờ biên dịch

### 5.1 Tối ưu hóa
- `-O0`/`-O1`/`-O2`/`-O3`/`-Os`/`-Og`/`-Oz`: mỗi mức bật gì về mặt nhóm tối ưu
- Tối ưu hóa chính và điều kiện áp dụng: inline, unroll, vector hóa, loại bỏ code chết, gộp biểu thức chung, phân bổ thanh ghi
- Tối ưu hóa lúc liên kết (LTO): full vs thin, lợi ích, chi phí, bẫy chẩn đoán
- Tối ưu hóa theo hồ sơ (PGO): quy trình hai pha
- Cờ làm thay đổi ngữ nghĩa: `-ffast-math`, `-fno-strict-aliasing`, `-fwrapv`
- Đánh đổi kích thước ↔ tốc độ ↔ khả năng debug

### 5.2 Chẩn đoán và cứng hóa
- Cảnh báo: tập nên bật mặc định, cảnh báo đáng bật thêm, `-Werror` và khi nào dùng
- Thông tin debug: `-g` các mức, định dạng DWARF, tách symbol (`objcopy --only-keep-debug`), build-id
- Strip và ảnh hưởng lên chẩn đoán sau sự cố
- Sanitizer như cờ build; chúng loại trừ nhau ra sao; dùng ở môi trường nào
- Cờ cứng hóa: stack protector, `_FORTIFY_SOURCE`, RELRO, PIE, CFI — làm gì và chi phí
- Phân tích tĩnh trong build: `-fanalyzer`, clang-tidy, cppcheck

**Tự kiểm mục 5:** giải thích từng cờ trong dòng biên dịch dự án hiện tại, không bỏ sót cái nào.

## 6. Build tái lập được và phụ thuộc

### 6.1 Tái lập
- Định nghĩa: cùng nguồn + cùng cấu hình → cùng bit
- Nguồn gây khác biệt: dấu thời gian, đường dẫn tuyệt đối, thứ tự file, song song, biến môi trường, ngẫu nhiên trong compiler
- Kỹ thuật: `SOURCE_DATE_EPOCH`, ánh xạ đường dẫn, sắp xếp đầu vào, cố định toolchain
- Build kín (hermetic) và cách ly bằng container
- Kiểm chứng tái lập: build hai lần, so sánh hash, `diffoscope`
- Vì sao điều này quan trọng: gỡ lỗi, kiểm toán, bảo mật chuỗi cung ứng

### 6.2 Phụ thuộc
- Chiến lược: gói hệ thống, vendoring, submodule, package manager, tải lúc cấu hình
- So sánh: khả năng tái lập, cập nhật bảo mật, kích thước repo, tính offline
- Ghim phiên bản và kiểm tra toàn vẹn bằng hash; lockfile
- Phụ thuộc bắc cầu, xung đột phiên bản, kim cương phụ thuộc
- Tương thích ABI khi nâng cấp thư viện chia sẻ
- Package manager C/C++: pkg-config, Conan, vcpkg — vai trò và giới hạn
- Chuỗi cung ứng: SBOM, nguồn gốc (provenance), quét lỗ hổng, rủi ro phụ thuộc bỏ hoang

### 6.3 Tăng tốc build
- Cache biên dịch: `ccache`, `sccache`; điều kiện trúng cache
- Build phân tán ở mức khái niệm
- Giảm phụ thuộc header, khai báo tới trước, unity build
- Đo thời gian build và tìm điểm nghẽn

**Tự kiểm mục 6:** build cùng một commit hai lần trên hai máy và giải thích mọi khác biệt.

## 7. CI và quy trình phát hành

### 7.1 Build trong CI
- Ma trận build: nền tảng × compiler × cấu hình; cái gì đáng chạy mọi lần
- Build sạch vs build tăng dần trong CI; cache và rủi ro của nó
- Cổng chất lượng: cảnh báo, phân tích tĩnh, sanitizer, test, coverage
- Thời gian phản hồi CI như ràng buộc thiết kế; chia tầng nhanh/chậm
- Tái tạo lỗi CI trên máy cục bộ: container, cùng ảnh, cùng cờ

### 7.2 Hiện vật và phát hành
- Hiện vật (artifact): cái gì lưu, lưu bao lâu, gắn với commit thế nào
- Đánh phiên bản binary; nhúng thông tin build (commit, thời gian, cấu hình)
- Symbol server / lưu trữ symbol cho chẩn đoán sau sự cố
- Ký và xác minh; kênh phát hành; khả năng quay lui
- Đóng gói theo đích: gói distro, container image, ảnh firmware

**Tự kiểm mục 7:** từ một binary đã phát hành, truy ngược ra commit và toolchain đã tạo ra nó.

## 8. Tổng kết

### 8.1 Mô hình tư duy rút gọn
- Phát biểu lại toàn bộ file trong 10–15 câu
- Danh sách kiểm tra tôi chạy khi dựng build cho một dự án mới

### 8.2 Cạm bẫy đã ghi nhận
- Chấp nhận cờ và file build không hiểu
- Build tăng dần sai âm thầm do phụ thuộc thiếu
- Phụ thuộc không ghim; "hôm qua build được"
- Những chỗ tôi từng hiểu sai và đã sửa
