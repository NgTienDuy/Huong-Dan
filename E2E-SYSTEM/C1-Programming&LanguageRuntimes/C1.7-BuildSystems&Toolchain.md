# C1.7 · Build system & toolchain — `In → Ad`

> **Mục tiêu của tài liệu.** Chuyển bạn từ "chạy được `make`" sang "biết chính xác chuyện gì xảy ra giữa file `.c` và binary chạy trên thiết bị, và sửa được khi nó hỏng".
>
> Đây là tài liệu về **tầng giữa** mà mọi người đi qua hàng ngày nhưng ít ai mở ra: bốn giai đoạn biên dịch, linker, thư viện, cross-compile. Nó nối trực tiếp với C1.1 §13 (ABI), C1.4 §1 (bố cục tiến trình, `.text`/`.data`/`.bss`) và C1.4 §7 (firmware).
>
> **Điều kiện tiên quyết:** C1.1 §2 (linkage), §13 (ABI); C1.4 §1 (section) và §7 (cấp phát tĩnh). Đọc qua là đủ.
> **Điều kiện hoàn thành:** vượt Checkpoint §11 — cross-compile một binary cho ARM từ x86, chạy được, và **giải thích được từng dòng** trong linker script.

## 0. Cách dùng tài liệu

### 0.1 Nguyên tắc

Build system là nơi người ta chấp nhận "không hiểu mà vẫn chạy" lâu nhất. Cái giá xuất hiện đúng lúc tệ nhất: lúc cross-compile, lúc binary chạy trên máy dev mà chết trên production, lúc phải giảm 20 KB cho vừa flash.

> **Mỗi giai đoạn của chuỗi build đều tạo ra một artifact bạn mở ra xem được.** Nếu bạn chưa từng mở, bạn đang tin chứ không phải biết.

### 0.2 Môi trường kiểm chứng

🔬 Mọi output chạy thật trên:
```
gcc 13.3.0 · GNU ld 2.42 · GNU make · cmake 3.28.3 · x86-64 Linux 1 vCPU
aarch64-linux-gnu-gcc 13.3.0   (cross Linux ARM64)
arm-none-eabi-gcc 13.2.1       (bare-metal Cortex-M)
qemu-aarch64-static 8.2.2      (chạy binary ARM trên x86)
```
Ký hiệu: ✅ output thật · 🔬 số đo · ⚠️ bẫy. *Quy ước trong khối output: chú thích sau dấu `←` là do tôi thêm; nhãn tiếng Việt mà script in ra (vốn không dấu) được thêm dấu cho dễ đọc. Mọi con số, mã lỗi và thông điệp của công cụ được giữ nguyên văn.*

## 1. Chuỗi biên dịch: bốn giai đoạn

### 1.1 Sơ đồ

```
hello.c
   │  1. PREPROCESS   cpp        gcc -E      → hello.i   (C thuần, đã khai triển)
   ▼
hello.i
   │  2. COMPILE      cc1        gcc -S      → hello.s   (assembly)
   ▼
hello.s
   │  3. ASSEMBLE     as         gcc -c      → hello.o   (ELF relocatable)
   ▼
hello.o  +  helper.o  +  libc
   │  4. LINK         ld/collect2            → hello     (ELF executable)
   ▼
hello
```
`gcc hello.c -o hello` chạy cả bốn. Mọi giai đoạn dừng lại được và artifact mở ra xem được.

### 1.2 Giai đoạn 1 — preprocess

Chỉ thao tác trên **dòng token**, không biết C (C1.1 §9.1).

✅ 13 dòng nguồn → **826 dòng** sau preprocess (64×, gần hết là từ `<stdio.h>`):
```c
/* nguồn */                          /* sau `gcc -E` */
#define GREETING "xin chao"          extern int helper(int);
#define TWICE(x) ((x) * 2)           int g_counter = 7;
static const char msg[] = GREETING;  int g_zero;
printf("%s %d\n", msg,               static const char msg[] = "xin chao";
       TWICE(helper(g_counter)));    printf("%s %d\n", msg, ((helper(g_counter)) * 2));
```
Macro biến mất, `#include` được nội tuyến, chuỗi liền kề được nối.

```sh
gcc -E f.c | grep -v '^#' | grep -v '^$'   # xem đúng cái compiler nhận được
gcc -dM -E - < /dev/null                   # mọi macro định nghĩa sẵn
gcc -M f.c                                 # liệt kê mọi header phụ thuộc
```
> **Khi nào cần:** macro không khai triển như bạn nghĩ, `#ifdef` chọn nhánh sai, xung đột tên do header.

### 1.3 Giai đoạn 2 — compile

✅ `gcc -S -masm=intel -O1`:
```asm
        .section    .rodata.str1.1
.LC0:   .string     "%s %d\n"
        .text
        .globl      main
main:
        endbr64
        sub     rsp, 8
        mov     edi, DWORD PTR g_counter[rip]
        call    helper@PLT               ; địa chỉ CHƯA biết
        lea     ecx, [rax+rax]           ; TWICE(x) đã thành x+x
        lea     rdx, msg[rip]
        call    __printf_chk@PLT
```
Đây là giai đoạn duy nhất **tối ưu hoá** xảy ra. Chi tiết tác động ở §7.

### 1.4 Giai đoạn 3 — assemble

Assembly → mã máy, đóng gói thành ELF relocatable. Chưa có địa chỉ thật.

✅
```text
$ file hello.o
hello.o: ELF 64-bit LSB relocatable, x86-64, not stripped

$ nm hello.o
0000000000000000 D g_counter      ← .data
0000000000000000 B g_zero         ← .bss
                 U helper         ← UNDEFINED: chưa biết ở đâu
0000000000000000 T main           ← .text
0000000000000000 r msg            ← .rodata (chữ thường = local)
                 U printf         ← UNDEFINED
```
Chú ý mọi địa chỉ đều là `0`: object file dùng offset trong section của chính nó.

### 1.5 Giai đoạn 4 — link

Linker làm ba việc: **gom section cùng loại**, **giải quyết symbol**, **ghi địa chỉ thật (relocation)**.

✅ Relocation là danh sách "chỗ nào cần điền địa chỉ":
```text
$ objdump -r hello.o
RELOCATION RECORDS FOR [.text]:
OFFSET            TYPE              VALUE
000000000000000a  R_X86_64_PC32     g_counter-0x4
0000000000000011  R_X86_64_PLT32    helper-0x4
000000000000001c  R_X86_64_PC32     .rodata-0x4
0000000000000033  R_X86_64_PLT32    printf-0x4
```
✅ Và đây là việc ghi địa chỉ, nhìn thấy trực tiếp:
```text
TRƯỚC link (hello.o):   10: call   15 <main+0x15>     ← chỗ trống, trỏ vào lệnh kế tiếp
SAU  link (hello)  : 1159: call   1187 <helper>       ← địa chỉ thật
```

✅ Hai lỗi linker kinh điển:
```text
/usr/bin/ld: hello.o: in function `main':
hello.c:(.text+0x11): undefined reference to `helper'

/usr/bin/ld: helper2.o: in function `helper':
helper2.c:(.text+0x0): multiple definition of `helper';
                       helper.o:helper.c:(.text+0x0): first defined here
```
Cả hai là hệ quả trực tiếp của **linkage** (C1.1 §2.5): `helper` có external linkage nên phải có đúng **một** định nghĩa trong toàn chương trình.

### 1.6 Lỗi ở giai đoạn nào — bảng tra

| Thông điệp | Giai đoạn | Nguyên nhân thường gặp |
|---|---|---|
| `No such file or directory` cho `#include` | 1 | thiếu `-I`, sai sysroot |
| `expected ';'`, `unknown type name` | 2 | cú pháp; hoặc thiếu header nên kiểu chưa khai báo |
| `implicit declaration of function` | 2 | thiếu prototype (C99 trở đi là lỗi) |
| `warning: conflicting types` | 2 | prototype khác định nghĩa |
| `Error: bad register name` | 3 | inline asm sai kiến trúc |
| **`undefined reference to X`** | **4** | thiếu `-l`, sai thứ tự `-l` (§10), symbol là `static`, tên bị mangle (C++) |
| **`multiple definition of X`** | **4** | định nghĩa trong header, thiếu `static`/`inline` |
| `cannot find -lfoo` | 4 | thiếu `-L`, thiếu gói `-dev` |
| `relocation R_X86_64_32S ... recompile with -fPIC` | 4 | thiếu `-fPIC` khi làm `.so` (§5.2) |
| `error while loading shared libraries` | **runtime** | `.so` không tìm thấy — `rpath`/`LD_LIBRARY_PATH` (§5.5) |
| `symbol lookup error` | runtime | `.so` tìm thấy nhưng thiếu symbol — sai phiên bản |

## 2. `make`

### 2.1 Mô hình

`make` **không** là ngôn ngữ script. Nó là một **bộ giải đồ thị phụ thuộc**:
```
đích : điều kiện tiên quyết
<TAB>công thức
```
Quy tắc duy nhất: *nếu đích không tồn tại, hoặc cũ hơn một điều kiện tiên quyết, thì chạy công thức.* So sánh bằng **mtime của file**.

### 2.2 Makefile đúng chuẩn

Bản dưới đây ngắn nhưng có đủ bốn thứ mà đa số Makefile viết tay thiếu.

```make
CC      ?= gcc
CFLAGS  ?= -std=c11 -O2 -g -Wall -Wextra -MMD -MP
LDFLAGS ?=
LDLIBS  ?=

SRC  := $(wildcard *.c)
OBJ  := $(SRC:%.c=build/%.o)
DEP  := $(OBJ:.o=.d)
BIN  := build/app

.PHONY: all clean run
all: $(BIN)

$(BIN): $(OBJ)
	$(CC) $(LDFLAGS) $^ $(LDLIBS) -o $@

build/%.o: %.c | build
	$(CC) $(CFLAGS) -c $< -o $@

build:
	mkdir -p $@

run: $(BIN)
	./$(BIN)

clean:
	rm -rf build

-include $(DEP)
```

Bốn điểm đáng chú ý:

**(1) `-MMD -MP` + `-include $(DEP)` — phụ thuộc header tự động.**
Không có nó, sửa một header thì `make` **không** build lại — bug tệ nhất của build system vì nó tạo ra binary lai giữa hai phiên bản mã nguồn.
```text
$ cat build/hello.d
build/hello.o: hello.c /usr/include/stdio.h ...
```
`-MP` thêm đích giả cho mỗi header, để xoá header không làm `make` báo lỗi.

**(2) `?=` thay vì `=`** — cho phép người dùng ghi đè: `make CC=clang CFLAGS='-O0 -g'`.

**(3) `| build`** — order-only prerequisite. Thư mục `build/` phải tồn tại, nhưng mtime của nó **không** được coi là lý do build lại.

**(4) `.PHONY`** — `all`, `clean`, `run` không phải tên file. Không khai báo thì một file tên `clean` sẽ làm `make clean` ngừng hoạt động.

✅ Chạy thật:
```text
$ make -s all && make -s run
xin chao 16
$ make all
make: Nothing to be done for 'all'.        ← không đổi gì thì không làm gì
$ touch hello.c && make -n all
cc -std=c11 -O2 -g -Wall -Wextra -MMD -MP -c hello.c -o build/hello.o
cc  build/hello.o build/helper.o  -o build/app       ← chỉ build lại cái cần
```

### 2.3 Biến tự động và bẫy

| Ký hiệu | Nghĩa |
|---|---|
| `$@` | tên đích |
| `$<` | điều kiện tiên quyết **đầu tiên** |
| `$^` | **mọi** điều kiện tiên quyết (đã loại trùng) |
| `$?` | những cái mới hơn đích |
| `$*` | phần khớp `%` trong pattern rule |

⚠️ Sáu bẫy hay gặp:
1. **TAB, không phải space** trong công thức. `make` báo `missing separator`.
2. **Mỗi dòng công thức là một shell riêng.** `cd foo` rồi xuống dòng `make` là vô nghĩa; dùng `cd foo && make` hoặc `.ONESHELL:`.
3. **`$` trong shell phải viết `$$`**: `for f in *.c; do echo $$f; done`.
4. **`=` là lazy, `:=` là ngay lập tức.** Dùng `:=` trừ khi bạn cố tình cần lazy.
5. **`make -j` cần phụ thuộc đúng.** Build chạy tuần tự nhưng hỏng song song = thiếu phụ thuộc.
6. **Thiếu phụ thuộc header** (điểm 1 ở trên) — nguyên nhân số một của "xoá build đi làm lại thì hết lỗi".

```sh
make -n            # in lệnh mà không chạy (dry run)
make -p            # in toàn bộ luật, kể cả luật ngầm
make -d            # vì sao make quyết định build lại
make --debug=b     # gọn hơn -d
make -j$(nproc)    # build song song
```

## 3. `CMake`

### 3.1 Mô hình

CMake **không** phải build system. Nó là **bộ sinh** build system: đọc `CMakeLists.txt` rồi sinh ra Makefile, Ninja, project Visual Studio hoặc Xcode.

Modern CMake (≥ 3.10) xoay quanh **target và property**, không phải biến toàn cục:
```
add_library / add_executable  → tạo target
target_*                      → gắn property lên target
PUBLIC / PRIVATE / INTERFACE  → property lan sang ai
```

| Từ khoá | Áp dụng cho target này | Lan sang target dùng nó |
|---|---|---|
| `PRIVATE` | ✔ | ✘ |
| `INTERFACE` | ✘ | ✔ |
| `PUBLIC` | ✔ | ✔ |

### 3.2 `CMakeLists.txt` đúng chuẩn

```cmake
cmake_minimum_required(VERSION 3.20)
project(mathx VERSION 1.0.0 LANGUAGES C)

set(CMAKE_C_STANDARD 11)
set(CMAKE_C_STANDARD_REQUIRED ON)
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)      # sinh compile_commands.json cho clangd/IDE

add_library(mathx src/mathx.c)
target_include_directories(mathx PUBLIC
    $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
    $<INSTALL_INTERFACE:include>)
target_compile_options(mathx PRIVATE -Wall -Wextra -Wconversion)
set_target_properties(mathx PROPERTIES VERSION ${PROJECT_VERSION} SOVERSION 1)

add_executable(app src/app.c)
target_link_libraries(app PRIVATE mathx)   # kéo theo include dir của mathx tự động

install(TARGETS mathx app EXPORT mathxTargets
        RUNTIME DESTINATION bin LIBRARY DESTINATION lib ARCHIVE DESTINATION lib)
install(DIRECTORY include/ DESTINATION include)

enable_testing()
add_test(NAME smoke COMMAND app)
```
✅
```text
$ cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j
$ ./build/app
mathx 1.0.0: 3+4=7  3*4=12
```

Ba điểm đáng chú ý:
* `target_include_directories(... PUBLIC ...)` — `app` **không** cần khai báo include dir; nó thừa hưởng qua `target_link_libraries`. Đây là toàn bộ ý nghĩa của "modern CMake".
* `$<BUILD_INTERFACE:...>` / `$<INSTALL_INTERFACE:...>` — generator expression: đường dẫn khác nhau khi build và khi đã cài.
* `SOVERSION 1` — sinh đúng bộ symlink `libmathx.so → .so.1 → .so.1.0.0` (§5.3).

✅ Đổi tĩnh ↔ động bằng **một** cờ:
```text
$ cmake -S . -B b2 -DBUILD_SHARED_LIBS=ON && cmake --build b2
b2/libmathx.so  b2/libmathx.so.1  b2/libmathx.so.1.0.0
```

### 3.3 `CMAKE_BUILD_TYPE`

✅ Cờ thật mà mỗi build type sinh ra:
```text
Debug            -g
Release          -O3 -DNDEBUG
RelWithDebInfo   -O2 -g -DNDEBUG
MinSizeRel       -Os -DNDEBUG
```
⚠️ **Không đặt `CMAKE_BUILD_TYPE` thì với generator Makefile/Ninja bạn được build KHÔNG có cờ tối ưu nào** — chậm hơn `-O2` nhiều lần (§7) và không ai để ý. Luôn đặt tường minh.
⚠️ `-DNDEBUG` **tắt `assert`** (C1.5 §8.3). Bất biến bạn kiểm bằng `assert` biến mất ở release.

### 3.4 Chọn build system nào

| | `make` | `CMake` | `Ninja` | `Meson` | `Bazel` |
|---|---|---|---|---|---|
| Vai trò | build system | **bộ sinh** | build system (nhanh) | bộ sinh | build + dependency + cache |
| Học | dễ đọc, khó viết đúng | trung bình | không viết tay | dễ nhất | khó |
| Đa nền tảng | kém (Windows) | **tốt nhất** | tốt | tốt | tốt |
| Cross-compile | thủ công | toolchain file | — | cross file | toolchain |
| Build song song | `-j` | qua generator | rất nhanh | qua Ninja | rất nhanh |
| Tìm dependency | thủ công | `find_package` | — | `dependency()` | workspace |
| Hermetic / cache phân tán | ✘ | ✘ | ✘ | ✘ | **✔** |
| Phù hợp | dự án nhỏ, firmware | mặc định cho C/C++ | backend của CMake/Meson | dự án mới | monorepo lớn |

Kết hợp thực dụng nhất hiện nay: **CMake sinh Ninja**.
```sh
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build
```

## 4. Linker

### 4.1 Symbol

Mỗi symbol có **loại**, **binding** và **visibility**.

✅ Đọc bằng `nm` (chữ hoa = global, chữ thường = local):
```text
0000000000000000 D g_counter     D/d = .data
0000000000000000 B g_zero        B/b = .bss
                 U helper        U   = undefined (cần từ nơi khác)
0000000000000000 T main          T/t = .text
0000000000000000 r msg           R/r = .rodata
                 W foo           W   = weak (có thể bị ghi đè)
0000000000000000 C bar           C   = common (biến chưa khởi tạo, C1.1 §2.7)
```

| Binding | Nghĩa |
|---|---|
| `GLOBAL` | thấy được từ object khác |
| `LOCAL` | chỉ trong object này (`static` — C1.1 §2.5) |
| `WEAK` | như global, nhưng bị định nghĩa mạnh ghi đè; không có cũng không lỗi |

Weak symbol là cơ chế của `__attribute__((weak, alias(...)))` dùng trong bảng vector firmware (§11.3): mọi handler mặc định trỏ tới `Default_Handler`, và người dùng chỉ cần định nghĩa lại cái mình cần.

**Visibility** (chỉ với `.so`):
```c
__attribute__((visibility("default"))) int public_api(void);
__attribute__((visibility("hidden")))  int internal(void);
```
```sh
gcc -fvisibility=hidden ...    # ẩn hết, rồi đánh dấu tường minh cái nào công khai
```
Lợi ích: `.so` nhỏ hơn, nạp nhanh hơn, và **không bị interposition ngoài ý muốn** (§10.1).

### 4.2 Relocation

Mỗi mục relocation nói: *"tại offset X trong section S, ghi địa chỉ của symbol Y theo cách Z"*.

| Loại (x86-64) | Cách tính | Dùng cho |
|---|---|---|
| `R_X86_64_PC32` | `S + A - P` (tương đối với PC) | truy cập trong cùng module |
| `R_X86_64_PLT32` | qua PLT | gọi hàm có thể ở `.so` khác |
| `R_X86_64_GOTPCREL` | qua GOT | truy cập dữ liệu ở `.so` khác |
| `R_X86_64_64` | `S + A` (tuyệt đối 64-bit) | bảng con trỏ |
| `R_X86_64_32S` | tuyệt đối 32-bit có dấu | ⚠️ không dùng được trong `.so` (§5.2) |

```sh
objdump -r  f.o        # relocation trong object
readelf -r  f.o
objdump -R  prog       # relocation động (còn lại lúc chạy)
```

### 4.3 Section vs segment

```
SECTION : đơn vị của LINKER   (.text, .data, .bss, .rodata, .debug_*)
SEGMENT : đơn vị của LOADER   (LOAD r-x, LOAD rw-, ...)
```
Linker gom nhiều section thành ít segment theo quyền truy cập — đó là lý do C1.4 §1.4 thấy cùng một file được map nhiều lần với quyền khác nhau.
```sh
readelf -S prog     # section
readelf -l prog     # segment + ánh xạ section → segment
```

### 4.4 `--gc-sections` và map file

```sh
gcc -ffunction-sections -fdata-sections -Wl,--gc-sections -Wl,-Map=out.map ...
```
* `-ffunction-sections` / `-fdata-sections`: mỗi hàm/biến vào một section riêng (`.text.foo`).
* `--gc-sections`: linker xoá section không ai tham chiếu tới.
* `-Map=out.map`: sinh map file — nguồn sự thật để biết **cái gì chiếm bao nhiêu**.

⚠️ `KEEP()` trong linker script bảo vệ section khỏi bị `--gc-sections` xoá. Bảng vector firmware **phải** có `KEEP`, vì không code nào tham chiếu tới nó (phần cứng đọc trực tiếp) — quên là firmware không boot.

```sh
grep -A30 'Memory Configuration' out.map     # bố cục bộ nhớ
grep 'Discarded input section' out.map       # cái gì bị gc-sections xoá
nm --size-sort -S prog | tail -20            # symbol to nhất
```

### 4.5 Linker script

Linker script mô tả **bố cục bộ nhớ đầu ra**. Với chương trình Linux thường, script mặc định (`ld --verbose`) là đủ. Với firmware bare-metal, bạn **phải** tự viết — xem §11.3, nơi từng dòng được giải thích và kiểm chứng.

## 5. Thư viện tĩnh vs động

### 5.1 So sánh

```
libfoo.a   = kho lưu trữ (ar) chứa các .o. Linker NHÚNG .o cần thiết vào binary.
libfoo.so  = ELF shared object. Linker chỉ ghi "cần libfoo.so.1"; loader nạp lúc chạy.
```

✅ Cùng một thư viện, hai cách:
```text
--- TĨNH ---
$ ar t libmathx.a          →  mathx.o
$ gcc app.c -L. -lmathx -o app_static
kích thước: 16.096 byte
$ nm app_static | grep mx_add
00000000000011b0 T mx_add          ← ĐÃ NẰM TRONG binary
$ ldd app_static
  libc.so.6 => ...                 ← chỉ còn libc

--- ĐỘNG ---
$ gcc -shared -Wl,-soname,libmathx.so.1 -o libmathx.so.1.0.0 mathx_pic.o
$ gcc app.c -L. -lmathx -o app_dyn
kích thước: 16.064 byte
$ nm -D app_dyn | grep mx_add
                 U mx_add          ← UNDEFINED, giải quyết lúc nạp
$ ldd app_dyn
  libmathx.so.1 => ./libmathx.so.1
```

| | Tĩnh `.a` | Động `.so` |
|---|---|---|
| Kích thước binary | lớn hơn (nhúng code) | nhỏ hơn |
| Tổng đĩa khi có N chương trình | N bản sao | 1 bản |
| RAM khi chạy N tiến trình | N bản | **1 bản `.text` chia sẻ** |
| Vá lỗi bảo mật của thư viện | build lại **mọi** chương trình | thay 1 file |
| Thời gian khởi động | nhanh | chậm hơn (nạp + relocate) |
| Chi phí mỗi lời gọi | 0 | qua PLT lần đầu |
| `--gc-sections` loại code chết | ✔ hiệu quả | ✘ (cả `.so` được nạp) |
| Tối ưu xuyên thư viện (LTO) | ✔ | ✘ |
| Triển khai | một file, dễ | phải mang theo `.so` đúng phiên bản |
| Phù hợp | container nhỏ, firmware, CLI phân phối | hệ điều hành, plugin |

### 5.2 `-fPIC` — vì sao bắt buộc cho `.so`

`.so` có thể được nạp ở **địa chỉ bất kỳ** (ASLR, và nhiều `.so` không thể cùng chiếm một địa chỉ cố định). Nên code trong đó không được chứa **địa chỉ tuyệt đối**.

* **PIC** (Position Independent Code): truy cập dữ liệu qua **GOT** (Global Offset Table), gọi hàm qua **PLT** (Procedure Linkage Table). Loader điền GOT lúc nạp.
* Code không PIC chứa relocation tuyệt đối → linker phải sửa trực tiếp trong `.text`.

✅ Hậu quả thật khi thiếu `-fPIC`:
```text
$ gcc -c -O2 -fno-pic -mcmodel=large absdata.c -o abs.o
$ gcc -shared -o b3.so abs.o
/usr/bin/ld: warning: relocation against `arr' in read-only section `.text'
/usr/bin/ld: warning: creating DT_TEXTREL in a shared object
```
`DT_TEXTREL` nghĩa là loader phải **làm `.text` ghi được** để vá, rồi đặt lại chỉ đọc. Ba cái giá: mất chia sẻ trang giữa các tiến trình (mỗi tiến trình một bản copy-on-write), nạp chậm hơn, và vi phạm W^X (C1.4 §1.4).

⚠️ Trên x86-64 với code model nhỏ (mặc định), GCC dùng địa chỉ tương đối PC cho phần lớn truy cập, nên lỗi này **ít gặp hơn xưa**. Trên x86 32-bit và với bảng dữ liệu lớn, nó vẫn là lỗi cứng: `relocation R_X86_64_32S ... can not be used when making a shared object; recompile with -fPIC`.

| Cờ | Nghĩa |
|---|---|
| `-fPIC` | PIC cho thư viện chia sẻ (bảng GOT không giới hạn kích thước) |
| `-fpic` | như trên, GOT nhỏ hơn (giới hạn trên vài kiến trúc) |
| `-fPIE` / `-fpie` | PIC cho **executable** — cho phép ASLR cả `.text` |
| `-fno-pie -no-pie` | binary nạp ở địa chỉ cố định (dễ debug, kém an toàn) |

Ubuntu/Debian bật `-fPIE -pie` mặc định cho executable.

### 5.3 `SONAME` và versioning

```
libmathx.so           → symlink, chỉ dùng lúc LINK (-lmathx)
libmathx.so.1         → SONAME, cái loader tìm lúc CHẠY
libmathx.so.1.0.0     → file thật
```
✅
```text
$ readelf -d libmathx.so.1.0.0 | grep SONAME
 0x000000000000000e (SONAME)  Library soname: [libmathx.so.1]
```
Quy ước: **tăng số sau `.so.` khi phá ABI** (C1.1 §13.8 — thêm trường vào struct công khai, đổi chữ ký, v.v.). Chương trình cũ link với `.so.1` vẫn chạy khi bạn cài thêm `.so.2` cạnh nó.

### 5.4 `LD_PRELOAD`

Nạp một `.so` **trước mọi thư viện khác**, nên symbol của nó thắng.

✅ Chạy thật:
```text
bình thường : mathx 1.0.0: 3+4=7    3*4=12
LD_PRELOAD  : mathx GIA-MAO-9.9.9: 3+4=999  3*4=12
                   ↑ mx_version bị thay   ↑ mx_add bị thay   ↑ mx_mul vẫn thật

LD_PRELOAD trên bản LIÊN KẾT TĨNH: mathx 1.0.0: 3+4=7  3*4=12
  → không có tác dụng: symbol đã được nhúng thẳng vào binary
```
Dùng để: mock trong test, profiler (`valgrind`, `jemalloc`), sửa lỗi thư viện không có mã nguồn, chèn instrumentation.
⚠️ Đây cũng là vector tấn công; vì vậy `LD_PRELOAD` bị bỏ qua với binary setuid.

### 5.5 `rpath`, `runpath`, `$ORIGIN`

✅
```text
$ gcc app.c -L. -lmathx -Wl,-rpath,'$ORIGIN' -o app_rpath
$ readelf -d app_rpath
 (NEEDED)   Shared library: [libmathx.so.1]
 (RUNPATH)  Library runpath: [$ORIGIN]
$ ./app_rpath                      ← chạy được, KHÔNG cần LD_LIBRARY_PATH
mathx 1.0.0: 3+4=7  3*4=12
```
`$ORIGIN` = thư mục chứa chính binary → cài đặt di chuyển được (`/opt/myapp/bin/app` tìm `.so` ở `/opt/myapp/lib` với `-Wl,-rpath,'$ORIGIN/../lib'`).

**Thứ tự loader tìm `.so`:**
```
1. DT_RPATH của binary       (cũ; LD_LIBRARY_PATH KHÔNG ghi đè được)
2. LD_LIBRARY_PATH
3. DT_RUNPATH của binary     (mới; BỊ LD_LIBRARY_PATH ghi đè trước)
4. /etc/ld.so.cache          (ldconfig)
5. /lib, /usr/lib
```
⚠️ Khác biệt `RPATH` vs `RUNPATH` quan trọng: `RPATH` khoá chặt, `RUNPATH` cho phép người vận hành ghi đè. Binutils hiện đại mặc định sinh `RUNPATH` (`--enable-new-dtags`). Nếu bạn *cần* khoá, thêm `-Wl,--disable-new-dtags`.

```sh
ldd prog                          # .so nào được nạp từ đâu
LD_DEBUG=libs ./prog              # nhật ký chi tiết quá trình tìm
LD_DEBUG=bindings ./prog          # symbol nào bind vào đâu
readelf -d prog | grep -E 'NEEDED|RPATH|RUNPATH'
```

## 6. Cross-compilation

### 6.1 Toolchain triple

```
aarch64 - linux - gnu
  │         │      └── ABI / thư viện C   (gnu, musl, eabi, eabihf, android)
  │         └───────── hệ điều hành       (linux, none, windows, darwin)
  └─────────────────── kiến trúc          (aarch64, arm, riscv64, x86_64)
```
✅
```text
$ gcc -dumpmachine
x86_64-linux-gnu
$ aarch64-linux-gnu-gcc -dumpmachine
aarch64-linux-gnu
$ arm-none-eabi-gcc -dumpmachine
arm-none-eabi              ← "none" = không có OS (bare metal), eabi = ABI nhúng
```

| Triple | Dùng cho |
|---|---|
| `aarch64-linux-gnu` | ARM64 chạy Linux có glibc (Raspberry Pi 64-bit, server ARM) |
| `arm-linux-gnueabihf` | ARM32 Linux, có FPU phần cứng (`hf` = hard float) |
| `arm-none-eabi` | Cortex-M bare metal (không OS) |
| `riscv64-linux-gnu` | RISC-V Linux |
| `x86_64-w64-mingw32` | Windows từ Linux |
| `aarch64-linux-musl` | ARM64 với musl libc (container nhỏ) |

### 6.2 Ba "máy" trong một build

```
BUILD  : máy bạn đang chạy compiler        (x86-64)
HOST   : máy binary sẽ CHẠY trên           (aarch64)
TARGET : máy binary SINH RA code cho       (chỉ có nghĩa khi build compiler)
```
Hầu hết trường hợp bạn chỉ quan tâm BUILD ≠ HOST. Khi build **chính compiler**, cả ba mới khác nhau (Canadian cross).

### 6.3 Sysroot

Cross-compiler cần header và thư viện của **hệ thống đích**, không phải của máy bạn.
```
sysroot/
├── usr/include/      ← header của đích (stdio.h của ARM, không phải x86)
└── usr/lib/          ← libc.so, crt1.o... của đích
```
✅
```text
$ aarch64-linux-gnu-gcc -print-sysroot
/
$ aarch64-linux-gnu-gcc -print-file-name=libc.so
/usr/lib/gcc-cross/aarch64-linux-gnu/13/../../../../aarch64-linux-gnu/lib/../lib/libc.so
$ echo | aarch64-linux-gnu-gcc -E -Wp,-v - 2>&1 | grep '^ /'
 /usr/lib/gcc-cross/aarch64-linux-gnu/13/include
 /usr/lib/gcc-cross/aarch64-linux-gnu/13/../../../../aarch64-linux-gnu/include
 /usr/include
```
⚠️ Dòng cuối `/usr/include` là **của máy x86**. Với gói cross của Debian điều này an toàn vì header ở đó độc lập kiến trúc; nhưng với sysroot tự dựng, lẫn header của host là nguồn lỗi khó chẩn đoán. Dùng `--sysroot=/path` để khoá.

```sh
aarch64-linux-gnu-gcc --sysroot=/opt/sysroot-arm64 -O2 f.c -o f
```

### 6.4 Bằng chứng: cùng nguồn, hai kiến trúc

✅ Cùng file `sysinfo.c`, build hai lần:
```text
=== x86-64 (native) ===
kiến trúc     : x86-64
sizeof: int=4 long=8 ptr=8 ldouble=16
char có dấu   : có

=== aarch64 (cross, chạy dưới qemu) ===
kiến trúc     : aarch64
sizeof: int=4 long=8 ptr=8 ldouble=16
char có dấu   : không
```
> ⚠️ **`char` có dấu trên x86-64, KHÔNG dấu trên aarch64.** Đây chính xác là điều C1.1 §2.2 nói là implementation-defined, giờ nhìn thấy bằng cách chạy **cùng một mã nguồn** trên hai kiến trúc. Mọi chỗ so sánh `char c < 0` hoặc truyền `char` cho `<ctype.h>` (C1.1 §8.4) sẽ hành xử khác nhau.
>
> Đây là lý do cross-compile **phải kèm chạy thử trên đích**, không chỉ "build thành công".

### 6.5 CMake toolchain file

✅ File này đủ để CMake cross-compile:
```cmake
set(CMAKE_SYSTEM_NAME Linux)             # ← đặt cái này là CMake biết đang cross
set(CMAKE_SYSTEM_PROCESSOR aarch64)
set(CMAKE_C_COMPILER   aarch64-linux-gnu-gcc)
set(CMAKE_CXX_COMPILER aarch64-linux-gnu-g++)
set(CMAKE_FIND_ROOT_PATH /usr/aarch64-linux-gnu)
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)   # công cụ: lấy từ HOST
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)    # thư viện: CHỈ lấy từ sysroot
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
```
```text
$ cmake -S . -B build-arm -DCMAKE_TOOLCHAIN_FILE=arm64.cmake -DCMAKE_BUILD_TYPE=Release
$ cmake --build build-arm -j
$ file build-arm/app
build-arm/app: ELF 64-bit LSB pie executable, ARM aarch64
$ qemu-aarch64-static -L /usr/aarch64-linux-gnu ./build-arm/app
mathx 1.0.0: 3+4=7  3*4=12
```
Ba dòng `FIND_ROOT_PATH_MODE` là điểm hay sai nhất: nếu để mặc định, `find_library` sẽ tìm thấy thư viện **x86** và link vào binary ARM → lỗi rất khó hiểu ở giai đoạn link.

### 6.6 Kiểm chứng mà không có board

| Cách | Kiểm được gì |
|---|---|
| `file`, `readelf -h` | đúng kiến trúc, đúng loại ELF |
| **`qemu-<arch>-static`** (user mode) | **chạy thật** binary Linux của đích |
| `qemu-system-<arch>` | boot cả hệ điều hành / firmware |
| `renode`, QEMU `-M` board cụ thể | firmware bare-metal với ngoại vi mô phỏng |
| `binfmt_misc` + qemu | chạy binary ARM như binary bản địa, kể cả trong Docker |

```sh
docker run --rm --platform linux/arm64 -v $PWD:/w -w /w ubuntu ./app   # cần qemu binfmt
```

## 7. Cờ tối ưu và tác động thật

### 7.1 Đo, không đoán

🔬 Bốn workload đại diện, `gcc 13.3`, trung vị 3 lần chạy. Thời gian tính bằng ms (thấp hơn = tốt hơn):

| Cờ | `.text` | `crc32` (bit-twiddling) | `dot` (số thực) | `saxpy` (vector hoá được) | `sum_mod` (có nhánh) |
|---|---|---|---|---|---|
| `-O0` | 3.422 | 203,9 | 145,5 | 78,4 | 75,4 |
| `-O1` | **2.831** | 84,4 | 38,6 | 23,7 | 54,5 |
| `-O2` | 3.455 | 86,6 | 36,7 | 24,7 | 58,7 |
| `-O3` | **4.445** | **63,8** | 38,3 | **7,9** | **41,2** |
| `-Os` | **2.710** | 86,7 | 37,1 | 23,1 | **109,4** |
| `-O2 -flto` | 3.423 | 87,9 | 37,7 | **7,7** | 41,5 |

**Tăng tốc so với `-O0`:**
```
-O1         crc32= 2,4x  dot= 3,8x  saxpy= 3,3x  sum_mod= 1,4x
-O2         crc32= 2,4x  dot= 4,0x  saxpy= 3,2x  sum_mod= 1,3x
-O3         crc32= 3,2x  dot= 3,8x  saxpy= 9,9x  sum_mod= 1,8x
-Os         crc32= 2,4x  dot= 3,9x  saxpy= 3,4x  sum_mod= 0,7x   ← CHẬM HƠN -O0
-O2 -flto   crc32= 2,3x  dot= 3,9x  saxpy=10,2x  sum_mod= 1,8x
```

Năm điều đọc được:

1. **`-O0` → `-O1` là bước nhảy lớn nhất** (2,4–4×). Chạy benchmark ở `-O0` rồi kết luận "ngôn ngữ này chậm" là sai lầm phổ biến.
2. **`-O1` → `-O2` gần như không đổi** với bốn workload này. `-O2` hơn `-O1` chủ yếu ở code lớn và phức tạp hơn.
3. **`-O3` đáng giá đúng khi có vòng lặp vector hoá được:** `saxpy` 24,7 → **7,9 ms** (3,1×). Cái giá là `.text` **+29%** (3.455 → 4.445).
4. ⚠️ **`-Os` có thể chậm hơn `-O0`.** `sum_mod` mất 109,4 ms ở `-Os` so với 75,4 ms ở `-O0` — `-Os` từ chối unroll/vector hoá để giữ code nhỏ, và với vòng lặp nhiều nhánh này lựa chọn đó phản tác dụng. **Luôn đo, đừng giả định `-Os` chỉ đánh đổi một chút tốc độ.**
5. **`-O2 -flto` cho tốc độ của `-O3` với kích thước của `-O2`:** `saxpy` 7,7 ms (bằng `-O3`) nhưng `.text` 3.423 (nhỏ hơn `-O3` 23%). Lý do: LTO cho phép inline **xuyên translation unit**, mở khoá vector hoá mà không phải unroll khắp nơi.

### 7.2 Từng mức làm gì

| Mức | Bật gì | Dùng khi |
|---|---|---|
| `-O0` | không tối ưu; mỗi biến có chỗ trên stack | **debug** — bước từng dòng khớp mã nguồn |
| `-O1` | tối ưu cơ bản, không tăng nhiều thời gian biên dịch | build nhanh có tối ưu |
| `-O2` | **mặc định cho release**; inline, vector hoá cơ bản, CSE, loại code chết | đa số trường hợp |
| `-O3` | + vector hoá mạnh, unroll, inline tích cực hơn | đã đo và thấy lợi |
| `-Os` | `-O2` trừ những gì làm to code | flash hạn chế |
| `-Oz` (clang) | nhỏ hơn `-Os`, hy sinh tốc độ nhiều hơn | firmware chật |
| `-Og` | tối ưu **giữ được khả năng debug** | dev build nghiêm túc |
| `-Ofast` | `-O3` + **vi phạm IEEE 754** | ⚠️ chỉ khi bạn hiểu hệ quả số học |

⚠️ `-ffast-math` (nằm trong `-Ofast`) cho phép sắp xếp lại phép toán dấu phẩy động, coi NaN/Inf không tồn tại, và **đổi kết quả số học**. Không bật trên code tài chính hay khoa học trừ khi đã kiểm chứng.

### 7.3 LTO

```sh
gcc -O2 -flto -c a.c -o a.o        # object chứa IR, không phải mã máy
gcc -O2 -flto a.o b.o -o prog      # tối ưu toàn chương trình rồi mới sinh mã
gcc -O2 -flto=auto ...             # song song hoá LTO
```
| Ưu | Nhược |
|---|---|
| Inline xuyên file | link chậm hơn nhiều |
| Loại code chết toàn cục | tốn RAM khi link |
| Truyền hằng số xuyên module | thông điệp lỗi khó đọc hơn |
| 🔬 `saxpy` 24,7 → 7,7 ms | phải dùng cùng cờ cho compile **và** link |

⚠️ Với LTO, `-fstack-usage` và phân tích stack (C1.4 §9.2) phải chạy **sau** LTO, trên binary cuối.

### 7.4 `-march` và `-mtune`

```sh
-march=x86-64-v3    # dùng tập lệnh đến AVX2 — binary KHÔNG chạy trên CPU cũ hơn
-mtune=native       # tối ưu lịch trình cho CPU này, nhưng VẪN chạy trên CPU cũ
-march=native       # ⚠️ binary chỉ chắc chắn chạy trên đúng máy build
```
⚠️ `-march=native` trong CI là bẫy: binary build trên runner có AVX-512 sẽ `SIGILL` trên máy production không có. Dùng mức baseline tường minh (`x86-64-v2`/`v3`), hoặc function multiversioning.

🔬 Trong phép đo trên, `-march=native` **không cải thiện gì** — vì máy ảo báo một CPU mức cơ sở. Một minh chứng nữa cho việc phải đo trên đúng phần cứng đích.

## 8. Cờ debug, symbol, stripping

### 8.1 Chi phí của thông tin debug

🔬 Cùng một chương trình:

| Build | Kích thước file |
|---|---|
| `-O2` | 16.408 |
| `-O2 -g` | **23.904** (+46%) |
| `-O2 -g3` | **65.568** (4×) — `-g3` thêm cả macro |
| `-O2 -g` rồi `strip` | **14.472** |
| `-O2 -g` rồi `strip --strip-debug` | 16.232 (giữ `.symtab`) |
| file `.debug` tách riêng | 12.536 |

✅ Section debug sinh ra:
```text
.debug_aranges .debug_info .debug_abbrev .debug_line .debug_str
.debug_line_str .debug_loclists .debug_rnglists
```
Sau `strip`: **0** section debug hoặc `.symtab`.

> **Quan trọng:** `-g` **không** làm chương trình chậm đi. Nó chỉ thêm section không được nạp vào bộ nhớ khi chạy (C1.4 §1.4 — chỉ segment `LOAD` mới vào RAM). Không có lý do kỹ thuật nào để build release mà không có `-g`.

### 8.2 Mẫu đúng: build có `-g`, ship đã strip, giữ symbol riêng

```sh
gcc -O2 -g -o app app.c                        # 1. build đầy đủ
objcopy --only-keep-debug app app.debug        # 2. tách thông tin debug
objcopy --strip-debug app                      # 3. binary gọn để ship
objcopy --add-gnu-debuglink=app.debug app      # 4. ghi liên kết tới file debug
```
Sau đó lưu `app.debug` vào symbol server. Khi có core dump từ production, `gdb` tự tìm được nhờ `debuglink` hoặc **Build ID**.

```sh
readelf -n app | grep -A1 'Build ID'    # hash nội dung, định danh bản build
```
Build ID là cách hiện đại để nối binary ↔ symbol: `/usr/lib/debug/.build-id/ab/cdef...debug`.

### 8.3 Các mức `-g`

| Cờ | Nội dung |
|---|---|
| `-g0` | không có |
| `-g1` | backtrace + tên hàm, không có biến cục bộ |
| `-g` (`-g2`) | mặc định: biến, kiểu, số dòng |
| `-g3` | + macro (`-g3` cho phép `print MY_MACRO` trong gdb) |
| `-gsplit-dwarf` | tách DWARF ra file `.dwo` — link nhanh hơn nhiều |
| `-fno-omit-frame-pointer` | giữ `rbp` — backtrace tin cậy cho profiler (C1.4 §2.2) |

Khuyến nghị cho release thật:
```sh
-O2 -g -fno-omit-frame-pointer -DNDEBUG
```
`-fno-omit-frame-pointer` tốn khoảng 1–2% hiệu năng và đổi lại `perf`/`py-spy` cho stack đúng.

## 9. Build tái lập được

### 9.1 Vì sao

Build tái lập được (**reproducible build**) nghĩa là: cùng nguồn + cùng toolchain + cùng cấu hình → **binary giống nhau từng bit**.

Ba lợi ích: kiểm chứng được binary phát hành đúng là từ mã nguồn công khai (chuỗi cung ứng); cache build hiệu quả; và debug dễ hơn vì "cùng input thì cùng output".

### 9.2 Đo thật

✅ Hai lần build cách nhau 1 giây:
```text
có __DATE__/__TIME__ trong nguồn:
   9c17035352cb8725328033d42f3c7cfb
   e25987ff32c9ecdd78c5e509753ecb24     ← KHÁC NHAU

không có macro thời gian:
   304a1f1162bcc49161d97961a5a5f049
   304a1f1162bcc49161d97961a5a5f049     ← GIỐNG HỆT, bit-for-bit
```
✅ Đường dẫn tuyệt đối lọt vào binary:
```text
strings app | grep -c "/home/claude"                        → 1
với -ffile-prefix-map=$(pwd)=/src                           → 0
```

### 9.3 Danh sách nguồn gây khác biệt

| Nguồn | Cách chữa |
|---|---|
| `__DATE__`, `__TIME__`, `__TIMESTAMP__` | bỏ; hoặc `SOURCE_DATE_EPOCH` |
| Đường dẫn build tuyệt đối | `-ffile-prefix-map=$(pwd)=/src` (gồm cả debug và `__FILE__`) |
| Thứ tự file từ `wildcard`/`glob` | `sort` tường minh |
| Thứ tự chạy song song ảnh hưởng thứ tự link | liệt kê object tường minh |
| Timestamp trong archive `.a` | `ar D` (deterministic mode — mặc định trên Debian) |
| `$USER`, `$HOSTNAME`, `$PWD` trong nguồn | loại bỏ |
| Phiên bản compiler/binutils khác | pin trong container |
| Locale ảnh hưởng sắp xếp | `LC_ALL=C` |
| Hash bảng phụ thuộc thứ tự con trỏ | `-frandom-seed=<cố định>` |

```sh
export SOURCE_DATE_EPOCH=1700000000        # chuẩn reproducible-builds.org
export LC_ALL=C TZ=UTC
gcc -O2 -g -ffile-prefix-map=$PWD=/src -frandom-seed=$(sha256sum f.c | cut -c1-16) ...
```

### 9.4 Hermetic build

Một bậc cao hơn: build **không phụ thuộc gì ở máy** ngoài cái được khai báo.
```
1. Toolchain được pin (phiên bản + hash)
2. Mọi dependency được pin (phiên bản + hash)
3. Không truy cập mạng trong lúc build
4. Không đọc biến môi trường không khai báo
5. Chạy trong container/sandbox
```
Công cụ: **Bazel**, **Nix**, **Guix**, hoặc container có lockfile nghiêm ngặt.

```dockerfile
# Cách "đủ dùng" cho đa số dự án: pin bằng digest, không phải tag
FROM debian:bookworm-20240513-slim@sha256:1234...
RUN apt-get update && apt-get install -y --no-install-recommends \
      gcc=4:12.2.0-3 make=4.3-4.1 && rm -rf /var/lib/apt/lists/*
ENV SOURCE_DATE_EPOCH=1700000000 LC_ALL=C TZ=UTC
```
⚠️ `FROM debian:bookworm` (tag) **không** tái lập được — tag di chuyển. Phải dùng digest `@sha256:`.

### 9.5 Kiểm chứng

```sh
# Build hai lần trong hai thư mục khác nhau rồi so
sha256sum build1/app build2/app
diffoscope build1/app build2/app     # nếu khác, công cụ này chỉ ra KHÁC Ở ĐÂU
```
`diffoscope` là công cụ chuẩn của dự án Reproducible Builds: nó giải nén, disassemble, so DWARF, và chỉ ra chính xác byte nào khác vì lý do gì.

## 10. Quản lý dependency và xung đột phiên bản

### 10.1 Bài toán kim cương với `.so`

```
          app
         /   \
      libA   libB
        │      │
      ver 1.0  ver 2.0     ← cùng tên symbol `ver()`
```
✅ Chạy thật, chỉ đổi thứ tự link:
```text
$ gcc main.o -L. -lA -lB -o d1 && ./d1
  A dùng ver() = 1.0
  B dùng ver() = 1.0        ← libB được build với 2.0 nhưng nhận 1.0

$ gcc main.o -L. -lB -lA -o d2 && ./d2
  A dùng ver() = 2.0        ← bây giờ libA nhận 2.0
  B dùng ver() = 2.0
```
> **Đây là ELF symbol interposition:** trong một tiến trình, một tên symbol chỉ bind tới **một** định nghĩa — cái được tìm thấy đầu tiên theo thứ tự nạp. Cả hai thư viện đều dùng chung, và **thư viện nào "thua" sẽ chạy với code nó chưa từng được test cùng**. Lỗi loại này không có thông báo nào.

Bốn cách chữa:

| Cách | Cụ thể |
|---|---|
| **Symbol versioning** | một `.so` chứa nhiều phiên bản của cùng symbol |
| **Ẩn symbol** | `-fvisibility=hidden` — libA không xuất `ver()` ra ngoài |
| **Đổi tên** (namespacing) | `mylib_v2_ver()`; chuẩn mực cho thư viện C |
| **Liên kết tĩnh** | mỗi bên nhúng bản của mình (tốn chỗ, nhưng hết xung đột) |

✅ glibc dùng cách thứ nhất, nhìn thấy được:
```text
$ readelf --dyn-syms /lib/x86_64-linux-gnu/libc.so.6 | grep realpath@
847: ... realpath@@GLIBC_2.3        ← mặc định cho code mới (@@)
848: ... realpath@GLIBC_2.2.5       ← bản cũ, giữ để binary cũ vẫn chạy (@)
```
Nhờ đó một `libc.so.6` duy nhất phục vụ được binary build từ 2005 lẫn binary build hôm nay.

### 10.2 Thứ tự link với thư viện tĩnh

⚠️ Linker duyệt **một lượt từ trái sang phải**, và một `.a` chỉ được quét để tìm những symbol **đang thiếu tại thời điểm gặp nó**.

✅
```text
$ gcc main.o libA.a libB.a libV.a -o ok && ./ok        ← ĐÚNG
  A dùng ver() = 1.0

$ gcc main.o libV.a libA.a libB.a -o bad              ← SAI thứ tự
/usr/bin/ld: libA.a(a.o): in function `a_fn':
a.c:(.text+0x9): undefined reference to `ver'
```
Khi gặp `libV.a`, chưa ai cần `ver()` nên linker bỏ qua; đến `libA.a` thì mới cần, nhưng `libV.a` đã đi qua rồi.

**Quy tắc:** *người dùng đứng trước nhà cung cấp.* Với phụ thuộc vòng:
```text
$ gcc main.o -Wl,--start-group libV.a libA.a libB.a -Wl,--end-group -o fixed && ./fixed
  A dùng ver() = 1.0
```
`--start-group`/`--end-group` bảo linker lặp lại nhóm cho tới khi không còn symbol thiếu. Tốn thời gian link, nhưng gỡ được mọi vòng.

⚠️ Với `.so` thì thứ tự **ít quan trọng hơn** vì linker động giải quyết lúc chạy — nhưng như §10.1 cho thấy, thứ tự vẫn quyết định **ai thắng**.

### 10.3 Ba mô hình quản lý dependency

| | Hệ thống (apt/yum) | Vendoring | Package manager của ngôn ngữ |
|---|---|---|---|
| Ví dụ | `libssl-dev` | copy nguồn vào repo | Conan, vcpkg, Cargo, uv |
| Ai quyết định phiên bản | distro | bạn | lockfile |
| Tái lập được | ✘ (khác distro khác phiên bản) | ✔ | ✔ với lockfile |
| Vá bảo mật | distro lo | **bạn lo** | tuỳ |
| Phù hợp | ứng dụng chạy trên một distro | firmware, thư viện phải portable | dự án hiện đại |

Đối chiếu C1.2 §7.5 và C1.3 §8.3: quy tắc **"thư viện để ràng buộc rộng, ứng dụng dùng lockfile"** áp dụng y hệt cho C/C++.

### 10.4 `pkg-config` và `find_package`

```sh
pkg-config --cflags --libs openssl
# -I/usr/include/openssl -lssl -lcrypto
gcc app.c $(pkg-config --cflags --libs openssl) -o app
```
```cmake
find_package(OpenSSL 3.0 REQUIRED)
target_link_libraries(app PRIVATE OpenSSL::SSL)   # target import: kéo cả include + flag
```
⚠️ Khi cross-compile, `pkg-config` phải trỏ vào sysroot:
```sh
export PKG_CONFIG_SYSROOT_DIR=/opt/sysroot-arm64
export PKG_CONFIG_LIBDIR=/opt/sysroot-arm64/usr/lib/pkgconfig
```
Quên bước này là cách phổ biến nhất để link nhầm thư viện x86 vào binary ARM.

### 10.5 Kiểm tra bạn thực sự phụ thuộc vào gì

```sh
ldd prog                       # .so trực tiếp + gián tiếp
readelf -d prog | grep NEEDED  # CHỈ .so khai báo trực tiếp
objdump -T prog                # symbol động
nm -D --undefined-only prog    # symbol cần từ ngoài
```
```sh
# Phiên bản glibc tối thiểu mà binary yêu cầu — quyết định nó chạy được trên distro nào
objdump -T prog | grep GLIBC_ | sed 's/.*GLIBC_\([0-9.]*\).*/\1/' | sort -uV | tail -1
```
Đây là công cụ để trả lời "vì sao binary build trên Ubuntu 24.04 không chạy trên CentOS 7": nó yêu cầu `GLIBC_2.34` mà hệ kia chỉ có `2.17`. Cách chữa: build trên distro cũ nhất cần hỗ trợ, hoặc liên kết tĩnh với musl.

## 11. Checkpoint

### 11.1 Yêu cầu

> Cross-compile một binary cho ARM từ máy x86, **chạy được trên board**, và **giải thích được từng dòng** trong linker script bạn dùng.

Tôi làm hai phần, vì "ARM" có hai nghĩa rất khác nhau:
* **Phần A — ARM64 Linux:** binary userspace, dùng linker script mặc định. Chạy thật dưới `qemu-aarch64` (user-mode emulation = tương đương chạy trên board, cùng mã máy, cùng ABI, cùng libc).
* **Phần B — Cortex-M bare metal:** linker script **tự viết**, giải thích từng dòng và kiểm chứng bằng địa chỉ thật.

### 11.2 Phần A — ARM64 Linux

```sh
sudo apt install gcc-aarch64-linux-gnu qemu-user-static
aarch64-linux-gnu-gcc -O2 sysinfo.c -o sysinfo_arm64
```
✅
```text
$ file sysinfo_arm64
sysinfo_arm64: ELF 64-bit LSB pie executable, ARM aarch64, version 1 (SYSV), dynamically linked

$ readelf -h sysinfo_arm64 | grep -E 'Class|Data|Machine|Type'
  Class:    ELF64
  Data:     2's complement, little endian
  Type:     DYN (Position-Independent Executable file)
  Machine:  AArch64

$ qemu-aarch64-static -L /usr/aarch64-linux-gnu ./sysinfo_arm64
kiến trúc     : aarch64
endian        : little
sizeof: int=4 long=8 ptr=8 ldouble=16
char có dấu   : không                 ← KHÁC x86-64 (§6.4)
align max     : 16
```
`-L /usr/aarch64-linux-gnu` chỉ cho qemu biết sysroot để tìm `ld-linux-aarch64.so.1` và `libc.so.6` của ARM.

Với CMake, dùng toolchain file ở §6.5 — cũng chạy được dưới qemu.

### 11.3 Phần B — linker script cho Cortex-M4, giải thích từng dòng

```sh
arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -Os \
  -ffunction-sections -fdata-sections -nostdlib \
  -T link.ld -Wl,--gc-sections -Wl,-Map=fw.map \
  startup.c app.c -o fw.elf
arm-none-eabi-objcopy -O binary fw.elf fw.bin
```
✅
```text
$ arm-none-eabi-size fw.elf
   text    data     bss     dec     hex  filename
    776       4    2308    3088     c10  fw.elf
$ ls -l fw.bin
780 byte           ← = text(776) + data(4).  .bss KHÔNG có trong ảnh flash (C1.4 §1.3)
```

Dưới đây là toàn bộ script, mỗi khối kèm giải thích và bằng chứng.

---

**Khối 1 — điểm vào**
```ld
ENTRY(Reset_Handler)
```
Ghi symbol nào là điểm vào vào header ELF (`e_entry`). Với Cortex-M, CPU thật **không đọc** trường này (nó đọc word[1] của bảng vector), nhưng debugger và `--gc-sections` dùng nó làm gốc để biết code nào còn sống. Thiếu dòng này, `--gc-sections` có thể xoá sạch.

---

**Khối 2 — bản đồ bộ nhớ vật lý**
```ld
MEMORY
{
  FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 512K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}
```
Khai báo các vùng nhớ **thật của chip** (tra datasheet). `0x08000000` và `0x20000000` là địa chỉ chuẩn của họ STM32F4.
Thuộc tính `r`/`w`/`x` chỉ để linker **cảnh báo** khi bạn đặt section sai chỗ (ví dụ `.data` ghi được vào vùng `rx`); nó không tạo ra bảo vệ phần cứng.
`LENGTH` là cơ chế an toàn: vượt quá thì linker báo `region FLASH overflowed by N bytes` — **fail tại build**, không phải tại lúc nạp.

---

**Khối 3 — hằng số và đỉnh stack**
```ld
_stack_size = 2K;
_estack = ORIGIN(RAM) + LENGTH(RAM);
```
Định nghĩa symbol cho code C dùng. Stack Cortex-M **mọc xuống** (C1.4 §1.1), nên giá trị nạp vào SP lúc reset là **đỉnh** RAM.
✅ Kiểm chứng: `_estack = 0x20000000 + 128K = 0x20020000`, và `nm` cho `20020000 R _estack`.

---

**Khối 4 — bảng vector**
```ld
.isr_vector : { KEEP(*(.isr_vector)) } > FLASH
```
* Đặt **đầu tiên**, vì Cortex-M đọc bảng vector tại địa chỉ 0 của flash khi reset.
* `*(.isr_vector)` = lấy section tên `.isr_vector` từ **mọi** file đầu vào.
* **`KEEP(...)` là bắt buộc.** Không code nào gọi bảng vector — phần cứng đọc trực tiếp — nên `--gc-sections` sẽ xoá nó. Thiếu `KEEP`, firmware biên dịch sạch và **không boot**.
* `> FLASH` = đặt vào vùng FLASH.

✅ Bằng chứng, 8 word đầu của `fw.bin`:
```text
$ od -A x -t x4 -N 32 fw.bin
000000  20020000  08000279  08000275  08000275
000010  00000000  00000000  00000000  00000000
```
```
word[0] = 0x20020000 = _estack                ← SP ban đầu
word[1] = 0x08000279 = Reset_Handler | 1      ← bit 0 = 1 báo chế độ Thumb
word[2] = 0x08000275 = Default_Handler | 1    ← NMI
word[3] = 0x08000275                          ← HardFault
```
✅ `nm` cho `08000278 T Reset_Handler`, và `0x08000278 | 1 = 0x08000279`. Khớp chính xác.

---

**Khối 5 — code và hằng số**
```ld
.text : {
  . = ALIGN(4);
  *(.text) *(.text*)
  *(.rodata) *(.rodata*)
  *(.glue_7) *(.glue_7t)
  KEEP(*(.init)) KEEP(*(.fini))
  . = ALIGN(4);
  _etext = .;
} > FLASH
```
* `.` là **location counter** — địa chỉ hiện tại. `. = ALIGN(4)` đẩy nó lên bội của 4 (ARM cần lệnh căn 4; C1.4 §4).
* `*(.text*)` với dấu `*` ở cuối gom cả `.text.main`, `.text.foo` do `-ffunction-sections` sinh ra. **Thiếu dấu sao này là lỗi hay gặp nhất** khi bật `-ffunction-sections`: linker im lặng bỏ rơi các section đó, hoặc báo `orphan section`.
* `.rodata` để cùng FLASH vì hằng số không cần ở RAM.
* `.glue_7`/`.glue_7t` là code chuyển đổi ARM ↔ Thumb do compiler sinh; Cortex-M chỉ có Thumb nên thường rỗng, nhưng để cho an toàn.
* `_etext = .;` ghi lại địa chỉ kết thúc, dùng để kiểm tra bố cục.

✅ `nm` cho `08000300 T _etext`.

---

**Khối 6 — bảng unwind của ARM**
```ld
.ARM.extab : { *(.ARM.extab* .gnu.linkonce.armextab.*) } > FLASH
.ARM       : { __exidx_start = .; *(.ARM.exidx*) __exidx_end = .; } > FLASH
```
Bảng exception unwinding của ARM EABI (dùng cho C++ exception và backtrace). Với C thuần và `-fno-exceptions` thì gần như rỗng, nhưng nếu không khai báo, linker sẽ báo `orphan section .ARM.exidx` hoặc đặt nó vào chỗ không mong muốn.
`__exidx_start`/`__exidx_end` là tên mà runtime của newlib/libgcc tìm.

---

**Khối 7 — hai địa chỉ của `.data`** (phần quan trọng nhất)
```ld
_sidata = LOADADDR(.data);

.data : {
  . = ALIGN(4);
  _sdata = .;
  *(.data) *(.data*)
  . = ALIGN(4);
  _edata = .;
} > RAM AT > FLASH
```
`> RAM AT > FLASH` là cú pháp then chốt:
```
> RAM       VMA (Virtual Memory Address)  = nơi code CHẠY  sẽ tìm biến  → RAM
AT > FLASH  LMA (Load Memory Address)     = nơi dữ liệu ĐƯỢC NẠP        → FLASH
```
Biến khởi tạo (`int g = 0x12345678;`) phải **có giá trị trong flash** (vì RAM mất nội dung khi tắt nguồn) nhưng **phải ghi được ở RAM** khi chạy. Nên nó tồn tại ở **hai địa chỉ**, và `Reset_Handler` copy từ LMA sang VMA:
```c
uint32_t *src = &_sidata, *dst = &_sdata;
while (dst < &_edata) *dst++ = *src++;
```
`LOADADDR(.data)` lấy LMA để code C biết copy từ đâu.

✅ Bằng chứng trực tiếp:
```text
$ arm-none-eabi-objdump -h fw.elf
  Name           Size      VMA        LMA
  .isr_vector    0000009c  08000000   08000000
  .text          00000264  0800009c   0800009c
  .data          00000004  20000000   08000308     ← HAI địa chỉ khác nhau!
  .bss           00000100  20000004   0800030c
```
```text
_sidata = 0x08000308   nằm trong FLASH? True
_sdata  = 0x20000000   nằm trong RAM?   True
```

---

**Khối 8 — `.bss`**
```ld
.bss : {
  . = ALIGN(4);
  _sbss = .;
  __bss_start__ = _sbss;
  *(.bss) *(.bss*) *(COMMON)
  . = ALIGN(4);
  _ebss = .;
  __bss_end__ = _ebss;
} > RAM
```
* Chỉ `> RAM`, **không** `AT > FLASH`: biến bằng 0 không cần lưu giá trị trong flash (C1.4 §1.3). Đó là lý do `fw.bin` chỉ 780 byte trong khi `.bss` là 2.308 byte.
* `*(COMMON)` gom biến common (C1.1 §2.7). Với `-fno-common` (mặc định từ GCC 10) thì rỗng, nhưng giữ để tương thích.
* `__bss_start__`/`__bss_end__` là tên newlib dùng; `_sbss`/`_ebss` là tên startup code của ta dùng. Khai báo cả hai để không phải sửa code khi đổi thư viện.
* `Reset_Handler` xoá vùng này về 0 — chuẩn C yêu cầu biến static không khởi tạo phải bằng 0.

✅ `_sbss = 0x20000004`, `_ebss = 0x20000104` → **256 byte** = `int g_zero[64]`. Khớp.

---

**Khối 9 — chỗ cho stack**
```ld
._user_heap_stack : {
  . = ALIGN(8);
  . = . + _stack_size;
  . = ALIGN(8);
} > RAM
```
Không chứa dữ liệu, chỉ **đẩy location counter** đi 2 KB. Mục đích: nếu `.bss` + stack vượt quá RAM, linker báo lỗi **tại build** thay vì để stack đè lên `.bss` lúc chạy (C1.4 §9.2 — đây là cách biến phân tích stack thành ràng buộc được linker kiểm tra).
`ALIGN(8)` vì AAPCS yêu cầu stack căn 8 byte.

✅ `objdump -h` cho `._user_heap_stack size=00000804 VMA=20000104` — đúng 2.052 byte (2K + căn chỉnh) nằm ngay sau `.bss`.

---

**Khối 10 — loại bỏ và phần siêu dữ liệu**
```ld
/DISCARD/ : { *(.comment) *(.note*) libc.a(*) libgcc.a(*) }
.ARM.attributes 0 : { *(.ARM.attributes) }
```
* `/DISCARD/` vứt hẳn section không cần: chuỗi phiên bản compiler, note. Với `-nostdlib` thì hai dòng `libc.a`/`libgcc.a` là thừa, nhưng giữ lại nếu bạn có lúc dùng newlib mà không muốn kéo theo gì.
* `.ARM.attributes` với địa chỉ `0` nghĩa là section không được nạp — nó chỉ mô tả ABI (phiên bản ARM, FPU, endian) để linker từ chối trộn object không tương thích.

✅ `objdump -h` cho `.ARM.attributes VMA=00000000 LMA=00000000` — xác nhận không nạp.

### 11.4 Bản đồ bộ nhớ cuối cùng — đã kiểm chứng

```
FLASH 0x08000000 ┌──────────────────────┐
                 │ .isr_vector    156 B │  ← CPU đọc word[0],[1] khi reset
      0x0800009c ├──────────────────────┤
                 │ .text          612 B │  ← code + .rodata
      0x08000300 ├── _etext ────────────┤
                 │ .ARM             8 B │
      0x08000308 ├── _sidata ───────────┤
                 │ ảnh gốc .data    4 B │  ← LMA, Reset_Handler copy đi
      0x0800030c └──────────────────────┘  ← hết fw.bin (780 byte)

RAM   0x20000000 ┌── _sdata ────────────┐
                 │ .data            4 B │  ← VMA
      0x20000004 ├── _edata/_sbss ──────┤
                 │ .bss           256 B │  ← Reset_Handler xoá về 0
      0x20000104 ├── _ebss ─────────────┤
                 │ stack        2.052 B │
      0x20000908 ├──────────────────────┤
                 │ (còn trống 126 KB)   │
      0x20020000 └── _estack ───────────┘  ← SP ban đầu, mọc XUỐNG ↓
```
Ngân sách: FLASH **780 / 524.288 byte** (0,15%), RAM **2.312 / 131.072 byte** (1,8%).

### 11.5 Tự chấm

| Tiêu chí | Đạt khi |
|---|---|
| Binary **đúng kiến trúc** | `file` và `readelf -h` cho đúng `Machine` |
| **Chạy được** | qemu-user, qemu-system, hoặc board thật — có output |
| Không lẫn thư viện host | `readelf -d` không NEEDED thư viện x86; `PKG_CONFIG_SYSROOT_DIR` đúng |
| **Giải thích từng dòng** linker script | mỗi khối nêu được: nó làm gì, xoá đi thì hỏng thế nào |
| Có **bằng chứng số** | mỗi symbol quan trọng đối chiếu với `nm`/`objdump -h` |
| Hiểu **VMA vs LMA** | chỉ ra được `.data` có hai địa chỉ và ai copy giữa chúng |
| Hiểu **`KEEP`** | giải thích được vì sao thiếu nó thì firmware không boot |
| Ngân sách bộ nhớ | báo được FLASH/RAM đã dùng bao nhiêu phần trăm |
| Kiểm chứng **hành vi khác nhau giữa hai kiến trúc** | ví dụ `char` có dấu (§6.4) |

### 11.6 Mở rộng

1. **Chạy trên board thật:** nạp `fw.bin` bằng `probe-rs` hoặc `st-flash`, xem output qua UART.
2. **Chạy firmware trong QEMU system:** `qemu-system-arm -M netduinoplus2 -kernel fw.elf -nographic -semihosting`.
3. **Thêm `.noinit`:** section không bị `Reset_Handler` xoá, sống qua reset mềm (C1.4 §7.3).
4. **Thêm `ASSERT`:** `ASSERT(_ebss + _stack_size <= ORIGIN(RAM) + LENGTH(RAM), "RAM overflow")` — biến ngân sách thành lỗi link.
5. **Ghép với C1.4 §9.2:** chạy `stackscan.py` trên `fw.elf` và chứng minh 2 KB stack là đủ.
6. **So sánh `-Os` với `-O2`** trên chính firmware này; đo `.text` và số chu kỳ.
7. **Cross-compile cho RISC-V** (`riscv64-linux-gnu-gcc`) và so bảng `sizeof` với ARM và x86.

## Phụ lục B — Bản đồ lệnh chẩn đoán build

### B.1 "Nó biên dịch ra cái gì?"
```sh
gcc -E f.c | grep -v '^#'          # sau preprocess
gcc -S -masm=intel -O2 f.c -o -    # assembly
gcc -save-temps -c f.c             # giữ .i .s .o
gcc -v -c f.c 2>&1 | head -30      # mọi lệnh con
gcc -dM -E - < /dev/null           # macro định nghĩa sẵn
gcc -Q --help=optimizers -O2 | grep enabled | head   # -O2 bật cờ nào
```

### B.2 "Trong file này có gì?"
```sh
file prog                  # loại, kiến trúc, tĩnh/động, stripped chưa
size -A prog               # từng section
readelf -h prog            # header ELF
readelf -S prog            # section
readelf -l prog            # segment (cái loader nạp)
readelf -d prog            # dynamic: NEEDED, SONAME, RPATH
readelf -n prog            # note: Build ID
nm -C prog                 # symbol (demangle C++)
nm -D prog                 # symbol động
nm --size-sort -S prog | tail -20    # symbol to nhất
objdump -d -M intel prog   # disassembly
objdump -r f.o             # relocation
objdump -h prog            # section + VMA/LMA
strings prog | less        # chuỗi nhúng
```

### B.3 "Vì sao không link được?"
```sh
nm f.o | grep ' U '                     # symbol nào đang thiếu
nm libfoo.a | grep ' T mysym'           # thư viện nào có nó
gcc ... -Wl,--verbose 2>&1 | head -40   # linker script mặc định
gcc ... -Wl,-Map=out.map                # rồi đọc map
gcc ... -Wl,--trace-symbol=mysym        # theo dấu một symbol
c++filt _Z3foov                         # demangle tên C++
```

### B.4 "Vì sao không chạy được?"
```sh
ldd prog                          # .so nào, ở đâu, thiếu cái nào
LD_DEBUG=libs ./prog              # nhật ký tìm .so
LD_DEBUG=bindings ./prog          # symbol bind vào đâu
LD_DEBUG=help ./prog
objdump -T prog | grep GLIBC_ | sed 's/.*GLIBC_\([0-9.]*\).*/\1/' | sort -uV | tail -1
readelf -d prog | grep -E 'NEEDED|RPATH|RUNPATH'
```

### B.5 "Cross-compile có đúng không?"
```sh
CC=aarch64-linux-gnu-gcc
$CC -dumpmachine                   # triple
$CC -print-sysroot
$CC -print-search-dirs
echo | $CC -E -Wp,-v -             # thứ tự tìm header
file out && readelf -h out | grep Machine
qemu-aarch64-static -L /usr/aarch64-linux-gnu ./out
```

### B.6 "Firmware chiếm bao nhiêu?"
```sh
arm-none-eabi-size fw.elf
arm-none-eabi-size -A fw.elf
arm-none-eabi-nm --size-sort -S fw.elf | tail -20
arm-none-eabi-objdump -h fw.elf            # VMA vs LMA
grep -A20 'Memory Configuration' fw.map
gcc ... -Wl,--print-memory-usage
```

## Tổng kết: mười điều phải mang theo

1. **Bốn giai đoạn đều dừng lại và mở ra xem được.** `-E`, `-S`, `-c`, rồi link. 🔬 13 dòng nguồn thành 826 dòng sau preprocess — nếu chưa từng nhìn, bạn đang tin chứ không biết.
2. **Linker chỉ làm ba việc:** gom section, giải quyết symbol, ghi địa chỉ. 🔬 `call 15 <main+0x15>` trước link thành `call 1187 <helper>` sau link — đó là toàn bộ "relocation".
3. **`undefined reference` và `multiple definition` là hai mặt của linkage** (C1.1 §2.5): mỗi symbol external cần đúng một định nghĩa.
4. **Thiếu phụ thuộc header là bug tệ nhất của build system** vì nó tạo binary lai hai phiên bản mã nguồn. `-MMD -MP` + `-include $(DEP)` là ba dòng chữa dứt điểm.
5. **`-O0` → `-O1` là bước nhảy lớn nhất** (🔬 2,4–4×); `-O1` → `-O2` gần như không đổi; `-O3` đáng giá đúng khi có vòng lặp vector hoá được (🔬 `saxpy` nhanh 3,1× nhưng `.text` +29%).
6. ⚠️ **`-Os` có thể chậm hơn `-O0`.** 🔬 `sum_mod`: 109,4 ms ở `-Os` so với 75,4 ms ở `-O0`. Luôn đo.
7. **`-O2 -flto` cho tốc độ của `-O3` với kích thước của `-O2`** 🔬 nhờ inline xuyên translation unit.
8. **`-g` không làm chương trình chậm.** Section debug không được nạp vào RAM. Build release có `-g`, strip khi ship, giữ file symbol riêng.
9. **Symbol interposition là cái bẫy im lặng của `.so`.** 🔬 Chỉ đổi thứ tự `-lA -lB` thành `-lB -lA` là libB chạy với `ver()` mà nó chưa từng được test cùng — không có thông báo nào.
10. **Cross-compile thành công ≠ chạy đúng.** 🔬 Cùng một mã nguồn: `char` **có dấu** trên x86-64, **không dấu** trên aarch64. Luôn chạy thử trên đích hoặc emulator.
