> **Mục tiêu của tài liệu.** Chuyển bạn từ "thuộc vài lệnh git và sợ phần còn lại" sang "hiểu git là gì bên dưới, nên không có thao tác nào làm mất dữ liệu mà không cứu được".

> Chín tài liệu trước là về viết code đúng. Tài liệu này là về **làm việc cùng người khác trên cùng một khối code** mà không phá của nhau — và về công cụ tìm lỗi mạnh nhất mà không cần đọc code: lịch sử.

> **Điều kiện hoàn thành:** vượt Checkpoint §10 — dùng `bisect` tìm được commit gây regression trong repo **≥ 500 commit**, và rebase sạch một nhánh **10 commit lộn xộn thành 3 commit nguyên tử**.

## 0. Cách dùng tài liệu

### 0.1 Nguyên tắc

Git có tiếng là khó vì người ta học **lệnh** trước khi học **mô hình**. Có hàng trăm lệnh, nhưng chỉ có bốn loại đối tượng và một cấu trúc dữ liệu. Hiểu cấu trúc đó thì mọi lệnh chỉ là thao tác trên nó.

> **Quy tắc an toàn quan trọng nhất của git:** một commit đã từng tồn tại thì gần như không bao giờ mất — trong ít nhất 30 ngày. Nếu bạn "làm mất" gì đó, nó vẫn ở trong kho, chỉ là không còn tên nào trỏ tới. §4 cho thấy cách tìm lại.

### 0.2 Môi trường

🔬 Mọi output chạy thật trên **git 2.43.0**, Linux. Ký hiệu: ✅ output thật · ⚠️ bẫy. *Quy ước trong khối output: chú thích sau dấu `←` là do tôi thêm; nhãn tiếng Việt mà script in ra (vốn không dấu) được thêm dấu cho dễ đọc. Mọi con số, mã lỗi và thông điệp của công cụ được giữ nguyên văn.*

## 1. Mô hình đối tượng — git là một DAG

### 1.1 Bốn loại đối tượng

```
BLOB    nội dung một file         (KHÔNG có tên, KHÔNG có quyền — chỉ byte)
TREE    một thư mục                (danh sách: quyền, loại, sha, tên)
COMMIT  một ảnh chụp               (trỏ tới MỘT tree + các commit cha + tác giả + thông điệp)
TAG     một nhãn có chú thích      (trỏ tới một object + người ký + thông điệp)

REF     KHÔNG phải object: chỉ là một file chứa sha  (branch, tag nhẹ, HEAD)
```
Mọi object được định danh bằng **SHA-1 của chính nội dung nó** (git 2.x hỗ trợ SHA-256 tuỳ chọn). Đó là **content-addressable storage**.

### 1.2 Tính SHA bằng tay

✅ Blob không phải hash của file, mà là hash của `"blob <kích thước>\0<nội dung>"`:
```text
$ printf 'xin chao\n' > a.txt
$ git hash-object a.txt
1a496688e748cc62548804021321e46386ea65df

$ printf 'blob 9\0xin chao\n' | sha1sum
1a496688e748cc62548804021321e46386ea65df          ← KHỚP
```
Hệ quả: **cùng nội dung → cùng SHA, ở mọi máy, mọi repo, mọi thời điểm.** Đó là lý do git kiểm tra toàn vẹn được, và là lý do nó hiệu quả.

### 1.3 Tree: thư mục là danh sách

✅
```text
$ git cat-file -p HEAD^{tree}
100644 blob 1a496688e748cc62548804021321e46386ea65df	a.txt
040000 tree 475b6eef4f365fde123fe23b8dabe9514dd9140d	src

$ git cat-file -p HEAD:src
100644 blob 1a496688e748cc62548804021321e46386ea65df	b.txt      ← CÙNG sha với a.txt
100644 blob b917a726c93f902e43291d9009d6488385133b67	main.py
```
`a.txt` và `src/b.txt` có cùng nội dung nên dùng **chung một blob**. Git lưu nó một lần.

✅ Đếm object để xác nhận:
```text
$ git count-objects -v
count: 7
```
= 1 blob chung (`a.txt`/`b.txt`) + 1 blob `main.py` + 2 tree gốc (mỗi commit một) + 1 tree `src` + 2 commit. Đúng 7.

### 1.4 Commit

✅
```text
$ git cat-file -p HEAD
tree a20798d574a9f4f2dada81f88e229122663bcf80
parent 3515acba92373a471c0b4e2276f9eea0312e68ea
author An <an@vd.vn> 1767261600 +0000
committer An <an@vd.vn> 1767261600 +0000

Them src/
```
Năm dòng, đó là toàn bộ một commit. Ba điều quan trọng:
1. Commit trỏ tới **một tree** — một ảnh chụp **đầy đủ**, không phải một diff. (Git tính diff khi bạn hỏi, và nén bằng delta trong packfile, nhưng mô hình logic là ảnh chụp.)
2. Commit trỏ tới **cha**. Commit merge có hai cha; commit đầu tiên không có cha.
3. SHA của commit phụ thuộc vào **mọi thứ ở trên** — kể cả SHA của cha. Đổi bất cứ gì, dù chỉ thông điệp hay thời gian, là ra **commit khác**.

### 1.5 Ref chỉ là file

✅
```text
$ cat .git/HEAD
ref: refs/heads/main                                   ← HEAD trỏ tới một branch
$ cat .git/refs/heads/main
023504bb98280cb2d578b50260f0857f8b8f0adb               ← branch trỏ tới một commit
$ git rev-parse HEAD
023504bb98280cb2d578b50260f0857f8b8f0adb
```
> **Một branch là một file 41 byte chứa một SHA.** Tạo branch là tạo một file. Xoá branch là xoá file đó — **commit vẫn còn nguyên**.
>
> "Detached HEAD" chỉ nghĩa là `.git/HEAD` chứa thẳng một SHA thay vì `ref: refs/heads/...`.

### 1.6 DAG

```
        A ── B ── C ── F          ← main
                  \   /
                   D ── E          ← feature (đã merge vào F)
```
* Mỗi mũi tên đi **từ con về cha**. Commit biết cha của nó, không biết con.
* **Có hướng, không chu trình** (Directed Acyclic Graph): không thể có chu trình vì SHA của con phụ thuộc SHA của cha.
* Branch và tag là **nhãn** dán lên các đỉnh.

Hệ quả thực dụng của mô hình này:

| Câu hỏi | Trả lời từ mô hình |
|---|---|
| Vì sao commit "bất biến"? | SHA phụ thuộc nội dung; đổi nội dung = commit mới |
| Vì sao rebase "viết lại lịch sử"? | nó tạo commit **mới** với cha mới, rồi dời nhãn branch |
| Vì sao xoá branch không mất commit? | chỉ xoá nhãn; object vẫn trong kho |
| `A..B` nghĩa là gì? | commit đến được từ B nhưng **không** đến được từ A |
| `merge-base` là gì? | tổ tiên chung gần nhất trong DAG |
| Vì sao clone nhanh dù repo lớn? | object trùng lặp chỉ lưu một lần; nén delta |

### 1.7 Ba khu vực

```
working tree  ──git add──▶  index (staging)  ──git commit──▶  repository
     ◀──git restore──            ◀──git restore --staged──
```
**Index** là một tree "đang soạn": `git add` ghi blob vào kho và cập nhật index; `git commit` biến index thành một tree object. Index là thứ cho phép commit **một phần** thay đổi (`git add -p`) — công cụ chính để tạo commit nguyên tử (§6).

## 2. Branch, merge, rebase

### 2.1 Tình huống xuất phát

✅
```text
$ git log --graph --oneline --all
* F2
* F1
| * M3
|/
* M2
* M1
merge-base = M2
```
`main` và `feature` rẽ nhánh tại M2. Có ba cách đưa `feature` vào `main`.

### 2.2 Merge — giữ lịch sử thật

✅
```text
$ git merge --no-ff feature -m "Merge feature"
*   Merge feature
|\
| * F2
| * F1
* | M3
|/
* M2
* M1

số cha của commit merge: 2
```
Tạo **một commit mới có hai cha**. Không commit cũ nào bị đổi.

### 2.3 Rebase — viết lại cho thẳng

✅
```text
$ git rebase main           (đang ở feature)
* F2
* F1
* M3
* M2
* M1

SHA của F1 trước: 099d916   sau: cb02208    ← KHÁC: đây là commit MỚI
```
Rebase **không di chuyển** commit. Nó **tạo bản sao** của F1, F2 với cha mới là M3 (nên SHA khác, theo §1.4), rồi dời nhãn `feature` sang bản sao. Bản gốc vẫn còn trong kho (§4).

### 2.4 Fast-forward — không có gì để hợp nhất

✅
```text
$ git merge --ff-only f_rebase
m_ff: M3 -> F2, không tạo commit mới
F2 F1 M3 M2 M1
```
Khi đích là tổ tiên trực tiếp của nguồn, merge chỉ **dời nhãn**. Không có commit merge.

### 2.5 Chọn cái nào

| | Merge | Rebase | Squash merge |
|---|---|---|---|
| Lịch sử | thật, có nhánh | thẳng, như viết tuần tự | một commit cho cả nhánh |
| Sửa commit cũ | ✘ | ✔ (tạo mới) | ✔ (gộp) |
| An toàn trên nhánh chia sẻ | **✔** | **✘** | ✔ (trên nhánh đích) |
| `bisect` | chạy được, phức tạp hơn | **dễ nhất** | mất chi tiết bên trong |
| `revert` cả tính năng | `revert -m 1 <merge>` | revert từng commit | **một lệnh** |
| Xung đột | giải một lần | giải **từng commit** | giải một lần |

**Quy tắc vàng — học thuộc:**
> **Đừng bao giờ rebase commit đã đẩy lên nhánh người khác đang dùng.**

Lý do nằm ngay trong §2.3: rebase tạo commit mới. Người khác vẫn giữ commit cũ; khi họ pull, git thấy hai lịch sử song song và họ nhận về các commit trùng lặp nội dung nhưng khác SHA.

**Quy trình thực dụng phổ biến nhất:**
```
1. Nhánh cá nhân: rebase thoải mái (dọn dẹp, cập nhật theo main)
2. Trước khi mở PR: rebase -i để có commit nguyên tử (§6, §10.2)
3. Hợp nhất vào main: merge --no-ff hoặc squash, theo quy ước nhóm
4. Nhánh đã chia sẻ: CHỈ merge
```
```sh
git pull --rebase                           # thay cho pull (merge) mặc định trên nhánh cá nhân
git config --global pull.rebase true
git push --force-with-lease                 # ⚠️ KHÔNG dùng --force trần
```
`--force-with-lease` từ chối ghi đè nếu nhánh trên server đã có commit mà bạn chưa thấy — nó ngăn bạn xoá mất công việc của đồng nghiệp.

## 3. `bisect`

Cơ bản đã có ở C1.9 §11. Mục này tập trung vào ba cái bẫy đã gặp thật khi dựng Checkpoint — cả ba làm bisect **trả về sai commit mà không báo lỗi**.

### 3.1 Script kiểm tra — mã thoát là hợp đồng

```
exit 0         → commit TỐT
exit 1..124    → commit XẤU
exit 125       → BỎ QUA (không build/không kiểm tra được)
exit ≥ 128     → dừng bisect
```

### 3.2 Ba bẫy — đo thật

✅ Repo nhỏ 21 commit: **c10** không build được (lỗi cú pháp, sửa ở c11), **c15** là hồi quy thật. Ba script khác nhau:

| Script | Kết quả | Đúng? |
|---|---|---|
| `naive.sh` — chỉ chạy test | **c10** | ✘ báo commit hỏng build là thủ phạm |
| `good.sh` — có `exit 125` | **c01** | ✘ bị bytecode cũ đầu độc |
| `good2.sh` — `exit 125` + xoá cache | **c15** | ✔ |

**Bẫy 1 — commit không build được bị tính là "xấu".**
```sh
#!/bin/sh
python3 t.py             # lỗi cú pháp -> exit 1 -> "xấu" -> bisect dừng ở c10
```
Sửa: kiểm tra build trước, trả **125** nếu không được.

**Bẫy 2 — artifact cũ đầu độc kết quả.**
Bản `good.sh` có `exit 125` nhưng vẫn ra **c01** — sai hoàn toàn. Nguyên nhân: file `__pycache__/*.pyc`. Python kiểm tra pyc còn hợp lệ không bằng **mtime (theo giây) + kích thước** của file nguồn. Ở đây `return 1` và `return 2` có **cùng kích thước** (18 byte), và bisect checkout nhanh nên nhiều lần rơi vào **cùng một giây** → Python dùng lại bytecode của commit **trước**.
```sh
#!/bin/sh
rm -rf __pycache__                                              # xoá artifact cũ
python3 -c "import ast; ast.parse(open('m.py').read())" || exit 125
PYTHONDONTWRITEBYTECODE=1 python3 t.py                          # không ghi cache mới
```
> Đây là bản của bẫy C1.7 §2.2 (thiếu phụ thuộc header → binary lai hai phiên bản). **Mọi hệ thống build tăng dần đều có thể đầu độc bisect**: `.o` cũ, `node_modules`, `target/` của Rust, `.pyc`. Script bisect phải bắt đầu từ trạng thái sạch, hoặc build thật sự phụ thuộc đúng nội dung.

**Bẫy 3 — script đo của chính tôi.**
Khi đo, tôi viết `git bisect reset -q`. Lệnh đó **không hợp lệ**:
```text
$ git bisect reset -q
error: '-q' is not a valid commit
```
Bisect không được reset, HEAD kẹt ở commit cũ, và lần bisect sau bắt đầu từ **sai chỗ**. Kết quả đo trôi dần: c10, c09, c08, c07… mỗi lần lùi một commit. Chỉ khi thấy mẫu hình đó mới nhận ra lỗi nằm ở công cụ đo, không phải ở repo.
> Bài học chung: khi kết quả đo **thay đổi một cách có quy luật giữa các lần chạy**, nghi ngờ **trạng thái rò rỉ** giữa các lần chạy trước khi nghi ngờ đối tượng đo.

### 3.3 Khi không tự động hoá được

```sh
git bisect start
git bisect bad                    # HEAD xấu
git bisect good v2.3.0            # tag này tốt
# git checkout một commit ở giữa; bạn tự kiểm tra rồi báo:
git bisect good    # hoặc: git bisect bad   hoặc: git bisect skip
# ... lặp lại ~log2(N) lần ...
git bisect reset
```
```sh
git bisect start --first-parent   # chỉ đi trên nhánh chính, bỏ qua commit trong nhánh merge
git bisect terms --term-old=nhanh --term-new=cham     # bisect cho thay đổi không phải "lỗi"
```

## 4. `reflog` và phục hồi sau thảm họa

### 4.1 Reflog là gì

**Reflog** là nhật ký **cục bộ** ghi lại mỗi lần một ref (HEAD, branch) di chuyển. Nó không được đẩy lên server, và mặc định giữ **90 ngày** cho commit còn đến được, **30 ngày** cho commit không còn đến được.

✅
```text
$ git reflog
1f170c6 HEAD@{0} reset: moving to HEAD~2
4aa0643 HEAD@{1} commit: C4 quan trong
0776a55 HEAD@{2} commit: C3 quan trong
1f170c6 HEAD@{3} commit: C2
```
`HEAD@{n}` nghĩa là "HEAD **n bước di chuyển trước**" — không phải "n commit trước".

### 4.2 Năm thảm họa — và cách cứu, đã chạy thật

**Thảm họa 1: `reset --hard` làm mất commit**
```text
$ git reset --hard HEAD~2
sau reset: C2 C1
$ git reset --hard HEAD@{1}
phục hồi: C4 C3 C2 C1            ← về đúng trạng thái trước
```

**Thảm họa 2: xoá nhầm branch chưa merge**
```text
$ git branch -D thu-nghiem
Deleted branch thu-nghiem (was 0ef810a).     ← git IN RA sha ngay trong thông báo
$ git branch thu-nghiem 0ef810a
phục hồi: T2 T1
```
Không kịp nhìn thông báo thì tìm trong `git reflog`.

**Thảm họa 3: rebase hỏng (xung đột rối, kết quả sai)**
```text
$ git rebase main             # ... kết quả không như ý
$ git reset --hard ORIG_HEAD
→ KHỚP chính xác bản trước rebase
```
`ORIG_HEAD` được đặt bởi mọi lệnh "nguy hiểm" (`rebase`, `reset`, `merge`, `am`). Nếu đã làm thêm thao tác khác, dùng reflog:
```text
63c1383 HEAD@{1} rebase (start): checkout main
8492f27 HEAD@{2} checkout: moving from main to thu-nghiem     ← trạng thái trước rebase
```
Đang dở rebase thì đơn giản hơn: `git rebase --abort`.

**Thảm họa 4: commit ở detached HEAD rồi chuyển đi**
✅ Git cảnh báo rất rõ — và cho sẵn lệnh cứu:
```text
Warning: you are leaving 1 commit behind, not connected to
any of your branches:

  8a67a5b D1 viết lúc detached

If you want to keep it by creating a new branch, this may be a good time
to do so with:

 git branch <new-branch-name> 8a67a5b
```
Bỏ qua cảnh báo thì vẫn tìm được:
```text
$ git fsck --lost-found
dangling commit 8a67a5bf97ef315e2e5031932aa04e59224258f9
$ git reflog | grep D1
8a67a5b commit: D1 viết lúc detached
```

**Thảm họa 5: `stash drop` nhầm**
Stash **không** có reflog sau khi drop. Nhưng:
```text
$ git stash drop
Dropped refs/stash@{0} (f4e75305bd61dac4614bc1a11912fe49a336fb89)   ← sha ngay đây

$ git fsck --no-reflog | grep 'dangling commit'
f4e7530  WIP on (no branch): 9ffa170 D1 viết lúc detached           ← tìm lại được
$ git stash apply f4e7530
→ nội dung đã quay lại
```

### 4.3 Cái gì **thật sự** mất được

| Tình huống | Cứu được? |
|---|---|
| Commit đã từng tạo | ✔ reflog / fsck (≥ 30 ngày) |
| File đã `git add` nhưng chưa commit | ✔ `git fsck --lost-found` (blob lơ lửng) |
| Thay đổi **chưa bao giờ `git add`** rồi `reset --hard` / `checkout .` | **✘ MẤT HẲN** — git chưa từng thấy nó |
| Sau `git gc --prune=now` + hết hạn reflog | ✘ |
| Repo bị xoá cả thư mục `.git` | ✘ (trừ khi có bản trên server) |

> **Quy tắc thực dụng:** trước một thao tác bạn không chắc, **commit hoặc stash mọi thứ**. Một thay đổi đã vào kho thì cứu được; thay đổi chỉ nằm trong working tree thì không.
>
> Và: `git reset --hard` cùng `git checkout -- <file>` / `git restore <file>` là **hai lệnh duy nhất** thường gặp xoá được dữ liệu không cứu lại được.

### 4.4 Lưới an toàn trước thao tác lớn

```sh
git tag backup/truoc-rebase                   # một nhãn, miễn phí, xoá đi khi xong
git branch backup-$(date +%s)
git stash push -u -m "an toan"                # -u gồm cả file chưa track
```

## 5. Giải quyết xung đột mà không mất thay đổi

### 5.1 Xung đột là gì

Xung đột xảy ra khi **hai phía cùng sửa một vùng** so với **tổ tiên chung** (merge-base, §1.6). Git không đoán được ý định, nên dừng lại hỏi.

### 5.2 Bật `zdiff3` — thay đổi cấu hình giá trị nhất

✅ Mặc định, git chỉ cho bạn thấy hai phía:
```text
<<<<<<< HEAD
TIMEOUT = 45  # theo SLA
=======
TIMEOUT = 60
>>>>>>> feature
```
Bạn không biết **ai đã đổi cái gì**. Có phải `main` đổi 60 → 45? Hay `feature` đổi 45 → 60? Hay cả hai cùng đổi từ một giá trị khác?

✅ Với `zdiff3`, git cho thêm **bản gốc**:
```text
<<<<<<< HEAD
TIMEOUT = 45  # theo SLA
||||||| 0b01b1f
TIMEOUT = 30                  ← BẢN GỐC
=======
TIMEOUT = 60
>>>>>>> feature
```
Giờ đọc được ngay: gốc là 30, **cả hai phía đều sửa**, một phía thành 45 vì SLA, phía kia thành 60. Đây là xung đột thật về **ý định**, cần hỏi người viết — không phải chọn đại một bên.
```sh
git config --global merge.conflictStyle zdiff3
```

### 5.3 Ba phiên bản nằm sẵn trong index

✅ Khi đang xung đột, index giữ **cả ba** phiên bản:
```text
$ git show :1:cfg.py | head -1      # base   (tổ tiên chung)
TIMEOUT = 30
$ git show :2:cfg.py | head -1      # ours   (HEAD)
TIMEOUT = 45  # theo SLA
$ git show :3:cfg.py | head -1      # theirs (nhánh đang merge vào)
TIMEOUT = 60
```
Không phiên bản nào mất, dù file trong working tree đang bị bạn sửa dở.

### 5.4 Lỡ tay sửa hỏng file đang xung đột

✅
```text
$ echo "HONG HET" > cfg.py          # xoá sạch cả dấu xung đột
$ git checkout -m cfg.py            # tạo lại dấu xung đột từ index
-> dấu xung đột đã quay lại (1 khối)
```
Đây là lệnh ít người biết nhất và cứu được nhiều nhất trong lúc giải xung đột.

### 5.5 Quy trình an toàn

```sh
git status                       # UU = cả hai phía sửa
git diff                         # chỉ phần xung đột, dạng combined
git log --merge -p <file>        # các commit ở CẢ HAI phía đã chạm vào file này
git checkout --ours   <file>     # lấy nguyên bản của mình (CẨN THẬN: mất phía kia)
git checkout --theirs <file>     # lấy nguyên bản phía kia
git mergetool                    # công cụ 3 cột (vimdiff, meld, VS Code)
# ... sửa ...
git add <file>                   # đánh dấu đã giải
git merge --continue             # hoặc: git rebase --continue
git merge --abort                # bỏ, quay về trước khi merge
```
⚠️ **Đảo nghĩa `ours`/`theirs` khi rebase.** Trong rebase, git đang phát lại commit **của bạn** lên trên nhánh đích, nên `ours` là **nhánh đích** và `theirs` là **commit của bạn** — ngược với trực giác. Nhầm chỗ này là cách phổ biến nhất để vô tình vứt đi công việc của mình.

⚠️ **Sau khi giải, phải chạy test.** Hai thay đổi đúng riêng lẻ có thể sai khi ghép lại, kể cả khi git merge **không** báo xung đột nào (xung đột ngữ nghĩa: một bên đổi tên hàm, bên kia thêm lời gọi tên cũ).

### 5.6 `rerere` — nhớ cách giải

**Re**use **re**corded **re**solution: git ghi lại cách bạn giải một xung đột, lần sau gặp đúng xung đột đó thì tự áp dụng.

✅
```text
$ git config rerere.enabled true
$ git merge feature              # giải tay lần 1
Recorded resolution for 'cfg.py'.

$ git reset --hard HEAD~1        # huỷ, làm lại
$ git merge feature
CONFLICT (content): Merge conflict in cfg.py
Resolved 'cfg.py' using previous resolution.      ← TỰ GIẢI
```
Rất có ích khi rebase một nhánh dài nhiều lần, hoặc khi phải huỷ và làm lại một merge phức tạp. Vẫn phải `git add` để xác nhận — rerere giải nhưng không tự commit.

### 5.7 Giảm xung đột từ gốc

| Nguyên nhân | Cách giảm |
|---|---|
| Nhánh sống lâu | nhánh ngắn, merge thường xuyên (§8) |
| Format lại cả file trong một PR tính năng | formatter tự động cho **cả** repo, trong commit riêng |
| Nhiều người sửa một file trung tâm (registry, routes) | tách file, đăng ký theo module |
| Sắp xếp import thủ công | `ruff`/`isort` tự động |
| Lockfile | để tool tự sinh lại, không giải tay |
| Đổi tên hàng loạt kèm thay đổi logic | tách thành hai PR |

## 6. Commit message và commit nguyên tử

### 6.1 Commit nguyên tử là gì

> **Một commit = một thay đổi logic, đầy đủ, và tự nó build + test xanh.**

Ba tính chất, mỗi cái có lý do riêng:

| Tính chất | Vì sao |
|---|---|
| **Một** thay đổi logic | review được; revert được mà không kéo theo thứ khác |
| **Đầy đủ** | không có commit "nửa tính năng" làm vỡ `main` |
| **Tự xanh** | `bisect` dùng được (§3); mỗi commit là một điểm quay lui an toàn |

✅ Giá trị thật, đo ở Checkpoint §10.2: với 3 commit nguyên tử, gỡ bỏ phần refactor config là **một lệnh `git revert`**, chỉ chạm `app/config.py`. Với 10 commit lộn xộn ban đầu, phải revert **đúng 3 commit rải rác** (số 2, 6, 9) — và nếu nhầm một cái là kéo theo thay đổi không liên quan.

### 6.2 Tạo commit nguyên tử khi đang làm dở

```sh
git add -p                   # chọn TỪNG ĐOẠN thay đổi đưa vào commit
git add -p file.py           # chỉ file này
git commit                   # commit phần đã chọn; phần còn lại vẫn trong working tree
git stash push -p            # cất tạm một phần
git commit --fixup=<sha>     # sửa cho một commit trước đó — xem §6.4
```
`git add -p` là kỹ năng đáng học nhất trong mục này: nó cho phép bạn làm việc lộn xộn nhưng commit gọn gàng.

### 6.3 Commit message

```
<type>(<scope>): <tóm tắt ở thể mệnh lệnh, ≤ 72 ký tự>
                                                           ← dòng trống bắt buộc
<VÌ SAO thay đổi — không phải CÁI GÌ (diff đã nói cái gì)>
<ngữ cảnh, đánh đổi đã cân nhắc, giới hạn đã biết>

<footer: Refs #123, BREAKING CHANGE: ..., Co-authored-by: ...>
```

**Ví dụ tốt:**
```
fix(pricing): áp giảm giá TRƯỚC thuế thay vì sau

Commit cdb9f03 gộp hai phép tính để "tối ưu" nhưng đổi thứ tự:
thuế tính trên giá chưa giảm rồi mới trừ giảm giá. Kết quả sai
khi có CẢ giảm giá lẫn thuế (100đ, giảm 20%, thuế 10%: ra 90 thay vì 88).
Test cũ không phát hiện vì không có ca nào có cả hai.

Thêm test cho tổ hợp giảm giá + thuế.

Refs #412
```

**Ví dụ tệ, và vì sao:**

| Message | Vấn đề |
|---|---|
| `fix` | không nói gì |
| `sửa lỗi` | lỗi gì? |
| `wip` | không phải một thay đổi logic |
| `update pricing.py` | diff đã nói điều đó |
| `fix bug reported by An` | 6 tháng sau không ai biết An báo gì |
| `Refactor and add validation and fix typo` | **ba** thay đổi → phải là ba commit |

**Conventional Commits** — `type` chuẩn hoá cho phép sinh changelog và quyết định bump version tự động:

| type | Nghĩa | SemVer |
|---|---|---|
| `feat` | tính năng mới | minor |
| `fix` | sửa lỗi | patch |
| `perf` | hiệu năng | patch |
| `refactor` | đổi cấu trúc, không đổi hành vi | — |
| `docs`, `test`, `build`, `ci`, `chore` | — | — |
| `!` hoặc `BREAKING CHANGE:` | phá tương thích | **major** (C1.5 §9) |

### 6.4 `--fixup` + `--autosquash` — dọn dẹp trong lúc làm

Thay vì tạo commit "fix typo" rồi phải dọn sau, đánh dấu ngay nó thuộc về commit nào:

✅
```text
$ git commit --fixup=8ba6d29
log trước autosquash:
    38bcda5 fixup! feat(validate): them is_email      ← tự đặt tên theo commit đích
    d3bc4b8 feat(other): them other
    8ba6d29 feat(validate): them is_email

$ git rebase -i --autosquash main
log sau autosquash:
    e4363ea feat(other): them other
    4f33c85 feat(validate): them is_email             ← đã gộp, đúng vị trí
```
```sh
git config --global rebase.autoSquash true      # luôn bật
git commit --fixup=amend:<sha>                  # sửa cả thông điệp của commit đích
git commit --squash=<sha>                       # gộp nhưng cho phép sửa thông điệp
```

## 7. Pull request và review

### 7.1 Một PR tốt

| Tiêu chí | Cụ thể |
|---|---|
| **Nhỏ** | < 400 dòng thay đổi. Nghiên cứu ở Cisco/SmartBear cho thấy khả năng phát hiện lỗi giảm mạnh khi vượt ~400 dòng |
| **Một mục đích** | refactor và tính năng là hai PR; format lại là PR riêng |
| **Mô tả nói VÌ SAO** | vấn đề là gì, vì sao chọn cách này, đã cân nhắc cách nào khác |
| **Chỉ đường cho người review** | "bắt đầu từ `pricing.py`; thay đổi ở `tests/` là hệ quả" |
| **Có bằng chứng** | test mới, số đo trước/sau, ảnh chụp giao diện |
| **Commit nguyên tử** | người review có thể đọc từng commit (§6) |
| **CI xanh trước khi yêu cầu review** | không tốn thời gian người khác cho lỗi máy bắt được |

**Mẫu mô tả:**
```markdown
## Vấn đề
Tổng đơn sai khi có cả giảm giá lẫn thuế (#412).

## Nguyên nhân
cdb9f03 đổi thứ tự áp dụng — tìm bằng `git bisect` trên 621 commit.

## Thay đổi
- Khôi phục thứ tự: giảm giá → thuế
- Thêm test cho tổ hợp giảm giá + thuế

## Kiểm chứng
- `pytest` xanh; test mới thất bại trên main, xanh trên nhánh này
```

### 7.2 Review — người review

**Thứ tự ưu tiên khi đọc**, từ quan trọng nhất:
```
1. Thiết kế     cách tiếp cận có đúng không? có cần làm điều này không?
2. Đúng đắn     có bug không? trường hợp biên? lỗi (C1.6)? race (C1.9)?
3. Bảo mật      dữ liệu ngoài được kiểm tra chưa? bí mật có lọt không?
4. Test         test có kiểm chứng đúng hành vi không, hay chỉ tăng coverage?
5. Dễ bảo trì   người khác đọc hiểu được sau 6 tháng không?
6. Phong cách   ← để máy làm (formatter, linter). Người đừng bàn.
```
⚠️ Nếu phần lớn comment là về phong cách, bạn đang dùng thời gian của người cho việc của máy.

**Cách viết comment:**

| Kém | Tốt |
|---|---|
| "Sai." | "Nếu `qty` là 0 thì dòng 12 chia cho 0 — có cần kiểm tra không?" |
| "Sao lại viết thế này?" | "Mình chưa hiểu vì sao dùng vòng lặp ở đây thay vì `sum()` — có lý do về hiệu năng không?" |
| "Dùng X đi." | "Có thể dùng X ở đây, vì Y. Không bắt buộc." |

Dùng tiền tố để rõ mức độ: **`blocker:`** (phải sửa trước khi merge), **`nit:`** (nhỏ, tuỳ), **`question:`** (hỏi để hiểu), **`suggestion:`**.

### 7.3 Nhận review khó

Đây là kỹ năng cộng tác bị đánh giá thấp nhất.

1. **Tách mình khỏi code.** Comment nói về dòng 42, không nói về bạn. Người review đang giúp phần mềm của *cả nhóm* tốt hơn.
2. **Giả định thiện ý.** Comment ngắn gọn thường do vội, không phải do khinh thường.
3. **Hỏi lại khi chưa hiểu**, đừng đoán rồi sửa sai hướng. "Ý bạn là X hay Y?"
4. **Không đồng ý thì nói lý do kỹ thuật, kèm bằng chứng.** "Mình giữ cách này vì benchmark cho thấy nhanh hơn 3× (đính kèm số); nếu bạn thấy khó đọc mình sẽ thêm comment giải thích."
5. **Tranh luận quá hai vòng → chuyển sang gọi thoại.** Văn bản khuếch đại hiểu lầm.
6. **Trả lời mọi comment**: "Đã sửa ở `a1b2c3d`", "Đã tạo #413 để làm sau", hoặc lý do không sửa. Đừng để comment treo.
7. **Cảm ơn**, đặc biệt khi review tìm ra bug thật. Một bug bắt được ở review rẻ hơn ở production hàng trăm lần.

> Review khó nhất thường đến từ người quan tâm nhất tới chất lượng. Đó là người bạn muốn review code của mình.

### 7.4 Trách nhiệm hai phía

| Tác giả | Người review |
|---|---|
| PR nhỏ, mô tả rõ | review trong vòng 1 ngày làm việc |
| Tự review diff trước khi gửi | nói rõ đâu là blocker, đâu là ý kiến |
| CI xanh trước | không bàn phong cách mà máy đã quy định |
| Trả lời mọi comment | duyệt khi "đủ tốt", không đòi hoàn hảo |
| Không force-push xoá lịch sử review khi đang review | chấp nhận "để làm sau" có issue theo dõi |

## 8. Chiến lược branching

### 8.1 Hai cực

**Trunk-based development**
```
main ──●──●──●──●──●──●──●──●──●──    ← luôn deploy được
        \─●─/   \─●─/   \─●●─/        ← nhánh sống vài giờ đến 1–2 ngày
```
* Mọi người merge vào `main` **ít nhất mỗi ngày**.
* Tính năng chưa xong được giấu sau **feature flag**, không nằm trên nhánh riêng.
* Release = một tag trên `main` (hoặc nhánh release ngắn hạn chỉ để vá).

**Git-flow**
```
main     ──●───────────────●───────────●──        ← chỉ bản phát hành
            \             /             /
release      \      ●──●─/       ●──●──/
              \    /             /
develop  ──●───●──●──●──●──●──●──●──●──           ← tích hợp
             \       /   \         /
feature       ●──●──●     ●──●──●─●               ← sống nhiều ngày/tuần
hotfix                                ●──         ← vá khẩn từ main
```
* Năm loại nhánh, mỗi loại một quy tắc merge.

### 8.2 Đánh đổi

| | Trunk-based | Git-flow |
|---|---|---|
| Nhánh sống | giờ – 1 ngày | ngày – tuần |
| Xung đột | nhỏ, thường xuyên | **lớn, dồn cục** |
| Tích hợp | liên tục | khi merge về `develop` |
| Yêu cầu | **CI mạnh**, test tốt, feature flag | kỷ luật quy trình |
| Tần suất release | nhiều lần/ngày | theo lịch |
| Nhiều phiên bản song song cần hỗ trợ | khó | **dễ** |
| Phù hợp | SaaS, web, dịch vụ nội bộ | phần mềm đóng gói, firmware, thư viện có nhiều bản LTS |
| Độ phức tạp | thấp | cao |

> Tác giả của git-flow (Vincent Driessen) đã bổ sung vào bài viết gốc năm 2020 rằng với ứng dụng web phân phối liên tục, nên dùng quy trình đơn giản hơn như GitHub flow thay vì git-flow.

### 8.3 Ở giữa: GitHub flow

```
1. main luôn deploy được
2. Tạo nhánh ngắn từ main cho mỗi thay đổi
3. Mở PR sớm; CI chạy trên mỗi push
4. Review, merge vào main
5. Deploy ngay sau khi merge
```
Đây là mặc định hợp lý cho đa số nhóm: gần trunk-based, nhưng mọi thay đổi đều qua PR.

### 8.4 Feature flag — thứ cho phép nhánh ngắn

```python
if flags.enabled("new_checkout", user=user):
    return new_checkout(cart)
return old_checkout(cart)
```
Code chưa xong vẫn được merge, nhưng tắt. Lợi ích kép: không có nhánh sống lâu (không xung đột dồn cục), **và** bật dần theo % người dùng, tắt ngay khi có sự cố — một dạng degrade của C1.6 §4.3.

⚠️ Flag là nợ kỹ thuật: mỗi flag phải có ngày hết hạn và người chịu trách nhiệm xoá.

### 8.5 Chọn thế nào

```
Deploy nhiều lần/tuần, một phiên bản duy nhất đang chạy?     → trunk-based / GitHub flow
Phải hỗ trợ song song v2.x và v3.x (vá lỗi cho cả hai)?       → nhánh release dài hạn
Firmware, phát hành theo đợt, chứng nhận?                     → git-flow hoặc release branch
Nhóm mới, CI yếu, test ít?                                    → GitHub flow + đầu tư CI trước
```

### 8.6 Bảo vệ nhánh chính

Trên GitHub/GitLab, cấu hình cho `main`:
- [ ] Cấm push trực tiếp; mọi thay đổi qua PR.
- [ ] Bắt buộc CI xanh.
- [ ] Bắt buộc ≥ 1 người duyệt (không tính tác giả).
- [ ] Bắt buộc nhánh cập nhật với `main` trước khi merge.
- [ ] Cấm force-push và cấm xoá nhánh.
- [ ] CODEOWNERS: file nhạy cảm phải có người phụ trách duyệt.

## 9. Hook và CI

### 9.1 Hook là gì

Script trong `.git/hooks/` mà git gọi tại các thời điểm cố định. Mã thoát khác 0 thì **chặn** thao tác.

| Hook | Khi nào | Dùng để |
|---|---|---|
| `pre-commit` | trước khi tạo commit | lint, format, chặn bí mật, file lớn |
| `commit-msg` | sau khi viết message | kiểm tra định dạng message |
| `pre-push` | trước khi push | chạy test nhanh |
| `post-checkout`, `post-merge` | sau khi đổi branch | cài lại dependency |
| `pre-receive` | **trên server** | chính sách không thể bỏ qua |

⚠️ `.git/hooks/` **không** được commit và **không** được clone. Để cả nhóm dùng chung:
```sh
git config core.hooksPath .githooks          # đặt hook TRONG repo
```
hoặc dùng framework **`pre-commit`** (C1.2 §13.3).

### 9.2 Hai hook thật — đã chạy

**`commit-msg`:**
```sh
#!/bin/sh
first=$(head -1 "$1")
if ! printf '%s' "$first" | grep -qE '^(feat|fix|docs|refactor|perf|test|build|ci|chore|revert)(\([a-z0-9-]+\))?!?: .{3,}$'; then
  echo "commit-msg: sai định dạng: '$first'"
  echo "  ví dụ đúng: 'fix(auth): kiểm tra hết hạn token trước khi refresh'"
  exit 1
fi
[ ${#first} -gt 72 ] && { echo "commit-msg: dòng đầu ${#first} > 72 ký tự"; exit 1; }
exit 0
```
✅
```text
$ git commit -m "sua loi"
commit-msg: sai định dạng: 'sua loi'
  ví dụ đúng: 'fix(auth): kiểm tra hết hạn token trước khi refresh'

$ git commit -m "feat(core): them bien x"
-> commit OK
```

**`pre-commit`** (chặn debug còn sót, bí mật, file > 1 MiB):
```sh
#!/bin/sh
fail=0
if git diff --cached -U0 | grep -nE '^\+.*(breakpoint\(\)|import pdb|console\.log)' ; then
  echo "pre-commit: còn debug statement"; fail=1; fi
if git diff --cached -U0 | grep -niE "^\+.*(aws_secret|api_key[[:space:]]*=[[:space:]]*[\"'][A-Za-z0-9_]{16,})" ; then
  echo "pre-commit: nghi có bí mật trong commit"; fail=1; fi
for f in $(git diff --cached --name-only --diff-filter=AM); do
  s=$(git cat-file -s ":$f" 2>/dev/null || echo 0)
  [ "$s" -gt 1048576 ] && { echo "pre-commit: $f lớn hơn 1 MiB"; fail=1; }
done
exit $fail
```
✅
```text
$ git commit -m "feat: them f"         # file có breakpoint()
8:+    breakpoint()
pre-commit: còn debug statement
```

### 9.3 ⚠️ Hook tự viết của tôi đã để lọt một bí mật

Phiên bản **đầu tiên** của hook trên dùng lớp ký tự `[A-Za-z0-9]{16,}`. Nó **không chặn**:
```text
$ echo 'api_key = "sk_live_ABCDEFGH12345678XYZ"' > b.py && git add b.py
$ git commit -m "feat: cau hinh api"
[main 6984800] feat: cau hinh api            ← BÍ MẬT ĐÃ VÀO LỊCH SỬ
```
Chẩn đoán đầu tiên của tôi là sai: tôi nghĩ `\s` không được hỗ trợ trong `grep -E`. Kiểm tra lại từng phần mới ra nguyên nhân thật:
```text
KHỚP     : \s có được GNU grep -E hỗ trợ không
KHÔNG    : lớp [A-Za-z0-9] KHÔNG có gạch dưới        ← thủ phạm
KHỚP     : lớp [A-Za-z0-9_] CÓ gạch dưới
```
Khoá thật có dạng `sk_live_…` — **có dấu gạch dưới**, nên không bao giờ có 16 ký tự chữ-số liên tiếp. Regex âm thầm không khớp. Thêm `_` vào lớp ký tự thì hook chặn đúng.

Ba bài học, theo thứ tự quan trọng:
1. **Đừng tự viết bộ quét bí mật.** Dùng `gitleaks`, `trufflehog`, `detect-secrets` — chúng có hàng trăm mẫu đã được kiểm thử với định dạng khoá thật.
2. **Hook phải có test**, như mọi code khác. Một hook không chặn được ca mẫu của chính nó là hook tạo cảm giác an toàn giả.
3. **Kiểm tra giả thuyết trước khi sửa.** Tôi suýt "sửa" `\s` — một thứ không hỏng — và để nguyên lỗi thật.

⚠️ Và nếu bí mật đã vào lịch sử: **thu hồi (rotate) nó ngay**. Viết lại lịch sử (`git filter-repo`) là bước thứ hai — bí mật đã có thể nằm trong bản clone của người khác, trong cache của CI, trong log.

### 9.4 Hook không phải hàng rào

✅
```text
$ git commit --no-verify -m "feat: cau hinh api"
--no-verify: LỌT QUA
```
Mọi hook phía client đều bỏ qua được bằng `--no-verify`. Hook là **tiện ích cho lập trình viên** (phản hồi nhanh, trước khi push), không phải **cơ chế bắt buộc**.

> **Nguyên tắc:** mọi kiểm tra quan trọng trong hook phải **chạy lại trong CI**, và CI mới là nơi quyết định. (C1.2 §13.3 nói cùng điều này cho `pre-commit`.)

### 9.5 CI tích hợp với git

```yaml
# Thứ tự: rẻ và nhanh trước, đắt sau — fail sớm tiết kiệm thời gian chờ
- run: gitleaks detect --redact                  # bí mật
- run: ./scripts/check-commit-messages.sh        # Conventional Commits cho mọi commit trong PR
- run: ruff check . && ruff format --check .     # lint + format
- run: mypy --strict src                         # kiểu
- run: pytest -q                                 # test
- run: ./scripts/each-commit-builds.sh           # MỖI commit trong PR đều build (cho bisect)
```
Kiểm tra cuối đáng chú ý nhất — nó giữ cho `bisect` luôn dùng được:
```sh
#!/bin/sh
# each-commit-builds.sh: mọi commit trong PR phải tự build + test xanh
for c in $(git rev-list --reverse origin/main..HEAD); do
  git checkout -q "$c" && make -s test || { echo "commit $c không xanh"; exit 1; }
done
```
Tương đương có sẵn trong git: `git rebase -x 'make test' origin/main` — chạy lệnh sau **mỗi** commit khi rebase, dừng ở commit đầu tiên thất bại. Checkpoint §10.2 dùng đúng cơ chế này.

## 10. Checkpoint

### 10.1 Phần A — `bisect` trên repo ≥ 500 commit

#### Dựng repo

Repo mô phỏng một dịch vụ bán hàng, **621 commit**, với:
* Commit rải đều giữa tài liệu, refactor, hằng số, test phụ — như lịch sử thật.
* **Một hồi quy tinh tế** ở commit 414: "tối ưu" hàm tính tổng bằng cách gộp phép tính, vô tình đổi thứ tự áp dụng giảm giá và thuế.
* **Ba commit không build được** (lỗi cú pháp, sửa ngay ở commit sau) — để kiểm tra script bisect xử lý đúng.

✅ Trạng thái:
```text
tổng số commit: 621
HEAD      : AssertionError
commit đầu: PASS
```

#### Vì sao hồi quy này tinh tế

✅
```text
đúng (giảm trước, thuế sau): 88.0
sai  (thuế trước, trừ giảm): 90.0
không giảm giá: đúng=110.0 sai=110.0   ← GIỐNG NHAU
```
Hồi quy **chỉ** biểu hiện khi có **cả** giảm giá lẫn thuế. Mọi test chỉ có một trong hai đều xanh. Đọc diff của 621 commit để tìm là không khả thi.

#### Script kiểm tra

```sh
#!/bin/sh
# bisect_check.sh — áp dụng cả ba bài học ở §3.2
rm -rf shop/__pycache__ tests/__pycache__                              # 1. xoá artifact cũ
python3 -c "import ast,sys
for f in sys.argv[1:]: ast.parse(open(f).read(), f)" shop/*.py 2>/dev/null || exit 125   # 2. không build → BỎ QUA
PYTHONDONTWRITEBYTECODE=1 python3 tests/test_pricing.py >/dev/null 2>&1                  # 3. 0 tốt / khác 0 xấu
```

#### Chạy

```sh
git bisect start main $(git rev-list --max-parents=0 main)
git bisect run ./bisect_check.sh
git bisect reset                       # ⚠️ KHÔNG có -q (§3.2 bẫy 3)
```
✅
```text
cdb9f03f391fab22c791c30093a8e6079a4a96af is the first bad commit
  thông điệp: perf(pricing): gop phep tinh giam gia va thue
  vị trí    : commit thứ 414 / 621

số lần kiểm tra: 9       thời gian: 274 ms       lý thuyết ⌈log₂ 621⌉ = 10
```
✅ Đường đi của bisect:
```text
bad:  refactor: util 620
good: init: shop pricing
good: docs: ghi chu 310        ← chia đôi 621
bad:  refactor: util 465
good: docs: ghi chu 387
bad:  test: bo sung 426
good: docs: ghi chu 406
bad:  refactor: util 416
good: chore: hang so 411
bad:  perf(pricing): gop phep tinh   ← thủ phạm
good: test: bo sung 412
```
✅ Diff của thủ phạm:
```diff
-    after = subtotal * (1 - discount)
-    return round(after * (1 + tax), 2)
+    taxed = subtotal * (1 + tax)
+    return round(taxed - subtotal * discount, 2)   # tối ưu: gộp phép tính
```

**9 lần chạy test thay cho việc đọc 621 commit, trong 274 ms.** Và kết quả là một commit có message rõ ràng, diff 4 dòng — sửa được ngay.

> Ghi chú trung thực: trong lần chạy này, đường đi của bisect **không** rơi vào ba commit hỏng build, nên không có lần `skip` nào. Việc `exit 125` là cần thiết đã được chứng minh riêng ở §3.2 trên repo 21 commit — nơi thiếu nó khiến bisect báo sai thủ phạm.

### 10.2 Phần B — 10 commit lộn xộn thành 3 commit nguyên tử

#### Xuất phát

Nhánh `feature` với 10 commit, trộn lẫn **ba** thay đổi logic theo thứ tự thời gian làm việc:

✅
```text
wip validate             app/validate.py
config refactor start    app/config.py
fix typo                 app/validate.py
docs                     README.md
oops forgot test         tests/test_validate.py
more config              app/config.py
wip                      app/validate.py
fix test                 tests/test_validate.py
address review: rename   app/config.py
docs typo                README.md
```
Ba thay đổi logic đan xen:
* **Kiểm tra đầu vào** — commit 1, 3, 5, 7, 8
* **Refactor nạp cấu hình** — commit 2, 6, 9
* **Tài liệu** — commit 4, 10

#### Kế hoạch: todo-list của `rebase -i`

`git rebase -i main` mở một danh sách mà bạn **sửa** để ra lệnh cho git. Tôi sắp lại theo **thay đổi logic** thay vì theo thời gian:
```text
pick  e5dff70 wip validate
fixup 6008f4f fix typo
fixup a18ac31 oops forgot test
fixup cd8141a wip
fixup 5171ea0 fix test
exec  git commit --amend -q -m 'feat(validate): them kiem tra email va so dien thoai'
exec  sh -c '... chạy test ...'
pick  21a6f43 config refactor start
fixup d036533 more config
fixup 3b3776d address review: rename
exec  git commit --amend -q -m 'refactor(config): dung context manager va them load_with_default'
exec  sh -c '... chạy test ...'
pick  a0484c6 docs
fixup 30fe650 docs typo
exec  git commit --amend -q -m 'docs: huong dan module kiem tra dau vao'
exec  sh -c '... chạy test ...'
```
| Lệnh | Tác dụng |
|---|---|
| `pick` | giữ commit |
| `fixup` | gộp vào commit phía trên, **bỏ** message của nó |
| `squash` | gộp, **ghép** message để bạn sửa |
| `reword` | giữ nội dung, sửa message |
| `edit` | dừng lại để sửa commit (tách commit: `reset HEAD~` rồi `add -p`) |
| `drop` | bỏ commit |
| **`exec`** | **chạy lệnh shell**; thất bại thì **dừng rebase ngay tại đó** |

Các dòng `exec` chạy test **sau mỗi commit mới** — đó là cách chứng minh từng commit tự xanh ngay trong lúc rebase.

(Ở đây todo-list được sửa bằng một script qua `GIT_SEQUENCE_EDITOR` để tái lập được; làm tay thì sửa y hệt trong trình soạn thảo.)

#### Lần thử đầu — `exec` bắt được một lỗi

✅
```text
Executing: sh -c '... python3 tests/test_validate.py ...'
    from app.validate import is_email
ModuleNotFoundError: No module named 'app'
interactive rebase in progress; onto ea24ebd
```
Rebase **dừng đúng tại commit đầu tiên** không xanh. Nguyên nhân: chạy `python3 tests/test_validate.py` từ gốc repo thì `sys.path[0]` là `tests/`, nên `import app` thất bại — **test đó chưa bao giờ chạy được** trong cả 10 commit gốc, chỉ là chưa ai chạy nó.

```text
$ git rebase --abort
-> quay về: docs typo  (10 commit)          ← không mất gì
```
Sửa lệnh test (`PYTHONPATH=.`), chạy lại:
```text
kết quả: On branch feature
```

#### Kết quả

✅
```text
30a9bde feat(validate): them kiem tra email va so dien thoai              2 files changed, 9 insertions(+)
b7c05fa refactor(config): dung context manager va them load_with_default  1 file changed, 8 insertions(+), 1 deletion(-)
cc8692e docs: huong dan module kiem tra dau vao                           1 file changed, 3 insertions(+)
```

#### Kiểm chứng ba tiêu chí

✅ **1. Không mất nội dung** — cây thư mục cuối giống hệt từng byte:
```text
$ git diff messy HEAD
(rỗng)
tree cũ: e74c9ba44107   tree mới: e74c9ba44107      ← CÙNG SHA (§1.2)
```
So SHA của tree là cách chứng minh chặt nhất: cùng SHA nghĩa là cùng nội dung, không cần diff.

✅ **2. Mỗi commit tự xanh:**
```text
30a9bde feat(validate): ...       run.py=PASS test_validate=PASS
b7c05fa refactor(config): ...     run.py=PASS test_validate=PASS
cc8692e docs: ...                 run.py=PASS test_validate=PASS
```

✅ **3. Mỗi commit đúng một thay đổi logic:**
```text
feat(validate): ...      -> app/validate.py tests/test_validate.py
refactor(config): ...    -> app/config.py
docs: ...                -> README.md
```

✅ **An toàn:** bản lộn xộn vẫn phục hồi được bất cứ lúc nào:
```text
cc8692e rebase (finish): returning to refs/heads/feature
e5dff70 rebase (start): checkout main
```

#### Nhận xét quan trọng: "xanh" chưa đủ để gọi là nguyên tử

✅ Kiểm tra 10 commit **gốc** từng cái một:
```text
wip validate               PASS
config refactor start      PASS
fix typo                   PASS
...                        PASS  (cả 10)
```
**Cả 10 commit lộn xộn cũng đều xanh.** Nên "mỗi commit xanh" là điều kiện **cần** nhưng không đủ. Giá trị thật của 3 commit nằm ở **tính gắn kết logic**, đo được bằng việc revert:

✅
```text
revert 'refactor(config)' -> file bị đổi: app/config.py
validate vẫn còn: có | docs vẫn còn: 1 dòng
```
Một lệnh, một file, không ảnh hưởng gì khác. Với 10 commit gốc, cùng thao tác đó cần revert **đúng 3 commit rải rác** (2, 6, 9) và không bỏ sót cái nào.

### 10.3 Tự chấm

**Phần A**

| Tiêu chí | Đạt khi |
|---|---|
| Repo **≥ 500 commit** | `git rev-list --count HEAD` |
| Bisect **tự động** | `git bisect run`, không làm tay |
| Script xử lý **commit không build được** | `exit 125` |
| Script **sạch artifact** giữa các lần | không có kết quả bị đầu độc |
| Tìm **đúng** commit | kiểm chứng: cha của nó xanh, nó đỏ |
| Số bước ≈ **⌈log₂ N⌉** | giải thích được vì sao |
| **Reset** bisect đúng cách | `git bisect reset` (không `-q`) |

**Phần B**

| Tiêu chí | Đạt khi |
|---|---|
| Đúng **3** commit | `git rev-list --count main..HEAD` |
| **Không mất nội dung** | `git diff messy HEAD` rỗng, hoặc cùng SHA tree |
| **Mỗi commit tự xanh** | `exec` sau mỗi commit, hoặc `rebase -x` |
| **Mỗi commit một thay đổi logic** | file bị đổi khớp với message |
| Message theo **quy ước** | Conventional Commits, nói VÌ SAO |
| Có **lưới an toàn** | tag/branch backup, hoặc biết dùng reflog |
| Biết **abort** khi sai | `git rebase --abort` |

### 10.4 Mở rộng

1. **Tách một commit làm hai:** trong todo-list dùng `edit`, rồi `git reset HEAD~`, `git add -p`, commit từng phần, `git rebase --continue`.
2. **Bisect hồi quy hiệu năng:** tiêu chí "xấu" là chậm hơn 20% (C1.9 §11.4).
3. **Bisect trên lịch sử có merge:** so kết quả có và không có `--first-parent`.
4. **Rebase một nhánh đã bị người khác kéo về**, rồi xem chuyện gì xảy ra với họ khi pull — để thấy vì sao có quy tắc vàng ở §2.5.
5. **Viết `pre-push` hook** chạy `git rebase -x 'make test' origin/main` trên bản sao để chặn push nếu có commit không xanh.
6. **Thử `git absorb`** — tự tạo commit `fixup!` cho đúng commit đích dựa vào dòng bị sửa.

## Phụ lục A — Cheat sheet

### A.1 Nhìn vào bên trong
```sh
git cat-file -t <sha>          # loại object
git cat-file -p <sha>          # nội dung object
git hash-object <file>         # SHA mà file SẼ có
git rev-parse HEAD~2^{tree}    # SHA của tree
git ls-tree -r HEAD            # mọi file trong commit
git count-objects -vH
git log --graph --oneline --all --decorate
git merge-base A B
git log A..B                   # có trong B, không có trong A
git log A...B                  # có trong một bên, không có trong cả hai
```

### A.2 Tích hợp
```sh
git merge --no-ff feat         git merge --ff-only feat      git merge --squash feat
git rebase main                git rebase -i main            git rebase -i --autosquash main
git rebase -x 'make test' main git rebase --onto new old feat
git rebase --continue / --skip / --abort
git cherry-pick <sha>          git cherry-pick -x <sha>      # -x ghi nguồn vào message
git revert <sha>               git revert -m 1 <merge-sha>
git pull --rebase              git push --force-with-lease
```

### A.3 Commit
```sh
git add -p                     git restore --staged -p       git stash push -p
git commit --fixup=<sha>       git commit --squash=<sha>     git commit --amend
git commit -v                  # hiện diff trong trình soạn thảo khi viết message
```

### A.4 Xung đột
```sh
git config --global merge.conflictStyle zdiff3
git config --global rerere.enabled true
git show :1:f  :2:f  :3:f      # base / ours / theirs
git checkout -m f              # tạo lại dấu xung đột
git checkout --ours f / --theirs f
git log --merge -p f
git mergetool
git merge --abort
```

### A.5 Phục hồi
```sh
git reflog                     git reflog show <branch>
git reset --hard HEAD@{1}      git reset --hard ORIG_HEAD
git branch <ten> <sha>         git fsck --lost-found         git fsck --no-reflog
git stash apply <sha>
git tag backup/<ten>           # trước thao tác lớn
```

### A.6 Bisect
```sh
git bisect start BAD GOOD      git bisect run ./check.sh     git bisect reset
git bisect good / bad / skip   git bisect log / replay       git bisect start --first-parent
# check.sh: 0 tốt · 1–124 xấu · 125 bỏ qua · ≥128 dừng · XOÁ ARTIFACT CŨ
```

## Phụ lục B — Thảm họa → cách cứu

| Chuyện đã xảy ra | Cứu bằng | Ghi chú |
|---|---|---|
| `reset --hard` mất commit | `git reset --hard HEAD@{1}` | xem `git reflog` để chọn đúng |
| Xoá nhầm branch | `git branch <tên> <sha>` | sha có trong thông báo xoá, hoặc reflog |
| Rebase hỏng, đã xong | `git reset --hard ORIG_HEAD` | hoặc reflog: vị trí trước `rebase (start)` |
| Rebase hỏng, đang dở | `git rebase --abort` | |
| Merge hỏng, đang dở | `git merge --abort` | |
| Merge hỏng, đã commit, chưa push | `git reset --hard HEAD~1` | |
| Merge hỏng, **đã push** | `git revert -m 1 <merge-sha>` | không viết lại lịch sử chung |
| Commit ở detached HEAD rồi chuyển đi | `git branch <tên> <sha>` | git in sẵn lệnh này |
| `stash drop` nhầm | `git fsck --no-reflog` → `git stash apply <sha>` | sha có trong thông báo drop |
| Commit nhầm lên `main` thay vì nhánh | `git branch feat; git reset --hard HEAD~n` | commit giờ nằm ở `feat` |
| Message sai ở commit cuối | `git commit --amend` | chỉ khi chưa push |
| Quên thêm file vào commit cuối | `git add f; git commit --amend --no-edit` | |
| Sửa lỗi xung đột hỏng file | `git checkout -m <file>` | |
| **Bí mật đã commit** | **thu hồi ngay**, rồi `git filter-repo` | xem §9.3 |
| **Thay đổi chưa từng `add` rồi `reset --hard`** | **không cứu được** | commit/stash trước khi làm gì nguy hiểm |

## Tổng kết: mười điều phải mang theo

1. **Git là một DAG của object bất biến, định danh bằng SHA của nội dung.** 🔬 `sha1("blob 9\0xin chao\n")` khớp chính xác `git hash-object`. Hiểu điều này thì mọi lệnh là thao tác trên đồ thị.
2. **Branch là một file 41 byte.** Xoá branch không xoá commit.
3. **Rebase không di chuyển commit, nó tạo bản sao.** 🔬 SHA đổi từ `099d916` thành `cb02208`. Vì vậy: không rebase nhánh đã chia sẻ, và `--force-with-lease` thay cho `--force`.
4. **Commit đã tồn tại thì cứu được.** 🔬 Năm thảm họa — reset, xoá branch, rebase hỏng, detached HEAD, stash drop — đều phục hồi bằng reflog, `ORIG_HEAD` hoặc `fsck`. Chỉ thay đổi **chưa từng `add`** là mất thật.
5. **Git thường in sẵn cách cứu.** 🔬 `Deleted branch ... (was 0ef810a)`, `Dropped refs/stash@{0} (f4e7530...)`, `git branch <new-branch-name> 8a67a5b`. Đọc thông báo trước khi hoảng.
6. **`zdiff3` biến xung đột từ "chọn một bên" thành "hiểu ý định".** 🔬 Thấy bản gốc `TIMEOUT = 30` mới biết cả hai phía đều sửa. `git checkout -m` tạo lại dấu xung đột khi lỡ tay.
7. **Script bisect có ba bẫy làm nó trả sai mà không báo lỗi.** 🔬 Thiếu `exit 125` → báo commit hỏng build (c10). Bytecode cũ → báo c01. Chỉ bản xoá artifact mới ra đúng c15.
8. **Bisect biến 621 commit thành 9 lần chạy test.** 🔬 274 ms, tìm ra hồi quy mà test đơn giản không bắt được vì chỉ sai khi có cả giảm giá lẫn thuế.
9. **"Mỗi commit xanh" là cần, không đủ.** 🔬 Cả 10 commit lộn xộn đều xanh. Giá trị của 3 commit nguyên tử là revert một thay đổi bằng **một** lệnh chạm **một** file, thay vì săn 3 commit rải rác. Và cây cuối cùng cùng SHA `e74c9ba44107` chứng minh không mất gì.
10. **Hook là tiện ích, CI là hàng rào — và hook cũng cần test.** 🔬 `--no-verify` bỏ qua mọi hook. Và hook quét bí mật tôi tự viết đã để lọt `sk_live_…` vì lớp ký tự thiếu dấu gạch dưới. Dùng `gitleaks`, và kiểm tra giả thuyết trước khi sửa.
